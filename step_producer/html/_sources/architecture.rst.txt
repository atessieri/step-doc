Architecture
============

This document describes the architecture of the STEP Producer, a Python package 
for managing Decentralized Environmental Notification (DEN) service.

Overview
--------

The **STEP Producer** is a critical component of the STEP (Safer Transport for Europe Platform) ecosystem, 
specifically designed for processing and managing Decentralized Environmental Notification Messages (DENM) 
within Intelligent Transportation Systems (ITS) environments. This Redis-based microservice implements 
the DEN (Decentralized Environmental Notification) service for collision prediction and environmental 
hazard notifications.

Library
-------

The STEP Producer leverages a carefully selected set of libraries and frameworks to implement 
robust, high-performance ITS message processing capabilities. The library architecture follows 
a layered approach with core Python libraries, specialized third-party packages, and custom STEP 
ecosystem components.

Core Dependencies
^^^^^^^^^^^^^^^^^

**Pydantic**
   Advanced data validation and settings management library that provides the foundation for 
   configuration management throughout the STEP Producer. Pydantic enables:

      * **Type Safety**: Strong typing with automatic validation for all configuration parameters
      * **Schema Generation**: Automated JSON schema creation for configuration documentation
      * **Serialization**: Robust JSON serialization/deserialization for configuration persistence
      * **Model Validation**: Runtime validation of configuration data with detailed error reporting

   Used extensively in ``StepProducerConfig`` and related configuration classes to ensure 
   type-safe, validated configuration management across all Producer components.

**SortedContainers**
   High-performance pure-Python sorted container implementation that provides the data structure 
   foundation for efficient DENM record management. Key capabilities include:

      * **Sorted Lists**: O(log n) insertion and deletion with maintained ordering
      * **Memory Efficiency**: Optimized memory layout for large collections
      * **Performance**: Fast search, insert, and delete operations for time-ordered records

   Critical for the ``DenServiceDataManager`` where chronologically ordered DENM records 
   require efficient insertion, removal, and time-based queries for expiration management.

**step_cloud_schemas**
   Custom STEP ecosystem library that defines standardized ITS message schemas and data structures. 
   This library provides:

      * **DENM Schemas**: Complete ``DenmDataV1`` message structures compliant with ETSI standards
      * **Cloud Events**: Standardized cloud event wrappers for ITS message distribution
      * **ITS Primitives**: Core ITS data types including timestamps, positions, and identifiers
      * **Collision Data**: ``StationCollisionArrayV1`` structures for collision prediction integration

   Essential for maintaining compatibility across the STEP ecosystem and ensuring standard-compliant 
   message generation and processing.

**step_redis**
   STEP-specific Redis integration library that provides the messaging and stream processing
   foundation as a black box interface. Core functionality includes:

      * **Connection Pooling**: Efficient Redis connection management with automatic reconnection
      * **Stream Processing**: High-level abstractions for Redis streams with consumer group support
      * **Message Serialization**: Automatic conversion between Python objects and Redis stream data
      * **Error Handling**: Robust error handling and recovery mechanisms for Redis operations

   Provides the base classes ``StepRedisPool`` and ``StepRedisStream``, along with specialized
   implementations like ``StepProducerRedisStream`` and ``StepClientRedisStream`` for different
   stream operations. The STEP Producer uses these classes directly without custom extensions.

**python-dotenv** (through step_redis)
   Loads Redis connection credentials from the ``.env`` file of the current working
   directory (or its nearest parent) into the process environment at startup, without
   overriding a variable already set, so secrets are kept out of the (persisted) JSON
   configuration document. Used by step_redis ``RedisCredential.from_env()``, called by the
   ``StepProducerApp`` constructor (see :ref:`step_producer_credentials`).

Architecture Integration
^^^^^^^^^^^^^^^^^^^^^^^^

The library selection supports the STEP Producer's architectural requirements:

* **High Performance**: SortedContainers and asyncio enable efficient handling of high-frequency 
  collision detection scenarios
* **Type Safety**: Pydantic provides compile-time and runtime type validation throughout the system
* **Standards Compliance**: step_cloud_schemas ensures ETSI ITS standard compliance for all messages
* **Scalability**: step_redis abstractions support horizontal scaling through Redis stream 
  distribution
* **Maintainability**: Comprehensive development tooling ensures code quality and documentation 
  standards

Components
----------

The architecture follows a modular design pattern that separates concerns between DEN service management, 
communication, Redis integration, and configuration management. This enables flexibility and maintainability 
in the system design.

Main Components:

   #. **DenServiceManager**: Orchestrator for DEN service lifecycle, including message creation, 
      processing, and termination
   #. **DenServiceDataManager**: Data management for DENM records with multi-index storage
   #. **OrderedListRecord/RecordKey**: Time-ordered record management with unique record keys
   #. **Redis Integration (step_redis)**: Redis connection pooling and stream processing via 
      StepRedisPool and StepRedisStream base classes
   #. **StepProducerConfig**: Configuration management for the Producer
   #. **StepLogger** (from ``step_cloud_schemas``): Logging utilities used by the STEP Producer
   #. **StepException**: Custom exceptions for error handling
   #. **Main Application (__main__)**: Command-line interface; runs ``StepProducerApp``
      through ``AppRunner`` (from ``step_cloud_schemas``)
   #. **StepProducerApp**: Workload of the program: environment-based Redis credentials,
      asynchronous task orchestration and automatic reconnection
   #. **Application Runtime** (from ``step_cloud_schemas``): ``AppRunner``, which runs the
      workload with a cooperative shutdown, and the abstract classes ``AbstractApp`` and
      ``ReconnectingApp``, which ``StepProducerApp`` derives from

DenServiceManager
^^^^^^^^^^^^^^^^^

The ``DenServiceManager`` class serves as the primary orchestrator for DEN (Decentralized Environmental 
Notification) services within the STEP Producer architecture. This component manages the 
complete lifecycle of collision risk notifications, from initial detection through message 
termination and cleanup.

**Core Responsibilities:**

   #. **Collision Event Processing**: Receives and processes ``StationCollisionArrayV1`` objects, converting 
      collision detection data into structured DENM messages for distribution throughout the ITS network.
   #. **Message Lifecycle Management**: Orchestrates the DENM message lifecycle, including creation, 
      update handling, and cancellation of expired notifications; the messages it returns are
      published by ``StepProducerApp``.
   #. **Termination Handling**: Processes incoming DENM records with negation termination flags, ensuring 
      proper cleanup of cancelled collision notifications.
   #. **Automatic Cleanup**: ``periodical_cleanup()`` removes the expired DENM records and returns a
      cancellation copy of each one still within its validity, which ``StepProducerApp`` publishes.

``DenServiceManager`` is synchronous and has no Redis access: all Redis reading and publishing is
done by ``StepProducerApp``.

**Key Methods:**

   * ``process_station_collisions_received()``: Main entry point for processing collision arrays, delegating 
     to the data manager for record creation and returning list of DENM messages
   * ``process_denm_record_received()``: Handles incoming DENM records, specifically processing 
     termination requests with negation flags
   * ``periodical_cleanup()``: Removes the records whose reference time is older than
     ``denm_last_update_max_delay_ms`` and returns a cancellation message for each removed record
     still within its ``validityDuration``
   * ``_denm_create_cancellation()``: Creates cancellation DENM messages by copying original message data 
     while setting the termination flag

**Architecture Integration:**

The ``DenServiceManager`` is a synchronous facade over the ``DenServiceDataManager``: it turns the received
messages into data operations and returns the DENM messages to publish. ``StepProducerApp`` creates a single
instance for the whole run (kept across Redis reconnects) and shares it between its receive and cleanup tasks;
the methods never await, so the two tasks never interleave inside it.

**Configuration Parameters:**

   * ``station_id``: Unique identifier for the originating ITS station
   * ``time_after_collision_sec``: Duration in seconds to continue broadcasting a DENM after the estimated
     collision time (added to the time to collision to form the ``validityDuration``)
   * ``denm_last_update_max_delay_ms``: Maximum age in milliseconds of a record's reference time before the
     record is treated as expired by the cleanup

DenServiceDataManager
^^^^^^^^^^^^^^^^^^^^^

The ``DenServiceDataManager`` class provides comprehensive data management capabilities for DENM records, 
implementing efficient storage, indexing, and retrieval mechanisms optimized for high-frequency collision 
detection scenarios. This component serves as the persistent storage layer for the DEN service, maintaining 
multiple data structures for optimal performance.

**Internal Architecture:**

The data management layer consists of four primary data structures:

   #. **DenmRecordInfo**: A frozen dataclass that encapsulates DENM data (``DenmDataV1``) and its record key;
      the reference time (``ItsTime``) and the monotonic creation timestamp are derived on initialization
      (from the DENM's management container and ``time.monotonic()``) and cannot be passed to the constructor.
   #. **OrderedListRecord**: A time-ordered record container with comparison operators for chronological 
      sorting. Pairs a reference time with a unique record key for efficient sorted list operations.
   #. **RecordKey**: A frozen dataclass holding unique identifiers for DENM records, containing reference 
      and involved actor IDs (station ID and object ID pairs).
   #. **DenServiceDataManager**: The core service class that manages collections using multiple specialized 
      indices for optimal performance across different access patterns.

**Data Storage Strategy:**

The data manager employs a multi-index architecture for optimal performance:

   * ``_denm_sorted_records``: A ``SortedList[OrderedListRecord]`` maintaining chronological ordering 
     for efficient time-based operations O(log n). Each record contains reference time and record key.
   * ``_record_key_index``: Hash-based dictionary ``dict[RecordKey, DenmRecordInfo]`` providing O(1) 
     lookup by unique record keys composed of reference and involved actor identifiers
   * ``_action_id_index``: Hash-based dictionary ``dict[ActionId, DenmRecordInfo]`` enabling fast 
     retrieval by action ID (originating station ID and sequence number)

**Key Functionality:**

   #. **Collision Array Processing**: The ``insert_station_collision_array()`` method converts a station
      collision array into DENM records, one for the reference station (the first after ordering) paired
      with each other station (k-1 records for k stations); the stations are ordered by station ID and
      object ID. A pair repeated in the same array is built once, the last occurrence winning. The
      records are first all built and then committed together: if any of them fails, no record of the
      array is created or updated.
   #. **DENM Content**: The validity duration is the time to collision (rounded up, never negative)
      plus ``time_after_collision_sec``. The situation's event type is the collision risk cause code,
      with the sub cause code selected by the type of the involved station (pedestrian, cyclist,
      vulnerable road user for mopeds, motorcycles, light VRU vehicles and animals, motor vehicle for
      the other vehicle types, unavailable otherwise). A station type confidence of 0 becomes an
      unavailable object type confidence.
   #. **Multi-Index Management**: Maintains synchronized indices across all data structures, ensuring 
      consistency during record creation, updates, and deletions while providing optimal access patterns 
      for different query types.
   #. **Automatic Expiration**: The ``get_denm_records_clean_reference_expired()`` method identifies 
      expired records based on configurable delay thresholds, supporting automatic cleanup operations.
   #. **Sequence Number Generation**: Generates the sequence numbers of the action IDs; after
      ``ActionId.SEQUENCE_NUMBER_MAX`` the counter wraps around and skips the sequence numbers still held
      by a tracked record, so a live ActionId is never reissued; ``OverflowError`` is raised when every
      sequence number is held by a tracked record. An existing record keeps its ActionId on update.

**Record Management:**

Each DENM record is uniquely identified by a ``RecordKey`` containing:

   * ``reference_actor_id``: ActorId (station_id, object_id) of the reference vehicle
   * ``involved_actor_id``: ActorId (station_id, object_id) of the involved vehicle

This structure enables precise tracking of collision relationships between specific ITS entities. The system 
supports both new record creation and existing record updates, reusing action IDs where appropriate to 
maintain message continuity.

**Performance Optimizations:**

   * Utilizes ``__slots__`` for memory efficiency in ``DenServiceDataManager`` and ``OrderedListRecord`` classes
   * Uses frozen dataclasses for ``DenmRecordInfo`` and ``RecordKey`` for immutability and performance
   * Implements ``SortedList`` for maintaining chronological order without manual sorting overhead
   * Caches hash values in ``OrderedListRecord`` for efficient dictionary/set operations
   * Provides multiple access patterns (chronological, key-based, action ID-based) for different operational requirements
   * Includes comprehensive logging with configurable detail levels for operational monitoring and debugging

**Expiration Management:**

``get_denm_records_clean_reference_expired()`` removes the records whose reference time is
older than ``now - denm_last_update_max_delay_ms`` and returns the DENM of those still within
their own ``validityDuration`` (by monotonic age), for which a cancellation is published; the
removed records no longer valid produce no cancellation. The cleanup runs every
``denmCheckLastUpdateInterval`` seconds.

**Thread Safety:**

No locking is used around the indexes. All the methods are synchronous (they never await), so one
instance can be shared by several asyncio tasks of the same event loop, as ``StepProducerApp`` does
through its ``DenServiceManager``; it must not be shared between threads.

OrderedListRecord Module
^^^^^^^^^^^^^^^^^^^^^^^^^

The ``ordered_list_record`` module provides lightweight, memory-efficient data structures for time-ordered 
operations in DENM management. This module is designed specifically for high-frequency, time-ordered 
operations (insert, search, delete) in sorted lists and hash tables.

**Core Components:**

   #. **RecordKey**: A frozen dataclass that holds unique identifiers for DENM records:
      
      * ``reference_actor_id``: ActorId containing station_id and object_id of reference vehicle
      * ``involved_actor_id``: ActorId containing station_id and object_id of involved vehicle
      
      Provides immutable record identification with automatic hashing for efficient dictionary operations.
   
   #. **OrderedListRecord**: A time-ordered record container implementing rich comparison operators:
      
      * Encapsulates reference time (``ItsTime``) and record key (``RecordKey``)
      * Implements ``__lt__``, ``__le__``, ``__gt__``, ``__ge__`` for chronological ordering
      * Implements ``__eq__`` and ``__hash__`` based on the (reference time, record key) pair,
        consistently with the ordering
      * Uses ``__slots__`` with hash caching for minimal memory footprint
      * Decorated with ``@total_ordering`` for complete comparison support

**Design Features:**

   * **Memory Efficiency**: Uses ``__slots__`` to minimize memory overhead per record
   * **Hash Caching**: Caches hash values during initialization for fast dictionary/set operations
   * **Immutable Keys**: Frozen dataclasses ensure record keys cannot be modified after creation
   * **Comparison Semantics**: 
     
     - Ordering based on reference time (chronological), ties broken by record key
     - Equality based on reference time and record key
   
   * **Type Safety**: Leverages dataclass validation and type hints for robust implementation

**Integration with DenServiceDataManager:**

The ``OrderedListRecord`` instances are stored in the ``_denm_sorted_records`` SortedList, enabling:

   * O(log n) insertion maintaining chronological order
   * O(log n) deletion when records expire
   * O(1) equality checks for duplicate detection
   * Fast iteration over time-ordered records for cleanup operations

This separation of concerns allows the ``DenServiceDataManager`` to focus on business logic while 
leveraging optimized data structures for time-ordered operations.

StepProducerConfig
^^^^^^^^^^^^^^^^^^

The ``StepProducerConfig`` component provides comprehensive configuration management for the STEP Producer architecture, 
leveraging Pydantic for robust validation, serialization, and schema generation capabilities. This component serves as 
the central configuration hub that defines all operational parameters, connection settings, and behavioral configurations
for the Producer service.

**Hierarchical Configuration Architecture:**

The configuration system follows a well-structured hierarchical model with multiple specialized configuration classes:

   #. **StepProducerConfig**: Top-level configuration class that orchestrates all Producer settings
   #. **RedisClientConfig**: Dedicated configuration for Redis connectivity and stream management
   #. **RedisConnection** (from step_redis): Low-level Redis connection parameters including SSL, timeouts, and pooling
   #. **RedisStreams**: Stream-specific configuration for input/output stream definitions
   #. **LogConfig**: Comprehensive logging configuration with multiple handler types

**Core Configuration Domains:**

**Producer Instance Settings:**

   * ``templateVersion``: Configuration schema version for compatibility management; only ``"1"`` is accepted
   * ``instanceName``: Unique identifier for the Producer instance within the ecosystem, also used as the
     Redis stream consumer name (not in config model, ``-i``/``--instance`` runtime parameter)
   * ``stationId``: ITS station identifier (0-4294967295) for message origination
   * ``timeAfterCollision``: Duration in seconds to continue broadcasting a DENM after the estimated collision time (0-10)
   * ``denmLastUpdateMaxDelay``: Maximum age in milliseconds of a record's reference time before it expires (1-10000)
   * ``denmCheckLastUpdateInterval``: Period in seconds of the expired DENM cleanup (1-60)
   * ``reconnectInterval``: Time interval in seconds for automatic reconnection attempts (1-10)

**Redis Integration Configuration:**

The ``RedisClientConfig`` provides comprehensive Redis connectivity management:

   * **Connection Management**: Database selection, SSL configuration and pool settings; the Redis host,
     port and credentials are not in the configuration, they are read from the ``REDIS_*`` environment
     variables (see :ref:`step_producer_credentials`)
   * **Socket Configuration**: Advanced socket settings for timeout management, keepalive parameters,
     and connection health monitoring
   * **Stream Configuration**: The input stream (``RedisStreamInput``: ``streamId``, consumer group
     ``groupId``, receive ``waitTimeout`` of at least 10000 ms) and the client output stream
     (``RedisStreamOutput``: ``streamId``, approximate ``maxLength`` of at least 1)
   * **Read Timeout Check**: ``connection.socketTimeout`` must be at least ``streams.input.waitTimeout``
     plus ``READ_TIMEOUT_MARGIN_MS`` (5000 ms), otherwise validation fails: a blocking ``XREADGROUP``
     that times out first drops the connection and loses any message delivered in that instant (the
     input stream is read with ``noack``)
   * **Security Settings**: SSL/TLS configuration with client certificates, CA verification, and 
     encrypted connections

**Logging System Configuration:**

The ``LogConfig`` component supports multiple logging strategies through a flexible handler system:

   * **LogStreamHandler**: Console-based logging for development and debugging
   * **LogFileHandler**: File-based logging with append/overwrite options
   * **LogSizeFileRotateHandler**: Size-based log rotation with configurable thresholds 
     and backup counts
   * **LogTimeFileRotateHandler**: Time-based log rotation supporting various intervals 
     (seconds, minutes, hours, days, weekdays)
   * **LogNullHandler**: Null logging for production environments requiring log suppression

**Validation and Schema Features:**

   #. **Strong Typing**: Comprehensive type annotations with Pydantic field validation for 
      all configuration parameters
   #. **Range Validation**: Numeric fields include appropriate range constraints 
      (e.g., station IDs 0-4294967295, keepalive intervals 1-32767)
   #. **String Validation**: Minimum length requirements and format validation for critical 
      string fields
   #. **Immutable Configuration**: Frozen model instances prevent accidental modification 
      after initialization
   #. **Schema Generation**: Automated JSON schema generation for configuration documentation 
      and validation
   #. **Default Factory Methods**: The configuration models provide ``get_default()`` methods 
      for rapid setup

**Configuration Management Utilities:**

   * ``print_config_schema()``: Generates the JSON schema file (``step_producer_config_v1_schema.json``,
     with ``$id`` and ``$schema`` set) for external configuration validation
   * ``print_config_example()``: Creates the example configuration file
     (``step_producer_config_v1_schema_template.json``) with the ``get_default()`` values
   * ``model_validate()``: Validates configuration data against the defined schema
   * ``model_dump_json()``: Serializes configuration to JSON format for persistence

**Security and Production Considerations:**

The configuration system includes production-ready security features:

   * SSL/TLS configuration for encrypted Redis connections
   * Redis authentication read from the environment, never stored in the configuration file
   * Certificate-based authentication with client key and certificate file support
   * Health check intervals for connection monitoring
   * Configurable connection pooling for performance optimization

**Integration with STEP Ecosystem:**

The configuration integrates seamlessly with other STEP components by providing standardized 
configuration patterns, consistent validation rules, and compatible schema definitions that 
enable configuration sharing and validation across the entire STEP platform.


Redis Integration (step_redis)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The STEP Producer integrates with Redis through the **step_redis** library, which provides 
the messaging infrastructure as a black box with well-defined interfaces. This library handles 
all Redis connection management, stream processing, and message serialization/deserialization.

**step_redis Interface:**

The library exposes several key abstractions used by STEP Producer:

   * **StepRedisPool**: Base class for managing Redis connection pools with automatic 
     reconnection and health monitoring
   * **StepRedisStream**: Base class for Redis stream operations providing:
     
     - Stream creation and consumer group management
     - Asynchronous message publishing
     - Message reception with automatic deserialization
     - Context manager support for resource cleanup
   
   * **StepRedisPoolParams**: Configuration parameters for connection pool initialization
   * **StepRedisStreamParams**: Configuration parameters for stream setup
   * **StepProducerRedisStream**: Producer input stream, used to receive:
     
     - Collision data from the ``step_crash_prediction`` component
     - DENM messages (negations) from the ``step_client`` component
   
   * **StepClientRedisStream**: Client output stream, used to publish the generated DENMs and the
     cancellations to ``step_client`` for distribution

**Message Flow:**

   #. **Input Processing**: Monitors Redis streams for:
      
      - ``ProducerCloudEventsStationCollisionArrayV1``: Collision prediction data
      - ``ProducerCloudEventsDenmDataV1``: DENM records (for negation processing)
   
   #. **Output Publishing**: Publishes generated DENM messages to the client output stream as
      ``ClientCloudEventsDenmDataV1`` cloud events

**Integration Benefits:**

   * Transparent connection pooling and resource management
   * Automatic message serialization using step_cloud_schemas
   * Consumer group support; the input is read without acknowledgement (``noack``), so a message
     is delivered at most once and is lost if its processing fails
   * Asynchronous operations for high throughput
   * Configurable retry and reconnection logic

The step_redis library abstracts all Redis-specific implementation details, allowing the 
STEP Producer to focus on DEN service logic while maintaining reliable, high-performance 
message processing.

StepLogger
^^^^^^^^^^

.. note::
   ``StepLogger`` is not part of the ``step_producer`` package itself - it is imported from
   the external ``step_cloud_schemas`` dependency and used by the STEP Producer for logging.

The ``StepLogger`` component provides specialized logging functionality used by the STEP Producer
architecture, enabling comprehensive and configurable logging throughout the application.
It serves as a wrapper around Python's standard logging facilities with additional features
tailored to STEP Producer's needs.

Key features of ``StepLogger`` include:

   #. **Multi-destination Logging**: Supports logging to different output formats and 
      destinations, including:
      
      * File-based logging for persistent records
      * Standard output (console) for development and debugging
      * Configurable log rotation based on size or time intervals
   
   #. **Log Level Management**: Provides fine-grained control over logging verbosity 
      with standard log levels (DEBUG, INFO, WARNING, ERROR, CRITICAL).
   #. **Structured Formatting**: Implements customizable log formats with timestamp, 
      severity level, source component, and structured message content.
   #. **Context-aware Logging**: Includes context information such as component IDs, 
      transaction IDs, and operation details to facilitate troubleshooting.
   #. **Configuration Integration**: Leverages the logging configuration section 
      from ``StepProducerConfig`` to enable consistent setup across components.
   #. **Utility Methods**: Offers ``get_logger()``, which configures and returns the logger
      from the ``log`` section of the configuration, and ``logger_force_write()``, which writes
      a line regardless of the configured level.
   #. **Error Handling**: Includes robust error handling to prevent logging failures 
      from impacting core application functionality.

The ``StepLogger`` component ensures that the STEP Producer maintains comprehensive 
logging capabilities to support monitoring, debugging, and operational insights 
across all system components.

StepException
^^^^^^^^^^^^^

The ``step_exception`` module defines two plain exception classes:

   #. **StepProducerError**: Base class of the STEP Producer exceptions.
   #. **StepCliError**: Command line misuse (only one of ``-c``/``--config`` and
      ``-i``/``--instance``); ``main()`` logs it as a single error line, without a
      traceback, and returns ``ExitCode.USAGE``.

Main Application (__main__)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The main application module is the command-line entry point. It parses the arguments,
loads the configuration and hands the workload, ``StepProducerApp``, to ``AppRunner``
(from ``step_cloud_schemas``), which owns the event loop and the signal handling.

Key features of the main application include:

   #. **Command-Line Interface**: Provides a CLI (``_args_parse()``) with options for:

      * no option: Display the help (exit code ``USAGE``)
      * ``--help``/``-h`` and ``--version``/``-v``: Display help or version information
        (exit code ``OK``); an invalid or unknown option exits with ``USAGE``
      * ``--conf_schema``/``-s``: Write the JSON configuration schema into a directory
      * ``--conf_template``/``-t``: Write the configuration template into a directory
      * ``--config``/``-c`` and ``--instance``/``-i``: Load configuration and run the service;
        the two options must be given together, otherwise ``StepCliError`` is logged as a
        plain error line and the exit code is ``USAGE``

   #. **Logging Setup**: Reconfigures ``StepLogger`` from the loaded configuration and logs
      the program, ``step_cloud_schemas`` and ``step_redis`` versions.
   #. **Application Run**: Builds ``AppRunner[ExitCode]`` (selector event loop on Windows,
      as for the other STEP programs) and runs ``StepProducerApp``, returning its exit code.
   #. **Exception Handling**: ``KeyboardInterrupt`` returns ``ABORTED``; any other unhandled
      exception (e.g. an invalid configuration file or a missing ``REDIS_URL``/``REDIS_PORT``
      variable) is logged with its traceback and returns ``ERROR``.

Application Runtime (step_cloud_schemas)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. note::
   ``AppRunner``, ``AbstractApp`` and ``ReconnectingApp`` are not part of the ``step_producer``
   package: they are imported from the external ``step_cloud_schemas`` dependency, shared by the
   STEP programs. Only their public interface, the part used by the STEP Producer, is described here.

The three classes split a long-running program in two parts: the process-wide plumbing (event
loop, signal handlers, exception hooks), owned by ``AppRunner``, and the workload, supplied by the
program as an ``AbstractApp`` subclass. ``R`` is the program's result type: for the STEP Producer,
``ExitCode``.

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - Class
     - Role
   * - ``AbstractApp[R]``
     - Abstract base class of a workload run by ``AppRunner``. It declares the two methods
       ``AppRunner`` needs and holds no state (empty ``__slots__``, so a subclass declares its own).
   * - ``ReconnectingApp[R]``
     - Abstract ``AbstractApp`` subclass that implements ``work`` as a reconnect loop around a
       connection cycle, implemented by the program.
   * - ``AppRunner[R]``
     - Singleton that runs an ``AbstractApp`` on a new event loop until it ends or a shutdown
       signal stops it.

The class diagram below shows the public interface of the three classes and how
``StepProducerApp`` plugs into them:

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      !theme plain
      skinparam classAttributeIconSize 0

      package "step_cloud_schemas" {
         abstract class "AbstractApp[R]" as AbstractApp {
            +{abstract} async work() : R
            +{abstract} on_shutdown(stop_signal : Signals) : R
         }

         abstract class "ReconnectingApp[R]" as ReconnectingApp {
            +__init__(logger : Logger, reconnect_interval : int)
            +{abstract} async cycle() : None
            +{abstract} fatal_result() : R
            +async work() : R
         }

         class "AppRunner[R]" as AppRunner <<singleton>> {
            +__init__(logger_param : Logger, loop_factory = None, exception_handler = None, unraisable_handler = None)
            +logger : Logger <<property>>
            +run(app : AbstractApp[R]) : R
         }
      }

      package "step_producer" {
         class "StepProducerApp" as StepProducerApp {
            +__init__(instance_name : str, config : StepProducerConfig, logger : Logger)
            +async cycle() : None
            +fatal_result() : ExitCode
            +on_shutdown(stop_signal : Signals) : ExitCode
         }

         enum ExitCode {
            OK = 0
            USAGE = 1
            ERROR = 2
            ABORTED = 3
         }
      }

      ReconnectingApp --|> AbstractApp
      StepProducerApp --|> ReconnectingApp : R = ExitCode
      AppRunner ..> AbstractApp : run(app)
      StepProducerApp ..> ExitCode : returns

      note bottom of AppRunner
         main() builds AppRunner[ExitCode]
         (SelectorEventLoop on Windows)
         and calls run(StepProducerApp(...))
      end note

**AbstractApp: public interface**

   * ``async work() -> R`` (abstract): The workload, called once per run as a task of the
     ``AppRunner`` ``TaskGroup``; it returns the result when it ends on its own. On a shutdown
     signal it is cancelled at the ``await`` it is suspended on, so it has to be
     cancellation-safe.
   * ``on_shutdown(stop_signal: Signals) -> R`` (abstract): Called by ``AppRunner`` after a
     shutdown signal stopped ``work``, once every task has unwound (the resources held by ``work``
     are already released); it runs on the event loop thread and cannot ``await``. Its value is
     the result of the run.

**ReconnectingApp: public interface**

   * ``ReconnectingApp(logger, reconnect_interval)``: ``logger`` is used for the start, error and
     retry messages, ``reconnect_interval`` is the number of seconds to wait before the next cycle.
   * ``async cycle() -> None`` (abstract): Opens the connections and runs the tasks until one of
     them fails; returns only if every task ends normally, and then the next cycle starts at once.
     Like ``work``, it has to be cancellation-safe.
   * ``fatal_result() -> R`` (abstract): The result returned by ``work`` after an error that a
     reconnect cannot fix.
   * ``async work() -> R``: Logs ``Program started``, then runs ``cycle`` in a loop. When ``cycle``
     raises:

        - while a shutdown cancellation is in progress, the error is logged at INFO level and
          ``CancelledError`` is restored, so the shutdown goes on without an ERROR traceback;
        - otherwise the error is logged with its traceback, and if it, or any error nested in an
          ``ExceptionGroup`` (as raised by a ``TaskGroup``), is one of the subclass's fatal error
          types, ``work`` returns ``fatal_result()``;
        - otherwise ``work`` waits ``reconnect_interval`` seconds and runs ``cycle`` again.

     It never returns otherwise: the loop ends only when ``AppRunner`` cancels it.

   The fatal error types are a class attribute that each subclass sets (``StepProducerApp``:
   ``StepRedisFatalError``); with none set, every error is retried.

**AppRunner: public interface**

   * ``AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None)``:

        - ``logger_param``: Logger used by the default exception and unraisable handlers.
        - ``loop_factory``: Factory of the event loop created by every ``run``, forwarded to
          ``asyncio.Runner``; ``None`` uses the asyncio default loop. The STEP Producer passes
          ``asyncio.SelectorEventLoop`` on Windows, as the other STEP programs do.
        - ``exception_handler``: Event loop exception handler; ``None`` logs the exception on
          the logger.
        - ``unraisable_handler``: Installed as ``sys.unraisablehook``; ``None`` logs the exception
          on the logger.

     The constructor installs the process-wide hooks (signal handlers, ``sys.unraisablehook``): it
     is called from the main thread as early as possible, which is why ``main()`` builds it before
     parsing the arguments, so that a signal received before ``run`` is still handled. Being a
     singleton, only the first construction takes effect; the arguments of later calls are ignored.
   * ``logger`` (property): The logger given to the constructor.
   * ``run(app: AbstractApp[R]) -> R``: Opens an ``asyncio.Runner``, installs the exception handler
     and the shutdown handlers (``SIGINT``/``SIGTERM`` on POSIX, ``CTRL_C``/``CTRL_BREAK`` on
     Windows), then runs ``app.work()`` next to a shutdown watcher in a ``TaskGroup``. It returns
     the value of ``app.work()`` when the workload ends on its own, or the value of
     ``app.on_shutdown(stop_signal)`` when a shutdown signal stops it. Any other exception raised
     by ``work`` propagates wrapped in an ``ExceptionGroup``, which ``main()`` logs and maps to
     ``ExitCode.ERROR``.

   A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only
   sets an event, the watcher task turns it into an exception, and the ``TaskGroup`` cancels
   ``work`` at the ``await`` it is suspended on.

StepProducerApp
^^^^^^^^^^^^^^^

``StepProducerApp`` (module ``step_producer_app``) is the ``ReconnectingApp`` subclass
(step_cloud_schemas, see `Application Runtime (step_cloud_schemas)`_) run by ``AppRunner``:
the reconnecting DEN service on top of the Redis
streams. It implements one connection cycle (``cycle()``) and the result of a fatal error
(``fatal_result()``), while the reconnect loop is the inherited ``work()``. It also defines
the ``ExitCode`` enumeration.

Key features of ``StepProducerApp`` include:

   #. **Environment-Based Credentials**: the constructor calls step_redis
      ``RedisCredential.from_env()`` once: it loads the ``.env`` file of the current working
      directory (or an ancestor of it) and reads ``REDIS_URL``, ``REDIS_PORT``,
      ``REDIS_USERNAME``, and ``REDIS_PASSWORD`` from the environment (see
      :ref:`step_producer_credentials`); ``REDIS_URL`` and ``REDIS_PORT`` are required, the
      username and password are optional (an empty value counts as unset).
      Reading them at construction (not in ``cycle()``) makes a missing variable end the
      program instead of being retried forever.
   #. **Asynchronous Task Orchestration**: the constructor creates a single
      ``DenServiceManager``; each ``cycle()`` opens a ``StepRedisPool`` (parameters from
      ``StepRedisPoolParams.from_connection()``, at most ``_REDIS_MAX_CONNECTIONS`` = 2
      connections) and the client output stream, then uses
      ``asyncio.TaskGroup`` to run three concurrent tasks - ``_stream_receive_run()`` (stream
      reception and dispatch), ``_periodical_cleanup_run()`` (expired DENM cleanup) and
      ``_redis_health_check_run()`` (Redis connection health check). The receive and cleanup tasks
      publish on the same client output stream.
   #. **Message Dispatch**: ``_producer_message_dispatch()`` routes a ``ProducerCloudEventsDenmDataV1``
      to ``_denm_message_handler()`` and a ``ProducerCloudEventsStationCollisionArrayV1`` to
      ``_station_collision_array_message_handler()``, whose DENMs are published as a batch by
      ``_denm_messages_publish()``; any other type is skipped with a warning. Each handler, the batch
      publish and each cleanup are timed by a ``LoggingTimer`` at INFO level.
   #. **Stream Parameters**: ``_input_stream_params()`` builds the input stream parameters (stream,
      consumer group, wait timeout, the instance name as consumer, TTL from
      ``StepRedisStreamParams.ttl_seconds_from_wait_timeout()``), also used by the health check;
      ``_client_stream_params()`` builds the client output stream parameters (stream and
      ``maxLength``).
   #. **Per-Message Error Isolation**: A received message whose processing raises ``ValueError``
      (pydantic ``ValidationError`` included) is logged and dropped; the loop goes on and the tracked
      DENM records are kept. A collision array is applied all or nothing.
   #. **Automatic Reconnection**: On any other error, the inherited ``work()`` waits
      ``config.reconnectInterval`` seconds and runs ``cycle()`` again, keeping the same
      ``DenServiceManager`` (tracked records and ActionId sequence survive the reconnect).
   #. **Permanent Errors**: An error that a reconnect cannot fix (``_FATAL_ERRORS``:
      ``StepRedisFatalError`` from step_redis, i.e. rejected credentials, ACL denial, missing
      SSL file, untrusted certificate) ends the run with ``fatal_result()``
      (``ExitCode.ERROR``) instead of retrying forever.
   #. **Graceful Shutdown**: Delegated to ``AppRunner``: on ``SIGINT``/``SIGTERM`` (POSIX) or
      ``CTRL_C``/``CTRL_BREAK`` (Windows) it cancels ``work()``, the ``async with`` blocks
      release the Redis pool and streams, and ``on_shutdown()`` logs the signal and returns
      ``ExitCode.ABORTED``. A failure raised while the cancellation unwinds is turned back
      into ``CancelledError`` instead of triggering a reconnect, and is logged at INFO level
      without an ERROR traceback.
   #. **Exit Code Management**: Defines standard exit codes through the ``ExitCode`` enum:

      * OK (0): Successful execution
      * USAGE (1): Invalid command-line usage
      * ERROR (2): General execution error
      * ABORTED (3): Process interrupted by signal

Performance Considerations
--------------------------

The STEP Producer architecture is designed for high-performance processing of ITS messages with 
careful consideration of algorithmic complexity and data structure selection. The following analysis 
provides Big O complexity calculations for the two primary message processing scenarios.

Data Structure Performance Characteristics
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The ``DenServiceDataManager`` employs a multi-index architecture optimized for different access patterns:

* **Sorted List (``_denm_sorted_records``)**: Maintains chronological 
  ordering with :math:`O(log n)` insertion/deletion
* **Hash-based Indices (``_record_key_index``, ``_action_id_index``)**: Provide :math:`O(1)` 
  constant time operation for accessing.
* **Record Key Insertion**: :math:`O(1)` constant time operation for unique key insertion.

Where **n** represents the total number of active DENM records in the system.

Collision Message Processing Performance
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

**Scenario**: Processing ``StationCollisionArrayV1`` from ``step_crash_prediction``

**Algorithm Complexity Analysis:**

For processing a collision array containing :math:`k+1` vehicles which generates :math:`k` 
DENM records:

1. **Station Ordering**: :math:`O(k*log(k))` - Comparison sort of the collision array stations
2. **Record Key Generation**: :math:`O(k)` - Linear iteration through the ordered stations
3. **Existing Record Lookup**: :math:`O(k)` - Hash table lookup for each collision record
4. **New Record Insertion (updating or creation)**: 
   
   * Sorted list insertion (and removal, when updating): :math:`O(k*log(n))` - Each record requires binary search positioning
   * Hash index updates: :math:`O(k)` - Constant time insertion per index
   
5. **DENM Message Creation**: :math:`O(k)` - Linear with number of collision records
6. **Redis Stream Publication**: :math:`O(k)` - Linear network operations

**Overall Complexity**: :math:`O(k*log(k) + k*log(n))`

**Performance Implications**:

* **Best Case**: All collision records already exist: still :math:`O(k*log(k) + k*log(n))`, since
  each existing record is removed from and re-inserted into the sorted list
* **Worst Case**: All collision records are new: :math:`O(k*log(k) + k*log(n))` for full processing
* **Space Complexity**: :math:`O(k)` additional per message, plus :math:`O(n)` for maintaining active DENM records

**Scalability Considerations:**

* With k=10 collision records and :math:`n=10000` active DENMs in the system: ~170 operations
* System performance degrades logarithmically with active record count
* Memory usage scales linearly with concurrent collision scenarios

DENM Negation Processing Performance
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

**Scenario**: Processing DENM negation messages from ``step_client``

**Algorithm Complexity Analysis:**

For processing a single DENM negation:

1. **Action ID Lookup**: :math:`O(1)` - Hash table lookup in ``_action_id_index``
2. **Record Removal from Sorted List**: :math:`O(log(n))` - Binary search and removal
3. **Hash Index Cleanup**: :math:`O(1)` - Constant time removal from both indices
4. **Memory Deallocation**: :math:`O(1)` - Single record cleanup

**Overall Complexity**: :math:`O(log(n))`

**Performance Implications:**

* **Consistent Performance**: Negation processing time grows logarithmically with total records
* **Efficient Cleanup**: Fast removal enables real-time termination handling
* **Memory Recovery**: Immediate memory release prevents accumulation

Periodic Cleanup Performance
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

**Scenario**: Automatic expiration cleanup in ``periodical_cleanup()``

**Algorithm Complexity Analysis:**

#. **Expired Range Lookup**: :math:`O(log(n))` - ``irange`` search of the threshold, paid even when
   nothing expired
#. **Batch Record Removal**: :math:`O(e*log(n))` where e is the number of expired records
#. **Cancellation Message Generation**: :math:`O(e)` - Linear with expired count
#. **Redis Stream Publication**: :math:`O(e)` - Linear network operations

**Overall Complexity**: :math:`O(log(n) + e*log(n))`

**Performance Optimization:**

* **Early Termination**: Sorted list enables early exit when unexpired records are encountered
* **Fixed Scheduling**: The cleanup runs every ``denmCheckLastUpdateInterval`` seconds; each
  cancellation is published with its own XADD

**Memory Management Strategies:**

* **Automatic Expiration**: Prevents unbounded memory growth
* **Efficient Data Structures**: Minimal overhead through ``__slots__`` usage
* **Connection Pooling**: Controlled resource allocation for Redis connections

Bottleneck Analysis
^^^^^^^^^^^^^^^^^^^
The STEP Producer architecture is designed to handle high-frequency collision detection scenarios, 
but certain bottlenecks may arise. The following analysis identifies 
potential bottlenecks and mitigation strategies:

* **Primary Bottleneck**: Redis stream publication latency (network I/O bound)
* **Secondary Bottleneck**: Sorted list maintenance for large record sets
* **Mitigation Strategy**: Asynchronous processing and connection pooling
