Architecture

This document describes the architecture of the STEP Producer, a Python package for managing Decentralized Environmental Notification (DEN) service.

Overview

The STEP Producer is a critical component of the STEP (Safer Transport for Europe Platform) ecosystem, specifically designed for processing and managing Decentralized Environmental Notification Messages (DENM) within Intelligent Transportation Systems (ITS) environments. This Redis-based microservice implements the DEN (Decentralized Environmental Notification) service for collision prediction and environmental hazard notifications.

Library

The STEP Producer leverages a carefully selected set of libraries and frameworks to implement robust, high-performance ITS message processing capabilities. The library architecture follows a layered approach with core Python libraries, specialized third-party packages, and custom STEP ecosystem components.

Core Dependencies

Pydantic

Advanced data validation and settings management library that provides the foundation for configuration management throughout the STEP Producer. Pydantic enables:

  • Type Safety: Strong typing with automatic validation for all configuration parameters

  • Schema Generation: Automated JSON schema creation for configuration documentation

  • Serialization: Robust JSON serialization/deserialization for configuration persistence

  • Model Validation: Runtime validation of configuration data with detailed error reporting

Used extensively in StepProducerConfig and related configuration classes to ensure type-safe, validated configuration management across all Producer components.

SortedContainers

High-performance pure-Python sorted container implementation that provides the data structure foundation for efficient DENM record management. Key capabilities include:

  • Sorted Lists: O(log n) insertion and deletion with maintained ordering

  • Memory Efficiency: Optimized memory layout for large collections

  • Performance: Fast search, insert, and delete operations for time-ordered records

Critical for the DenServiceDataManager where chronologically ordered DENM records require efficient insertion, removal, and time-based queries for expiration management.

step_cloud_schemas

Custom STEP ecosystem library that defines standardized ITS message schemas and data structures. This library provides:

  • DENM Schemas: Complete DenmDataV1 message structures compliant with ETSI standards

  • Cloud Events: Standardized cloud event wrappers for ITS message distribution

  • ITS Primitives: Core ITS data types including timestamps, positions, and identifiers

  • Collision Data: StationCollisionArrayV1 structures for collision prediction integration

Essential for maintaining compatibility across the STEP ecosystem and ensuring standard-compliant message generation and processing.

step_redis

STEP-specific Redis integration library that provides the messaging and stream processing foundation as a black box interface. Core functionality includes:

  • Connection Pooling: Efficient Redis connection management with automatic reconnection

  • Stream Processing: High-level abstractions for Redis streams with consumer group support

  • Message Serialization: Automatic conversion between Python objects and Redis stream data

  • Error Handling: Robust error handling and recovery mechanisms for Redis operations

Provides the base classes StepRedisPool and StepRedisStream, along with specialized implementations like StepProducerRedisStream and StepClientRedisStream for different stream operations. The STEP Producer uses these classes directly without custom extensions.

python-dotenv (through step_redis)

Loads Redis connection credentials from the .env file of the current working directory (or its nearest parent) into the process environment at startup, without overriding a variable already set, so secrets are kept out of the (persisted) JSON configuration document. Used by step_redis RedisCredential.from_env(), called by the StepProducerApp constructor (see Environment Variables).

Architecture Integration

The library selection supports the STEP Producer’s architectural requirements:

  • High Performance: SortedContainers and asyncio enable efficient handling of high-frequency collision detection scenarios

  • Type Safety: Pydantic provides compile-time and runtime type validation throughout the system

  • Standards Compliance: step_cloud_schemas ensures ETSI ITS standard compliance for all messages

  • Scalability: step_redis abstractions support horizontal scaling through Redis stream distribution

  • Maintainability: Comprehensive development tooling ensures code quality and documentation standards

Components

The architecture follows a modular design pattern that separates concerns between DEN service management, communication, Redis integration, and configuration management. This enables flexibility and maintainability in the system design.

Main Components:

  1. DenServiceManager: Orchestrator for DEN service lifecycle, including message creation, processing, and termination

  2. DenServiceDataManager: Data management for DENM records with multi-index storage

  3. OrderedListRecord/RecordKey: Time-ordered record management with unique record keys

  4. Redis Integration (step_redis): Redis connection pooling and stream processing via StepRedisPool and StepRedisStream base classes

  5. StepProducerConfig: Configuration management for the Producer

  6. StepLogger (from step_cloud_schemas): Logging utilities used by the STEP Producer

  7. StepException: Custom exceptions for error handling

  8. Main Application (__main__): Command-line interface; runs StepProducerApp through AppRunner (from step_cloud_schemas)

  9. StepProducerApp: Workload of the program: environment-based Redis credentials, asynchronous task orchestration and automatic reconnection

  10. Application Runtime (from step_cloud_schemas): AppRunner, which runs the workload with a cooperative shutdown, and the abstract classes AbstractApp and ReconnectingApp, which StepProducerApp derives from

DenServiceManager

The DenServiceManager class serves as the primary orchestrator for DEN (Decentralized Environmental Notification) services within the STEP Producer architecture. This component manages the complete lifecycle of collision risk notifications, from initial detection through message termination and cleanup.

Core Responsibilities:

  1. Collision Event Processing: Receives and processes StationCollisionArrayV1 objects, converting collision detection data into structured DENM messages for distribution throughout the ITS network.

  2. Message Lifecycle Management: Orchestrates the DENM message lifecycle, including creation, update handling, and cancellation of expired notifications; the messages it returns are published by StepProducerApp.

  3. Termination Handling: Processes incoming DENM records with negation termination flags, ensuring proper cleanup of cancelled collision notifications.

  4. Automatic Cleanup: periodical_cleanup() removes the expired DENM records and returns a cancellation copy of each one still within its validity, which StepProducerApp publishes.

DenServiceManager is synchronous and has no Redis access: all Redis reading and publishing is done by StepProducerApp.

Key Methods:

  • process_station_collisions_received(): Main entry point for processing collision arrays, delegating to the data manager for record creation and returning list of DENM messages

  • process_denm_record_received(): Handles incoming DENM records, specifically processing termination requests with negation flags

  • periodical_cleanup(): Removes the records whose reference time is older than denm_last_update_max_delay_ms and returns a cancellation message for each removed record still within its validityDuration

  • _denm_create_cancellation(): Creates cancellation DENM messages by copying original message data while setting the termination flag

Architecture Integration:

The DenServiceManager is a synchronous facade over the DenServiceDataManager: it turns the received messages into data operations and returns the DENM messages to publish. StepProducerApp creates a single instance for the whole run (kept across Redis reconnects) and shares it between its receive and cleanup tasks; the methods never await, so the two tasks never interleave inside it.

Configuration Parameters:

  • station_id: Unique identifier for the originating ITS station

  • time_after_collision_sec: Duration in seconds to continue broadcasting a DENM after the estimated collision time (added to the time to collision to form the validityDuration)

  • denm_last_update_max_delay_ms: Maximum age in milliseconds of a record’s reference time before the record is treated as expired by the cleanup

DenServiceDataManager

The DenServiceDataManager class provides comprehensive data management capabilities for DENM records, implementing efficient storage, indexing, and retrieval mechanisms optimized for high-frequency collision detection scenarios. This component serves as the persistent storage layer for the DEN service, maintaining multiple data structures for optimal performance.

Internal Architecture:

The data management layer consists of four primary data structures:

  1. DenmRecordInfo: A frozen dataclass that encapsulates DENM data (DenmDataV1) and its record key; the reference time (ItsTime) and the monotonic creation timestamp are derived on initialization (from the DENM’s management container and time.monotonic()) and cannot be passed to the constructor.

  2. OrderedListRecord: A time-ordered record container with comparison operators for chronological sorting. Pairs a reference time with a unique record key for efficient sorted list operations.

  3. RecordKey: A frozen dataclass holding unique identifiers for DENM records, containing reference and involved actor IDs (station ID and object ID pairs).

  4. DenServiceDataManager: The core service class that manages collections using multiple specialized indices for optimal performance across different access patterns.

Data Storage Strategy:

The data manager employs a multi-index architecture for optimal performance:

  • _denm_sorted_records: A SortedList[OrderedListRecord] maintaining chronological ordering for efficient time-based operations O(log n). Each record contains reference time and record key.

  • _record_key_index: Hash-based dictionary dict[RecordKey, DenmRecordInfo] providing O(1) lookup by unique record keys composed of reference and involved actor identifiers

  • _action_id_index: Hash-based dictionary dict[ActionId, DenmRecordInfo] enabling fast retrieval by action ID (originating station ID and sequence number)

Key Functionality:

  1. Collision Array Processing: The insert_station_collision_array() method converts a station collision array into DENM records, one for the reference station (the first after ordering) paired with each other station (k-1 records for k stations); the stations are ordered by station ID and object ID. A pair repeated in the same array is built once, the last occurrence winning. The records are first all built and then committed together: if any of them fails, no record of the array is created or updated.

  2. DENM Content: The validity duration is the time to collision (rounded up, never negative) plus time_after_collision_sec. The situation’s event type is the collision risk cause code, with the sub cause code selected by the type of the involved station (pedestrian, cyclist, vulnerable road user for mopeds, motorcycles, light VRU vehicles and animals, motor vehicle for the other vehicle types, unavailable otherwise). A station type confidence of 0 becomes an unavailable object type confidence.

  3. Multi-Index Management: Maintains synchronized indices across all data structures, ensuring consistency during record creation, updates, and deletions while providing optimal access patterns for different query types.

  4. Automatic Expiration: The get_denm_records_clean_reference_expired() method identifies expired records based on configurable delay thresholds, supporting automatic cleanup operations.

  5. Sequence Number Generation: Generates the sequence numbers of the action IDs; after ActionId.SEQUENCE_NUMBER_MAX the counter wraps around and skips the sequence numbers still held by a tracked record, so a live ActionId is never reissued; OverflowError is raised when every sequence number is held by a tracked record. An existing record keeps its ActionId on update.

Record Management:

Each DENM record is uniquely identified by a RecordKey containing:

  • reference_actor_id: ActorId (station_id, object_id) of the reference vehicle

  • involved_actor_id: ActorId (station_id, object_id) of the involved vehicle

This structure enables precise tracking of collision relationships between specific ITS entities. The system supports both new record creation and existing record updates, reusing action IDs where appropriate to maintain message continuity.

Performance Optimizations:

  • Utilizes __slots__ for memory efficiency in DenServiceDataManager and OrderedListRecord classes

  • Uses frozen dataclasses for DenmRecordInfo and RecordKey for immutability and performance

  • Implements SortedList for maintaining chronological order without manual sorting overhead

  • Caches hash values in OrderedListRecord for efficient dictionary/set operations

  • Provides multiple access patterns (chronological, key-based, action ID-based) for different operational requirements

  • Includes comprehensive logging with configurable detail levels for operational monitoring and debugging

Expiration Management:

get_denm_records_clean_reference_expired() removes the records whose reference time is older than now - denm_last_update_max_delay_ms and returns the DENM of those still within their own validityDuration (by monotonic age), for which a cancellation is published; the removed records no longer valid produce no cancellation. The cleanup runs every denmCheckLastUpdateInterval seconds.

Thread Safety:

No locking is used around the indexes. All the methods are synchronous (they never await), so one instance can be shared by several asyncio tasks of the same event loop, as StepProducerApp does through its DenServiceManager; it must not be shared between threads.

OrderedListRecord Module

The ordered_list_record module provides lightweight, memory-efficient data structures for time-ordered operations in DENM management. This module is designed specifically for high-frequency, time-ordered operations (insert, search, delete) in sorted lists and hash tables.

Core Components:

  1. RecordKey: A frozen dataclass that holds unique identifiers for DENM records:

    • reference_actor_id: ActorId containing station_id and object_id of reference vehicle

    • involved_actor_id: ActorId containing station_id and object_id of involved vehicle

    Provides immutable record identification with automatic hashing for efficient dictionary operations.

  2. OrderedListRecord: A time-ordered record container implementing rich comparison operators:

    • Encapsulates reference time (ItsTime) and record key (RecordKey)

    • Implements __lt__, __le__, __gt__, __ge__ for chronological ordering

    • Implements __eq__ and __hash__ based on the (reference time, record key) pair, consistently with the ordering

    • Uses __slots__ with hash caching for minimal memory footprint

    • Decorated with @total_ordering for complete comparison support

Design Features:

  • Memory Efficiency: Uses __slots__ to minimize memory overhead per record

  • Hash Caching: Caches hash values during initialization for fast dictionary/set operations

  • Immutable Keys: Frozen dataclasses ensure record keys cannot be modified after creation

  • Comparison Semantics:

    • Ordering based on reference time (chronological), ties broken by record key

    • Equality based on reference time and record key

  • Type Safety: Leverages dataclass validation and type hints for robust implementation

Integration with DenServiceDataManager:

The OrderedListRecord instances are stored in the _denm_sorted_records SortedList, enabling:

  • O(log n) insertion maintaining chronological order

  • O(log n) deletion when records expire

  • O(1) equality checks for duplicate detection

  • Fast iteration over time-ordered records for cleanup operations

This separation of concerns allows the DenServiceDataManager to focus on business logic while leveraging optimized data structures for time-ordered operations.

Application Runtime (step_cloud_schemas)

Note

AppRunner, AbstractApp and ReconnectingApp are not part of the step_producer package: they are imported from the external step_cloud_schemas dependency, shared by the STEP programs. Only their public interface, the part used by the STEP Producer, is described here.

The three classes split a long-running program in two parts: the process-wide plumbing (event loop, signal handlers, exception hooks), owned by AppRunner, and the workload, supplied by the program as an AbstractApp subclass. R is the program’s result type: for the STEP Producer, ExitCode.

Class

Role

AbstractApp[R]

Abstract base class of a workload run by AppRunner. It declares the two methods AppRunner needs and holds no state (empty __slots__, so a subclass declares its own).

ReconnectingApp[R]

Abstract AbstractApp subclass that implements work as a reconnect loop around a connection cycle, implemented by the program.

AppRunner[R]

Singleton that runs an AbstractApp on a new event loop until it ends or a shutdown signal stops it.

The class diagram below shows the public interface of the three classes and how StepProducerApp plugs into them:

AbstractApp: public interface

  • async work() -> R (abstract): The workload, called once per run as a task of the AppRunner TaskGroup; it returns the result when it ends on its own. On a shutdown signal it is cancelled at the await it is suspended on, so it has to be cancellation-safe.

  • on_shutdown(stop_signal: Signals) -> R (abstract): Called by AppRunner after a shutdown signal stopped work, once every task has unwound (the resources held by work are already released); it runs on the event loop thread and cannot await. Its value is the result of the run.

ReconnectingApp: public interface

  • ReconnectingApp(logger, reconnect_interval): logger is used for the start, error and retry messages, reconnect_interval is the number of seconds to wait before the next cycle.

  • async cycle() -> None (abstract): Opens the connections and runs the tasks until one of them fails; returns only if every task ends normally, and then the next cycle starts at once. Like work, it has to be cancellation-safe.

  • fatal_result() -> R (abstract): The result returned by work after an error that a reconnect cannot fix.

  • async work() -> R: Logs Program started, then runs cycle in a loop. When cycle raises:

    • while a shutdown cancellation is in progress, the error is logged at INFO level and CancelledError is restored, so the shutdown goes on without an ERROR traceback;

    • otherwise the error is logged with its traceback, and if it, or any error nested in an ExceptionGroup (as raised by a TaskGroup), is one of the subclass’s fatal error types, work returns fatal_result();

    • otherwise work waits reconnect_interval seconds and runs cycle again.

    It never returns otherwise: the loop ends only when AppRunner cancels it.

The fatal error types are a class attribute that each subclass sets (StepProducerApp: StepRedisFatalError); with none set, every error is retried.

AppRunner: public interface

  • AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None):

    • logger_param: Logger used by the default exception and unraisable handlers.

    • loop_factory: Factory of the event loop created by every run, forwarded to asyncio.Runner; None uses the asyncio default loop. The STEP Producer passes asyncio.SelectorEventLoop on Windows, as the other STEP programs do.

    • exception_handler: Event loop exception handler; None logs the exception on the logger.

    • unraisable_handler: Installed as sys.unraisablehook; None logs the exception on the logger.

    The constructor installs the process-wide hooks (signal handlers, sys.unraisablehook): it is called from the main thread as early as possible, which is why main() builds it before parsing the arguments, so that a signal received before run is still handled. Being a singleton, only the first construction takes effect; the arguments of later calls are ignored.

  • logger (property): The logger given to the constructor.

  • run(app: AbstractApp[R]) -> R: Opens an asyncio.Runner, installs the exception handler and the shutdown handlers (SIGINT/SIGTERM on POSIX, CTRL_C/CTRL_BREAK on Windows), then runs app.work() next to a shutdown watcher in a TaskGroup. It returns the value of app.work() when the workload ends on its own, or the value of app.on_shutdown(stop_signal) when a shutdown signal stops it. Any other exception raised by work propagates wrapped in an ExceptionGroup, which main() logs and maps to ExitCode.ERROR.

A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only sets an event, the watcher task turns it into an exception, and the TaskGroup cancels work at the await it is suspended on.

How the STEP Producer uses them:

StepProducerApp

StepProducerApp (module step_producer_app) is the ReconnectingApp subclass (step_cloud_schemas, see Application Runtime (step_cloud_schemas)) run by AppRunner: the reconnecting DEN service on top of the Redis streams. It implements one connection cycle (cycle()) and the result of a fatal error (fatal_result()), while the reconnect loop is the inherited work(). It also defines the ExitCode enumeration.

Key features of StepProducerApp include:

  1. Environment-Based Credentials: the constructor calls step_redis RedisCredential.from_env() once: it loads the .env file of the current working directory (or an ancestor of it) and reads REDIS_URL, REDIS_PORT, REDIS_USERNAME, and REDIS_PASSWORD from the environment (see Environment Variables); REDIS_URL and REDIS_PORT are required, the username and password are optional (an empty value counts as unset). Reading them at construction (not in cycle()) makes a missing variable end the program instead of being retried forever.

  2. Asynchronous Task Orchestration: the constructor creates a single DenServiceManager; each cycle() opens a StepRedisPool (parameters from StepRedisPoolParams.from_connection(), at most _REDIS_MAX_CONNECTIONS = 2 connections) and the client output stream, then uses asyncio.TaskGroup to run three concurrent tasks - _stream_receive_run() (stream reception and dispatch), _periodical_cleanup_run() (expired DENM cleanup) and _redis_health_check_run() (Redis connection health check). The receive and cleanup tasks publish on the same client output stream.

  3. Message Dispatch: _producer_message_dispatch() routes a ProducerCloudEventsDenmDataV1 to _denm_message_handler() and a ProducerCloudEventsStationCollisionArrayV1 to _station_collision_array_message_handler(), whose DENMs are published as a batch by _denm_messages_publish(); any other type is skipped with a warning. Each handler, the batch publish and each cleanup are timed by a LoggingTimer at INFO level.

  4. Stream Parameters: _input_stream_params() builds the input stream parameters (stream, consumer group, wait timeout, the instance name as consumer, TTL from StepRedisStreamParams.ttl_seconds_from_wait_timeout()), also used by the health check; _client_stream_params() builds the client output stream parameters (stream and maxLength).

  5. Per-Message Error Isolation: A received message whose processing raises ValueError (pydantic ValidationError included) is logged and dropped; the loop goes on and the tracked DENM records are kept. A collision array is applied all or nothing.

  6. Automatic Reconnection: On any other error, the inherited work() waits config.reconnectInterval seconds and runs cycle() again, keeping the same DenServiceManager (tracked records and ActionId sequence survive the reconnect).

  7. Permanent Errors: An error that a reconnect cannot fix (_FATAL_ERRORS: StepRedisFatalError from step_redis, i.e. rejected credentials, ACL denial, missing SSL file, untrusted certificate) ends the run with fatal_result() (ExitCode.ERROR) instead of retrying forever.

  8. Graceful Shutdown: Delegated to AppRunner: on SIGINT/SIGTERM (POSIX) or CTRL_C/CTRL_BREAK (Windows) it cancels work(), the async with blocks release the Redis pool and streams, and on_shutdown() logs the signal and returns ExitCode.ABORTED. A failure raised while the cancellation unwinds is turned back into CancelledError instead of triggering a reconnect, and is logged at INFO level without an ERROR traceback.

  9. Exit Code Management: Defines standard exit codes through the ExitCode enum:

    • OK (0): Successful execution

    • USAGE (1): Invalid command-line usage

    • ERROR (2): General execution error

    • ABORTED (3): Process interrupted by signal

Performance Considerations

The STEP Producer architecture is designed for high-performance processing of ITS messages with careful consideration of algorithmic complexity and data structure selection. The following analysis provides Big O complexity calculations for the two primary message processing scenarios.

Data Structure Performance Characteristics

The DenServiceDataManager employs a multi-index architecture optimized for different access patterns:

  • Sorted List (``_denm_sorted_records``): Maintains chronological ordering with \(O(log n)\) insertion/deletion

  • Hash-based Indices (``_record_key_index``, ``_action_id_index``): Provide \(O(1)\) constant time operation for accessing.

  • Record Key Insertion: \(O(1)\) constant time operation for unique key insertion.

Where n represents the total number of active DENM records in the system.

Collision Message Processing Performance

Scenario: Processing StationCollisionArrayV1 from step_crash_prediction

Algorithm Complexity Analysis:

For processing a collision array containing \(k+1\) vehicles which generates \(k\) DENM records:

  1. Station Ordering: \(O(k*log(k))\) - Comparison sort of the collision array stations

  2. Record Key Generation: \(O(k)\) - Linear iteration through the ordered stations

  3. Existing Record Lookup: \(O(k)\) - Hash table lookup for each collision record

  4. New Record Insertion (updating or creation):

    • Sorted list insertion (and removal, when updating): \(O(k*log(n))\) - Each record requires binary search positioning

    • Hash index updates: \(O(k)\) - Constant time insertion per index

  5. DENM Message Creation: \(O(k)\) - Linear with number of collision records

  6. Redis Stream Publication: \(O(k)\) - Linear network operations

Overall Complexity: \(O(k*log(k) + k*log(n))\)

Performance Implications:

  • Best Case: All collision records already exist: still \(O(k*log(k) + k*log(n))\), since each existing record is removed from and re-inserted into the sorted list

  • Worst Case: All collision records are new: \(O(k*log(k) + k*log(n))\) for full processing

  • Space Complexity: \(O(k)\) additional per message, plus \(O(n)\) for maintaining active DENM records

Scalability Considerations:

  • With k=10 collision records and \(n=10000\) active DENMs in the system: ~170 operations

  • System performance degrades logarithmically with active record count

  • Memory usage scales linearly with concurrent collision scenarios

DENM Negation Processing Performance

Scenario: Processing DENM negation messages from step_client

Algorithm Complexity Analysis:

For processing a single DENM negation:

  1. Action ID Lookup: \(O(1)\) - Hash table lookup in _action_id_index

  2. Record Removal from Sorted List: \(O(log(n))\) - Binary search and removal

  3. Hash Index Cleanup: \(O(1)\) - Constant time removal from both indices

  4. Memory Deallocation: \(O(1)\) - Single record cleanup

Overall Complexity: \(O(log(n))\)

Performance Implications:

  • Consistent Performance: Negation processing time grows logarithmically with total records

  • Efficient Cleanup: Fast removal enables real-time termination handling

  • Memory Recovery: Immediate memory release prevents accumulation

Periodic Cleanup Performance

Scenario: Automatic expiration cleanup in periodical_cleanup()

Algorithm Complexity Analysis:

  1. Expired Range Lookup: \(O(log(n))\) - irange search of the threshold, paid even when nothing expired

  2. Batch Record Removal: \(O(e*log(n))\) where e is the number of expired records

  3. Cancellation Message Generation: \(O(e)\) - Linear with expired count

  4. Redis Stream Publication: \(O(e)\) - Linear network operations

Overall Complexity: \(O(log(n) + e*log(n))\)

Performance Optimization:

  • Early Termination: Sorted list enables early exit when unexpired records are encountered

  • Fixed Scheduling: The cleanup runs every denmCheckLastUpdateInterval seconds; each cancellation is published with its own XADD

Memory Management Strategies:

  • Automatic Expiration: Prevents unbounded memory growth

  • Efficient Data Structures: Minimal overhead through __slots__ usage

  • Connection Pooling: Controlled resource allocation for Redis connections

Bottleneck Analysis

The STEP Producer architecture is designed to handle high-frequency collision detection scenarios, but certain bottlenecks may arise. The following analysis identifies potential bottlenecks and mitigation strategies:

  • Primary Bottleneck: Redis stream publication latency (network I/O bound)

  • Secondary Bottleneck: Sorted list maintenance for large record sets

  • Mitigation Strategy: Asynchronous processing and connection pooling
