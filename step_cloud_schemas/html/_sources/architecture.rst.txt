============
Architecture
============

The STEP Cloud Schemas project provides a standardized way to define and validate 
data structures used in cloud-based STEP (Safer Transport for Europe Platform)
implementations.
The system is composed of three main components:

    #.  **STEP Broker**: The broker is responsible for routing messages to the clients subscribed.
    #.  **STEP Elaboration System**: The system is responsible for adapting the messages to be used 
        by **Machine Learning** subsystem and for sending any warnings.
    #.  **Machine Learning**: The subsystem is responsible for processing the messages received and for finding 
        any possible future crashes.

-------
Library
-------

The library uses the following external libraries:

    * **Pydantic**
    * **Pyproj**

----------------
Pydantic Library
----------------

Pydantic is a data validation library for Python, leveraging Python type annotations.
It provides a way to define data models with type hints and validate data against these models.

Key features of Pydantic include:

    * **Data validation**: Automatically validates data against the defined types.
    * **Data parsing**: Parses input data into the specified types.
    * **Serialization**: Convert models to and from JSON and other formats.

Example usage:

.. code-block:: python

    from datetime import datetime

    from pydantic import BaseModel

    class User(BaseModel):
        id: int
        name: str
        signup_ts: datetime | None = None
        friends: list[int] = []

    user = User(id=123, name="John Doe", friends=[1, 2, 3])
    print(user.model_dump())

--------------
Pyproj Library
--------------

:xref:`Pyproj` is a Python interface used here to solve geodesic
problems on the WGS84 ellipsoid via its ``Geod`` class. Unlike the great-circle (spherical)
Haversine formula previously used, ``Geod`` accounts for the Earth's ellipsoidal shape,
giving more accurate distances and bearings. It also solves the distance and forward
azimuth (bearing) together in a single call, whether the inputs are scalars or numpy arrays.

Key features of Pyproj's ``Geod`` used by this project include:

    * **Inverse geodesic problem**: Given two points, compute the distance and forward
      azimuth between them (``Geod.inv``).
    * **Forward geodesic problem**: Given a starting point, a bearing, and a distance,
      compute the resulting point (``Geod.fwd``).
    * **Vectorized calculations**: Both ``inv`` and ``fwd`` accept numpy arrays,
      allowing distance/bearing calculations over millions of points in a single call.

Example usage:

.. code-block:: python

    from pyproj import Geod

    geod = Geod(ellps="WGS84")

    # Coordinates of two points (longitude, latitude)
    point1 = (21.0122287, 52.2296756)
    point2 = (12.5113300, 41.8919300)

    # Solve the inverse geodesic problem: forward azimuth, back azimuth, distance (meters)
    azimuth_deg, back_azimuth_deg, distance_m = geod.inv(
        point1[0], point1[1], point2[0], point2[1]
    )
    print(f"Distance: {distance_m / 1000.0} km")

-----------
Flow Format
-----------

Each flow is encapsulated in a :xref:`Cloud Events JSON Format` message.
The general structure of the message is:

#. **id**: Unique identifies the event.
#. **source**: The process that produced the event.
#. **specversion**: The version of the :xref:`Cloud Events` specification which the event uses.
#. **datacontenttype**: The content type of data value.
#. **time**: Timestamp of when the occurrence happened.
#. **type**: Type of the message.
#. **dataschema**: Identifies the schema that data adheres to.
#. **data**: The data of the message.

An example is the following:

.. code-block:: json

    {
        "id": "56c5ecec-00ef-4a27-a5a0-bcb85a7378c1",
        "source": "instance_1",
        "specversion": "1.0",
        "datacontenttype": "application/json",
        "time": "2018-04-05T17:31:00.000Z",
        "type": "CAM",
        "dataschema": "cam_data_v1_schema",
        "data": "message data"
    }

----------------
Flow Description
----------------

In the previous diagram, the flows are numerated. The description of each flow is:

    1.  **ANS.1 ITS from STEP Broker to Client**: The messages in the flow are:
        
            * CAM 
            * DENM
            * CPM

        The messages received are based on the geo-hashing in the MQTT topic.
    2.  **ANS.1 ITS from STEP Client to STEP Broker**: The messages in the flow are:
        
            * DENM

        The message sent contains a forecasting of a Crash. The message contains the 
        information of only 2 stations involved. So if the crash involves more than 2 stations,
        the messages generated will be the number of stations decreased by one. 
    3.  **CAM,CPM from STEP Client to Adapter**: The messages received by STEP Client
        are encoded in CloudEvent compatible format. The data field contains:
        
            * CAM
            * CPM

        The message is validated by JSON schema :ref:`target_cloud_events_step_adapter_schema`.
    4.  **Position points array from adapter to trajectory**: STEP Adapter executes the
        following tasks:
            
            * Collect the messages per station id or perceptive object id
            * Filter duplicate message (**duplication filter**)
            * Sequence the position point per station id
            * Interpolate data to recover lost point a constant rate (**fill in the gap**)
            * Merge different source flow of the same actor (**idempotence**)
            * Down or up sampling to have a constant rate (**sampling normalize**)

        The message is validated by JSON schema :ref:`target_cloud_events_step_crash_prediction_schema`.
    5.  **Trajectory forecasted data from trajectory to monitoring**: The message contains the
        position point of the station involved in the event. The message is validated by JSON schema
        :ref:`target_cloud_events_step_monitoring_schema`.
    6.  **Event forecasted from avoidance collision to Producer**: The message contains the
        position point of the station involved in the event. The message is validated by JSON schema
        :ref:`target_cloud_events_step_producer_schema`.
    7.  **DENM from Producer to client**: The message DENM contains the pre-crash container. The message
        is validated by JSON schema :ref:`target_cloud_events_step_client_schema`.
    8.  **DENM from client to Producer**: The message DENM contains the environment notification generated
        by other stations. The message is validated by JSON schema :ref:`target_cloud_events_step_producer_schema`.

-------------------
AppRunner Structure
-------------------

:class:`~step_cloud_schemas.runtime.app_runner.AppRunner` is the entry-point helper
shared by the long-running STEP programs: it runs an asyncio workload and stops it
cooperatively on a shutdown signal. The usage is described in :doc:`app_runner<app_runner>`;
this section describes how it is built.

The structure is made of the following elements:

    #.  **AppRunner**: Singleton, generic in the result type ``R`` of the application.
        The constructor stores the settings and installs the process-wide hooks
        (signal handlers and ``sys.unraisablehook``). The method ``run`` opens an
        ``asyncio.Runner``, installs the loop exception handler, creates the
        ``stop_event`` and runs ``_main_async``.
    #.  **SingletonMeta**: Metaclass of ``AppRunner`` and ``WindowsOsShutdownState``.
        The hooks are process-wide, so a single instance of each class exists.
    #.  **WindowsOsShutdownState**: Singleton holding the loop and the ``stop_event``
        of the current run. It is used only on Windows, where ``asyncio`` has no
        ``loop.add_signal_handler``: the raw ``SIGBREAK`` handler calls
        ``request_shutdown``, which schedules ``stop_event.set()`` on the loop with
        ``loop.call_soon_threadsafe``.
    #.  **_ShutdownRequestedError**: Internal marker exception. It is raised by the
        watcher task and caught by ``_main_async``; it never leaves the module.
    #.  **Application**: The class of the program using ``AppRunner`` (e.g. ``MessageSaveApp``
        of ``step_message_save``). It supplies the workload ``work`` and the callback
        ``on_shutdown``, both returning ``R``.

The following class diagram shows the structure:

.. container:: scrollable-diagram

A run goes through the following steps:

    1.  ``run`` opens the ``asyncio.Runner``, creates the ``stop_event`` and publishes
        it to the signal handlers before the loop runs: with ``loop.add_signal_handler``
        for ``SIGINT``/``SIGTERM`` on POSIX, with ``WindowsOsShutdownState.publish`` on
        Windows.
    2.  ``_main_async`` creates two sibling tasks in a ``TaskGroup``: the workload
        ``work()`` and the watcher ``_wait_for_shutdown``, which awaits the ``stop_event``.
    3.  **Normal end**: when ``work`` ends, a done callback cancels the watcher, the
        ``TaskGroup`` closes and the result of ``work`` is returned.
    4.  **Shutdown**: a signal records the stop signal and sets the ``stop_event``. The
        watcher raises ``_ShutdownRequestedError``, the ``TaskGroup`` cancels ``work``
        wherever it is and, once every task has unwound, ``on_shutdown`` is called with
        the stop signal and its result is returned.
    5.  ``_main_async`` clears ``WindowsOsShutdownState`` (Windows) and ``run`` registers
        the signal handlers again, once with the loop still open and once after it is
        closed, because ``asyncio.Runner`` replaces them while the loop is open and
        resets them to the defaults when it closes.
