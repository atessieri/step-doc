============================================
Cubic Spline Interpolation for Trajectories
============================================

Overview
========

The cubic spline interpolation in ``step_cloud_schemas.gnss.gap_filler`` turns sparse trajectory
data into continuous, time-aligned position sequences for the resampled lists
(``GapFiller.resample()``), in latitude, longitude and altitude. It uses SciPy's ``CubicSpline``
class. The stream gaps (``GapFiller.fill()``) use no cubic spline: a Hermite segment for latitude
and longitude and a straight line for the altitude (see :doc:`spline_hermite`).

Mathematical Foundation
=======================

Cubic Spline Theory
-------------------

A cubic spline is a piecewise polynomial function that interpolates a set of data points with continuous
first and second derivatives. For a set of data points :math:`(x_0, y_0), (x_1, y_1), ..., (x_n, y_n)`,
the cubic spline :math:`S(x)` consists of cubic polynomials :math:`S_i(x)` for each interval :math:`[x_i, x_{i+1}]`:

.. math::

   S_i(x) = a_i + b_i(x - x_i) + c_i(x - x_i)^2 + d_i(x - x_i)^3

where the coefficients :math:`a_i, b_i, c_i, d_i` are determined by the constraints:

1. **Interpolation constraint**: :math:`S_i(x_i) = y_i` and :math:`S_i(x_{i+1}) = y_{i+1}`
2. **Continuity constraint**: :math:`S_i(x_{i+1}) = S_{i+1}(x_{i+1})`
3. **First derivative continuity**: :math:`S'_i(x_{i+1}) = S'_{i+1}(x_{i+1})`
4. **Second derivative continuity**: :math:`S''_i(x_{i+1}) = S''_{i+1}(x_{i+1})`

Multi-dimensional Interpolation
-------------------------------

Latitude, longitude and altitude share the same abscissa :math:`t` (time in milliseconds since
epoch), so they are interpolated by one **vector-valued** cubic spline: SciPy solves a single
tridiagonal system for all the columns instead of building independent splines.

- **Every point has an altitude**: one spline over (latitude, longitude, altitude).
- **Some points lack it**: one spline over (latitude, longitude); the altitude is interpolated by a
  separate spline (``GapFiller._interpolate_altitudes()``) over the **trailing run** of
  consecutive points with altitude ending at the last point of the list, only when that run is at
  least ``input_min_altitude_trailing_point_percent`` percent of the points, and never shorter
  than 4 points (the smallest run giving a real cubic: 2 points give a line, 3 a parabola).
  Otherwise the interpolated positions have no altitude; with ``extrapolate=False`` the positions
  before the run have none either.

Implementation Details
======================

Core Algorithm
--------------

The spline lives in ``GapFiller`` (module ``step_cloud_schemas.gnss.gap_filler``). For a
time-ordered list of positions, ``GapFiller.resample()`` follows these steps:

1. **Validation**: Fewer than 2 positions are returned as-is; times not strictly increasing raise
   ``ValueError``
2. **Already at the Output Period**: When every interval is within the period range, the positions
   keep their times (truncated to the maximum point number) and no spline is built
3. **Grid**: Otherwise the grid of the output period spans the points (see :doc:`find_period`),
   so a longer input period is interpolated and a shorter one decimated; only the first
   ``max_point_number`` grid times are generated
4. **Real Points**: A grid time equal to an input time keeps that real position
5. **Spline**: ``GapFiller.interpolate()`` fits one spline on every point of the list and evaluates
   it only at the grid times without a real point; for a pure decimation (every grid time on an
   input time) no spline is built
6. **Output Generation**: ``GapFiller._build_chain_positions()`` computes distance, speed and
   heading of the whole grid with one batched geodesic call. The first position is kept
   unchanged; after it, a real position is unchanged when it reports both speed and heading,
   otherwise both are recomputed from the displacement (see the Real New Position section of
   :doc:`spline_hermite`); the other grid points become estimated positions with the displacement
   speed and heading

Code Structure
--------------

.. code-block:: python

   # GapFiller.interpolate: lat/lon (and altitude, when every point has one) share the same x
   column_count = 3 if altitude_complete else 2
   combined_y = np.empty(shape=(points_number, column_count), dtype=np.float64)
   combined_y[:, 0] = latitudes
   combined_y[:, 1] = np.unwrap(longitudes, period=LONGITUDE_RANGE)
   if altitude_complete:
       combined_y[:, 2] = altitudes_m
   interpolator = CubicSpline(x=times_ms, y=combined_y)
   interpolated = interpolator(x=target_times_ms, extrapolate=False)

Performance Analysis
====================

Time Complexity
---------------

The cubic spline interpolation has the following time complexity characteristics:

**Spline Construction: O(n)**
  - Array preparation: O(n) where n is the number of input points
  - SciPy CubicSpline construction: O(n) due to the tridiagonal matrix solver
  - Total spline creation: O(n), one vector-valued spline plus, at most, one altitude spline

**Interpolation Evaluation: O(log(n))**
  - Binary search for spline segment: O(log(n))
  - Polynomial evaluation: O(1)
  - **Per evaluation**: O(log(n))

**Resampling: O(n + k·log(n))**
  - Input arrays: O(n)
  - Grid generation: O(k) where k is the number of grid points kept
  - Grid matching (``numpy.searchsorted``): O(k·log(n))
  - Spline construction: O(n), only when some grid point is estimated
  - Interpolation evaluation: O(k·log(n))
  - Output generation: O(k) for the batched geodesic call and the position objects
  - **Total**: O(n + k·log(n))

Space Complexity
----------------

**Memory Usage: O(n + k)**
  - Input arrays: O(n), the positions of the list (n points)
  - Spline coefficients: O(n), temporary
  - Output: O(k) for the grid positions
  - **Total**: O(n + k)

.. note::
   ``GapFiller`` keeps no mutable state: the cost of one call depends only on the list length.

Configuration Parameters
========================

The interpolation behavior is controlled by ``GapFillerConfig``:

.. code-block:: python

   @dataclass(frozen=True, kw_only=True, slots=True)
   class GapFillerConfig:
       input_min_altitude_trailing_point_percent: int  # Altitude trailing run (%)
       output_nominal_period_ms: int                   # Target output period (ms)
       output_max_period_deviation_ms: int             # Timing tolerance (ms)

**Parameter Constraints** (checked by ``__post_init__``, inclusive):
  - ``input_min_altitude_trailing_point_percent``: 0-100, used by ``resample`` only (``fill``
    interpolates the altitude linearly)
  - ``output_nominal_period_ms``: 100-1000
  - ``output_max_period_deviation_ms``: 0-50

Examples
========

Basic Usage Example
-------------------

.. code-block:: python

   import logging

   from step_cloud_schemas import GapFiller, GapFillerConfig

   gap_filler = GapFiller(
       config_par=GapFillerConfig(
           input_min_altitude_trailing_point_percent=25,
           output_nominal_period_ms=100,  # 10 Hz output rate
           output_max_period_deviation_ms=25,
       ),
       logger=logging.getLogger(),
   )

   # records: PositionInfoRecord list, strictly increasing time
   positions = gap_filler.resample(
       actor=actor_id, records=records, max_point_number=100
   )

   # The positions at the output period, the first one unchanged
   for pos in positions:
       print(f"Time: {pos.time}, Lat: {pos.position.latitude}, "
             f"Lon: {pos.position.longitude}")

The stream gaps use ``GapFiller.fill()`` instead, see :doc:`spline_hermite`.

Algorithm Advantages
====================

**Smoothness**: Cubic splines provide C^2 continuity, ensuring smooth trajectories without sharp corners or discontinuities.

**Global Fit**: The spline coefficients come from one tridiagonal system over the whole
list, so a change in one data point affects every segment, with an influence decaying away
from the point; the construction cost stays O(n).

**Smoothness of the End Conditions**: SciPy's default not-a-knot end conditions are used;
the minimum-curvature property holds only for natural end conditions, which are not used
here.

**Computational Efficiency**: O(n) construction time and O(log n) evaluation time make it suitable for real-time applications.

Limitations and Considerations
==============================

**Boundary Effects**: Spline behavior at boundaries depends on boundary conditions (natural, clamped, or not-a-knot).

**Oscillation**: With noisy data or poor point distribution, cubic splines can exhibit unwanted oscillations between data points. In a stream, the velocity of the last point is also estimated without the following point, which is why the latitude and longitude of the stream gaps use a Hermite segment (see :doc:`spline_hermite`).

**Temporal Gaps**: Large gaps in time can cause unrealistic interpolation; a list spanning a long gap is better split by the caller before resampling.

**Coordinate System**: Interpolation is performed in geographic coordinates (lat/lon), which may introduce distortions for large distances due to Earth's curvature.

**Minimum Points**: The interpolation needs at least 2 points: with 2 points the spline degenerates to a line, with 3 to a parabola; a real cubic needs at least 4 points (the minimum required for the separate altitude spline).
