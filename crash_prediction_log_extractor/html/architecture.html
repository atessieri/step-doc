Architecture

This document describes the architecture of crash_prediction_log_extractor, a Python library and CLI that parses marker-based step_crash_prediction logs and produces JSON payloads, interactive HTML maps and dashboards, and a GPX file.

Overview

The library implements a deterministic, file-based pipeline, run once per input log file:

  1. Read a plain-text UTF-8 log file line by line.

  2. Parse every scenario block into one Session of a CollectionSessions payload (LogExtractor).

  3. Derive CollectionActors, CollectionSequences, and CollectionCheckpoints from the sessions (DataRetriever).

  4. Write the JSON payloads, the Folium maps (InteractiveMap), the Plotly dashboards (InteractiveChart), and the GPX tracks (GpxBuilder).

The architecture is layered:

  • Orchestration layer: CLI entry point in __main__.py

  • Parsing layer: LogExtractor and its parser state machines (log_extractor.py)

  • Data model layer: Pydantic models in collection_sessions.py, collection_actors.py, collection_sequences.py, collection_checkpoints.py, and the configuration model in crash_prediction_log_extractor_config.py

  • Transformation layer: DataRetriever (data_retriever.py)

  • Rendering layer: InteractiveMap (interactive_map.py), InteractiveChart (interactive_chart.py), GpxBuilder (gpx_builder.py), and the static assets of the templates package

Components

CLI Entry Point

The main() function in __main__.py orchestrates all user operations.

Responsibilities:

  1. Print help and return USAGE when no argument is given.

  2. Write the JSON schemas (-s) and examples (-e) of all models.

  3. With -c, validate the configuration, configure the logger from its log field, create outputFolderPath, and run _create_write_files for every entry of inputFilePathList, with the union of the three road-type lists as map filter.

  4. Return typed exit codes (ExitCode):

    • 0 (OK): success

    • 1 (USAGE): no arguments

    • 2 (ERROR): unhandled exception

    • 3 (ABORTED): KeyboardInterrupt

_create_write_files runs, for one log file, the sessions step (JSON and map), the actors step (JSON, map, and GPX), the sequences step (JSON and distance/heading dashboard), and the checkpoints step (JSON and performance dashboard). A file from which no session is extracted produces no output.

LogExtractor

LogExtractor is the parser engine. Instantiate it with the log file path and a logging.Logger, call extract(), then read the result from the collections property. It is not thread-safe.

Parser state machines:

  • ParserScenarioState: WAIT_FOR_START_SCENARIO → WAIT_FOR_SESSION_TIME → WAIT_FOR_END_SCENARIO → DONE

  • ParserSectionDataState: WAIT_START_SECTION_DATA → WAIT_END_SECTION_DATA → DONE, for each of the three blocks in DATA_MARKERS (ParserTableDataMarkerItem of DataType x SectionDataType)

  • ParserCrashState: WAIT_START_CRASH → WAIT_RISK → WAIT_END_CRASH → DONE

Regex marker families:

  • Scenario: --Scenario (start|end)-- and --Scenario t: <ISO8601>--

  • Section data: --Section (normalized real|normalized forecasted|anomaly real) (start|end)--

  • Crash section: --Section crash (start|end)--

  • Crash record: --Crash (start|end)-- and --Time: <ISO8601>, pos: (<lat>, <lon>), risk: <1-7>--

  • Actor: --sid: <station_id>, oid: <object_id|None>, type: <TrafficParticipantType>, confidence: <0-100|None>--

  • Point: --t: <ISO8601>, p: (<lat>, <lon>), t: <PositionType>, s: <speed|None>, h: <heading|None>--

  • Checkpoint: --Checkpoint: <name>, timer: <ms>--

Session assembly rules:

  • Every complete scenario with at least one actor becomes one Session.

  • An actor’s dataType is normalized when it has normalized real points, otherwise anomaly; the two are never combined.

  • Forecasted positions are kept for normalized data only.

  • A missing speed/heading is derived from the actor’s previous point (SpeedHeading).

  • A crash record needs at least MINIMUM_ACTORS_IN_CRASH (2) distinct actors to be kept.

  • Checkpoints with an unknown name are skipped with a warning.

Data Models

All models are strict, frozen, forbid extra fields, and expose print_to_file(), print_schema(), and print_example() (the configuration exposes a template instead of an example).

  • collection_sessions: ActorIdModel (with ActorKey identity), Position, CrashInfo, DataType, SessionData, ActorSession, Session, CollectionSessions

  • collection_actors: ActorSessionData, CollectionActor, CollectionActors

  • collection_sequences: ForecastedPosition, SequenceElement, ActorSequence, CollectionSequences

  • collection_checkpoints: CheckpointType, CheckpointDataModel, SessionCheckpoints, CollectionCheckpoints

  • crash_prediction_log_extractor_config: MapRoadType, CrashPredictionLogExtractorConfig

DataRetriever

DataRetriever derives the secondary payloads from a CollectionSessions document:

  • get_collection_actors: regroups the sessions per actor; each session keeps only the crashes involving that actor.

  • get_collection_sequences: for each actor, merges the real positions of its sessions into one chronological list (skipping positions at or before the last appended timestamp) and pairs each real position with the forecasted positions of earlier sessions (ForecastedPoints) matched within maxToleranceTime, with their distance and heading errors.

  • get_collection_checkpoints: extracts the per-session checkpoints.

ISO 8601 to epoch-millisecond conversions are memoized for the lifetime of the instance. It is not thread-safe.

InteractiveMap

InteractiveMap parses and filters the OSM road networks once at construction (MapData with MapBounds per file). Each map (collection_sessions_create_map, collection_actors_create_map) draws the road network of the first loaded OSM file whose bounds overlap the collection, one selectable layer per road type, and injects the serialized collection as chunked <script> blocks (64 Mi characters each) so large logs stay below the browser string-length limit. Crashes below collisionRiskThreshold are drawn in gray, the others in yellow.

InteractiveChart

InteractiveChart fills the dashboard templates by placeholder substitution and inlines the full plotly.js bundle, so every file is self-contained:

  • distance_heading_write_html: distance-error and heading-error series per actor and per forecast index, from CollectionSequences.

  • checkpoints_write_html: elapsed time between two selectable checkpoints across sessions, with statistics, from CollectionCheckpoints.

GpxBuilder

GpxBuilder.build_file writes one track per actor, named Path actor <stationId>_<objectId> (none when there is no object id), in the format written by step_message_save’s GpxWriter and read by step_publisher_pkl. Consecutive sessions are merged into one chronological segment; tracks are sorted by station id then object id; heading and speed are written to the Garmin TrackPointExtension v2 course/speed elements. Actors without track points are skipped.

Templates

The templates package contains no Python code; it is an importlib.resources anchor for the HTML templates, JavaScript scripts, and CSS stylesheets of the maps and dashboards.

Performance Considerations

The complexity figures below come from the module docstrings.

Let:

  • \(B\) = size of the log file, \(K\) = crash records, \(a\) = actors per crash record

  • \(M\) = total size of the OSM files, \(E\) = road edges of the matched map, \(n\) = size of the serialized outputs

  • \(s\) = sessions of an actor, \(Q\) = forecasted positions of an actor, \(P\) = real positions appended to its sequence, \(F\) = forecasts inside one matching window, \(k\) = prior sessions matched per real position

Time Complexity

  • Log extraction: \(O(B + K \cdot a^2)\)

  • Maps: \(O(M + n + E)\)

  • Sequences (dominant): \(O(s \cdot Q + P \cdot F)\) per actor, the only cost that grows with the product of two data sizes

  • JSON, dashboards: \(O(n)\)

  • GPX: \(O(a \log a + N + S \log p)\)

Space Complexity

  • Log extraction: \(O(P)\) parsed positions, crashes, and checkpoints

  • Sequences: \(O(P \cdot k + Q)\) per actor

  • Pipeline: \(O(M + P + n + E \cdot h)\), one input file at a time

Practical Notes

  • Parsing is robust to non-marker lines (ignored), independently of log level.

  • Incomplete scenarios and scenarios without actors produce no session.

  • Logging detail is controlled by the log field of the configuration file.
