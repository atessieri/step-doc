Architecture

This document describes the architecture of STEP Message Save, a Python package for communicating with the STEP (Safer Transport for Europe Platform) MQTT broker to receive ITS (Intelligent Transport Systems) messages.

Overview

STEP Message Save serves as a client of the STEP MQTT broker. It subscribes to the configured topics, receives ITS messages, and appends them, as JSON lines, to a single local output file. There is no Redis integration, message publication, or CloudEvents conversion involved: the client is a receive-only bridge between MQTT and the filesystem.

Next to the client, the package provides an offline file conversion feature: a file of ITS messages (e.g. the JSON-lines output file, or a pickle actor trajectory file) can be converted into another format (e.g. GPX) through pluggable file loaders and writers.

Library

The STEP Message Save project leverages several key libraries to provide robust ITS message communication and file persistence capabilities:

Direct Dependencies (declared in pyproject.toml and imported directly by step_message_save’s own source):

  1. Pydantic: Used extensively for configuration management and data validation throughout the system. The StepMessageSaveConfig class and its nested configuration models rely on Pydantic’s BaseModel for type-safe configuration loading, validation, and JSON schema generation.

  2. step_cloud_schemas: Provides standardized data schemas for ITS messages including CAM (Cooperative Awareness Messages), CPM (Cooperative Perception Messages) and DENM (Decentralized Environmental Notification Messages) identifiers. It also provides the runtime used by STEP Message Save:

    • AppRunner/AbstractApp: asyncio application runner with a cooperative shutdown on SIGINT/SIGTERM (SIGINT/SIGBREAK on Windows)

    • ReconnectingApp: the AbstractApp running cycle() forever, with the reconnect loop and the fatal error handling

    • StepLogger: logger factory

    • IS_WINDOWS: platform flag selecting the event loop

  3. step_lib: Core library providing fundamental components including:

    • AsyncComManager: Base class for asynchronous communication management

    • FacilityMessage: ITS message handling and encoding/decoding functionality

    • MQTT utilities including MqttQoS enumerations

    • TLS/SSL security parameter management

    • MqttCredential: the MQTT broker host, port and authentication, read from the environment by from_env()

    • StepLibMqttFatalError: the MQTT connection refusals a reconnect cannot fix

  4. paho-mqtt: Imported directly in StepBroker (ReasonCode, SubscribeOptions) to build MQTT subscription options and interpret SUBACK reason codes.

  5. python-dotenv (through step_lib): MqttCredential.from_env(), called by MessageSaveApp.__init__(), loads the .env file found in the current working directory (or an ancestor of it) into the environment before the credential is read.

  6. gpx: Used by GpxWriter to build and write GPX documents (tracks, segments, track points and their extensions).

Transitive Dependencies Used Indirectly (not imported by step_message_save’s own source, but relied upon underneath a direct dependency):

  1. aiomqtt: Asynchronous MQTT client library with TLS support, used by step_lib.AsyncComManager to implement the actual MQTT connection; step_message_save never imports it directly.

This library ecosystem enables STEP Message Save to provide a comprehensive, type-safe, and highly configurable solution for capturing ITS message traffic within the STEP platform.

Components

The architecture follows a modular design pattern that separates concerns between MQTT communication, message persistence, and configuration management. This enables flexibility and maintainability in the system design.

Main Components:

  1. main / AppRunner: CLI entry point and process runner (AppRunner from the step_cloud_schemas library)

  2. AbstractApp / ReconnectingApp: Abstract workload classes (from the step_cloud_schemas library) that MessageSaveApp derives from

  3. StepBroker: Gateway class for MQTT communication with the STEP broker

  4. Message Pipeline (MessageSaveApp in message_save_app.py): The receiver/writer tasks and the asyncio.Queue connecting them, with reconnect handling; this is the part of the application that actually reads from StepBroker and appends to the output file

  5. StepMessageSaveConfig: Configuration management for the client

  6. MqttCredential: MQTT credential read from the environment (from the step_lib library), see Environment Variables

  7. StepLogger: Logging utilities used by the client (from the step_cloud_schemas library)

  8. StepException: Custom exceptions for error handling

  9. File Conversion: FileConverter with the pluggable FileLoader and FileWriter subclasses, used by the -f/-x/-o command-line options

StepBroker

The StepBroker (STEP Gateway) is a core component of the STEP Message Save architecture that manages MQTT communication with the STEP broker. Extending the AsyncComManager class, it provides an asynchronous interface for secure, reliable message reception from the STEP ecosystem.

Key responsibilities of StepBroker include:

  1. MQTT Connection Setup: Configures TLS/SSL parameters (when mqttClient.sslEnable is set) and the underlying MQTT v5 connection settings for the lifetime of the async with StepBroker(...) block. StepBroker itself has no self-reconnect logic; reconnection after a lost connection is handled by the inherited ReconnectingApp.work() of MessageSaveApp (see Message Pipeline below), which discards the broker and, after waiting reconnectInterval seconds, runs MessageSaveApp.cycle() again to construct a new one.

  2. Topic Subscription: subscribe_execution() subscribes to the topics configured in mqttProtocol.subscriptionTopics with a fixed set of MQTT options (configured QoS, noLocal=False, retainAsPublished=False, retainHandling=RETAIN_DO_NOT_SEND) and raises StepMessageSaveError if the number of results doesn’t match the number of topics or if any granted QoS doesn’t match the one requested.

  3. ITS Message Access: Exposes received messages through the inherited its_messages property. Each access returns a new ItsMessagesIterator that decodes raw MQTT payloads into step_lib.FacilityMessage objects, but every iterator wraps the same underlying incoming-message queue of the single MQTT connection — it is a “dynamic view”, not an independent stream.

  4. Context Management: Implements asynchronous context management through an overridden __aenter__ (which delegates to the parent and returns self) and the inherited __aexit__, for clean resource handling.

StepBroker is receive-only in this application: publish_topics_params is never configured, so the inherited publish_its_message() would just log a warning and return if it were ever called, and it never is. The class uses asynchronous patterns throughout to ensure non-blocking operations, making it suitable for high-throughput messaging environments in ITS applications.

Message Pipeline

The message pipeline is implemented entirely by the MessageSaveApp class of message_save_app.py, the ReconnectingApp[ExitCode] workload (see Application Runtime (step_cloud_schemas)) that main() hands to AppRunner, on top of the StepBroker instance and the configuration; StepBroker itself never touches the queue or the output file. Its constants and coroutines are private members of the class. It is composed of:

  1. STEP receiver tasks: config.stepReceiverNumber instances of _step_receive_run() are started concurrently in a single TaskGroup, all sharing the same StepBroker instance. Each task loops async for message in step_broker.its_messages and puts message.its_payload.to_json(indent=None) onto a shared, bounded asyncio.Queue[str]. Because every ItsMessagesIterator returned by its_messages wraps the same underlying MQTT incoming-message queue, the N tasks act as competing consumers (a worker pool) over one physical connection’s message stream, rather than each receiving an independent copy of all traffic.

  2. The queue: A single asyncio.Queue[str], sized by config.maxFileWriterQueueRooms, decouples the receiver tasks from the file writer task. It is created once by MessageSaveApp.__init__() before the first cycle(), and that same instance is shared across every connection cycle — a message already queued when a connection drops is not discarded, it is simply drained by the writer task started on the next cycle. A message is only lost if a receiver task is cancelled while blocked handing it off to a full queue, or if the writer fails to write it to disk.

  3. The file writer task: The output file (config.outputFile) path is resolved once by MessageSaveApp.__init__() before the first cycle(), but the file itself is opened, in append mode, by _step_message_write_run() — once per connection cycle, since exactly one instance of that task is (re)started per cycle. Append mode means a reconnect, or even a full process restart, never truncates the file: messages already on disk are always preserved. Each writer instance loops forever, dequeuing one JSON string at a time, writing it followed by a newline, and closing the file when the task is cancelled at the end of that cycle. Because only one writer task is ever active at a time, writes are naturally serialized without a lock. Writes are buffered and are not explicitly flushed after each message — they reach disk once the buffer fills or the file is closed.

  4. The connection cycle: each MessageSaveApp.cycle() creates the directory of the output file (a no-op once it exists), constructs a brand-new StepBroker, awaits StepBroker.subscribe_execution() and runs the receiver tasks and the writer task in a TaskGroup nested in the broker context, so the broker only disconnects once the group has unwound.

  5. The reconnect loop: the inherited ReconnectingApp.work() runs cycle() in a loop. If an exception propagates out of cycle() (e.g. a lost MQTT connection), the broker and all receiver/writer tasks are torn down as the async with/TaskGroup blocks exit, work() logs it with its traceback, sleeps config.reconnectInterval seconds and runs cycle() again, whose fresh _step_message_write_run() task reopens the same output file in append mode against the same shared queue. If the current task is being cancelled (shutdown in progress), a CancelledError is raised instead, without an ERROR traceback, so the shutdown is not turned into a reconnect.

  6. Permanent errors: an error that a reconnect cannot fix (_FATAL_ERRORS: step_lib StepLibMqttFatalError - CONNACK refusing the MQTT authentication or authorization) ends the run with fatal_result() (ExitCode.ERROR) instead of retrying forever.

  7. The graceful shutdown: AppRunner (from step_cloud_schemas) runs MessageSaveApp.work() as a task of its own TaskGroup and, on a shutdown signal (SIGINT/SIGTERM on POSIX, SIGINT/SIGBREAK on Windows), cancels it wherever it is (connecting, subscribing, running the tasks of cycle() or waiting to reconnect), so StepBroker disconnects cleanly even while the broker is unreachable. Once the group has unwound, AppRunner calls MessageSaveApp.on_shutdown(), whose _drain_queue() appends the messages still queued to the output file, and the program exits with ExitCode.ABORTED. See Entry Point and AppRunner below.

work() returns only after a fatal error; otherwise it runs until AppRunner cancels it.

Entry Point and AppRunner

step_message_save.__main__.main() is the console script entry point. It:

  1. Builds a default StepLogger logger (stderr, WARNING) and an AppRunner[ExitCode]. On Windows the runner uses asyncio.SelectorEventLoop, because the default ProactorEventLoop does not implement add_reader/add_writer, which aiomqtt’s socket needs to detect the CONNACK response.

  2. Prints the help and returns ExitCode.USAGE when no argument is given.

  3. Writes the configuration JSON schema (-s/--conf_schema) and/or the configuration template (-t/--conf_template) to the given directories.

  4. Raises StepCliError when only one of -c/--config and -i/--instance is given.

  5. Runs the file conversion requested with -f/--file (-x/--convert, -o/--output), see File Conversion, before the client is started.

  6. With both -c/--config and -i/--instance, validates the configuration file into StepMessageSaveConfig, rebuilds the logger from config.log, force-writes the program and library versions (step_cloud_schemas, step_lib) and runs MessageSaveApp with AppRunner.run(), returning its exit code.

AppRunner (from step_cloud_schemas) owns the process-wide plumbing: the asyncio.Runner, the loop exception handler, sys.unraisablehook and the shutdown signal handlers. It runs MessageSaveApp.work() (inherited from ReconnectingApp) next to a shutdown watcher task in a TaskGroup: when a shutdown signal arrives the watcher raises an internal _ShutdownRequestedError, the TaskGroup cancels work wherever it is and, once every task has unwound (the writer task has closed the output file and StepBroker has disconnected), MessageSaveApp.on_shutdown() is called with the signal.

main() maps the outcome to an ExitCode:

  • OK (0): success (e.g. only schema/template generation or a file conversion was requested), including -h/--help and -v/--version

  • USAGE (1): no argument, an invalid or unknown option, or StepCliError (logged as a plain error line)

  • ERROR (2): a file conversion failure (LoaderError/WriterError, logged as a plain error line), or any other unhandled exception, logged with its traceback: an invalid configuration file, a missing or invalid environment variable (ValueError raised by the MessageSaveApp constructor, see Environment Variables), or an error that a reconnect cannot fix (fatal_result())

  • ABORTED (3): shutdown signal (returned by on_shutdown, after the queue has been drained to the output file) or KeyboardInterrupt (a signal received before run() has started the event loop, or after it has returned)

Application Runtime (step_cloud_schemas)

Note

AppRunner, AbstractApp and ReconnectingApp are not part of the step_message_save package: they are imported from the external step_cloud_schemas dependency, shared by the STEP programs. Only their public interface, the part used by STEP Message Save, is described here.

The three classes split a long-running program in two parts: the process-wide plumbing (event loop, signal handlers, exception hooks), owned by AppRunner, and the workload, supplied by the program as an AbstractApp subclass. R is the program’s result type: for STEP Message Save, ExitCode.

Class

Role

AbstractApp[R]

Abstract base class of a workload run by AppRunner. It declares the two methods AppRunner needs and holds no state (empty __slots__, so a subclass declares its own).

ReconnectingApp[R]

Abstract AbstractApp subclass that implements work as a reconnect loop around a connection cycle (cycle), implemented by the program.

AppRunner[R]

Singleton that runs an AbstractApp on a new event loop until it ends or a shutdown signal stops it.

The class diagram below shows the public interface of the three classes and how MessageSaveApp plugs into them:

AbstractApp: public interface

  • async work() -> R (abstract): The workload, called once per run as a task of the AppRunner TaskGroup; it returns the result when it ends on its own. On a shutdown signal it is cancelled at the await it is suspended on, so it has to be cancellation-safe.

  • on_shutdown(stop_signal: Signals) -> R (abstract): Called by AppRunner after a shutdown signal stopped work, once every task has unwound (the resources held by work are already released); it runs on the event loop thread and cannot await. Its value is the result of the run. MessageSaveApp appends the messages still queued to the output file (_drain_queue()), logs the signal name and the number of messages saved, and returns ExitCode.ABORTED.

ReconnectingApp: public interface

  • ReconnectingApp(logger, reconnect_interval): logger is used for the start, error and retry messages, reconnect_interval is the number of seconds to wait before the next cycle. MessageSaveApp passes its own logger and config.reconnectInterval.

  • async cycle() -> None (abstract): Opens the connections and runs the tasks until one of them fails; returns only if every task ends normally, and then the next cycle starts at once. Like work, it has to be cancellation-safe. MessageSaveApp.cycle() creates the directory of the output file, opens the StepBroker and runs the receiver and writer tasks.

  • fatal_result() -> R (abstract): The result returned by work after an error that a reconnect cannot fix (MessageSaveApp: ExitCode.ERROR).

  • async work() -> R: Logs Program started, then runs cycle in a loop. When cycle raises:

    • while a shutdown cancellation is in progress, the error is logged at INFO level and CancelledError is restored, so the shutdown goes on without an ERROR traceback;

    • otherwise the error is logged with its traceback, and if it, or any error nested in an ExceptionGroup (as raised by a TaskGroup), is one of the subclass’s fatal error types, work logs a CRITICAL line and returns fatal_result();

    • otherwise work waits reconnect_interval seconds and runs cycle again.

    It never returns otherwise: the loop ends only when AppRunner cancels it.

The fatal error types are the _FATAL_ERRORS class attribute that each subclass sets (MessageSaveApp: step_lib StepLibMqttFatalError); with none set, every error is retried. Any other error, including an output file or directory that cannot be written, is retried every reconnectInterval seconds.

AppRunner: public interface

  • AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None):

    • logger_param: Logger used by the default exception and unraisable handlers.

    • loop_factory: Factory of the event loop created by every run, forwarded to asyncio.Runner; None uses the asyncio default loop. STEP Message Save passes asyncio.SelectorEventLoop on Windows (IS_WINDOWS), because the default ProactorEventLoop lacks the add_reader/add_writer that aiomqtt needs.

    • exception_handler: Event loop exception handler; None logs the exception on the logger.

    • unraisable_handler: Installed as sys.unraisablehook; None logs the exception on the logger.

    The constructor installs the process-wide hooks (signal handlers, sys.unraisablehook): it is called from the main thread as early as possible, which is why main() builds it before parsing the arguments, so that a signal received before run (e.g. during the file conversion or the configuration loading) is still handled. Being a singleton, only the first construction takes effect; the arguments of later calls are ignored.

  • logger (property): The logger given to the constructor.

  • run(app: AbstractApp[R]) -> R: Opens an asyncio.Runner, installs the exception handler and the shutdown handlers (SIGINT/SIGTERM on POSIX, SIGINT/SIGBREAK on Windows), then runs app.work() next to a shutdown watcher in a TaskGroup. It returns the value of app.work() when the workload ends on its own, or the value of app.on_shutdown(stop_signal) when a shutdown signal stops it. Any other exception raised by work propagates wrapped in an ExceptionGroup, which main() logs and maps to ExitCode.ERROR.

A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only sets an event, the watcher task turns it into an exception, and the TaskGroup cancels work at the await it is suspended on.

StepMessageSaveConfig

The StepMessageSaveConfig component is responsible for configuration management in the STEP Message Save architecture. Built as a Pydantic BaseModel, it provides a robust, type-safe mechanism for loading, validating, and accessing configuration settings throughout the application.

Key features of StepMessageSaveConfig include:

  1. JSON Configuration Loading: Loads configuration settings from a JSON file specified at startup, providing a centralized source of configuration for all components.

  2. Type Validation: Leverages Pydantic’s validation system to ensure all configuration values meet the expected types and constraints, preventing configuration errors at runtime.

  3. Hierarchical Structure: Organizes configuration in a hierarchical manner, with nested models for different aspects of the system:

    • MQTT Client configuration (connection parameters, security settings)

    • MQTT Protocol configuration (QoS, subscription topic management)

    • Logging configuration (handlers, levels, formatting)

  4. Immutable Configuration: Once loaded at startup, the configuration becomes immutable, ensuring consistency throughout the application’s lifecycle.

  5. Output and Concurrency Settings: Carries the output file path (outputFile), the number of concurrent STEP receiver tasks (stepReceiverNumber), and the maximum size of the file writer queue (maxFileWriterQueueRooms).

  6. Default Configuration: Provides get_default() methods to generate sensible default configurations when specific values are not provided.

  7. JSON Schema Generation: Supports generating JSON schemas for configuration validation through the _ConfigGenerateJsonSchema utility class.

The design of StepMessageSaveConfig emphasizes immutability and strong validation, helping prevent configuration-related issues during runtime while providing a clear, structured approach to configuration management.

The MQTT broker address and credentials are the only settings not taken from the JSON configuration file: they are read from the environment, so that secrets are never written to a configuration document. The TLS settings of the MQTT client stay in the configuration file, in the stepBroker.mqttClient section.

How they are read:

  1. MessageSaveApp.__init__() calls MqttCredential.from_env() once, before AppRunner.run(). The credential is read once at construction rather than in cycle(), because work() retries on every non-fatal exception and a missing variable would never end the program. The resulting MqttCredential (a frozen dataclass, kept separate from StepMessageSaveConfig) is handed to every StepBroker built by cycle().

  2. from_env() first loads the .env file found in the current working directory or its nearest parent (load_dotenv(find_dotenv(usecwd=True))): what counts is the directory step_message_save is launched from, not the directory of the installed package. Without a .env file only the environment is read.

  3. A variable already set in the environment (shell, container) wins over the .env file: load_dotenv only adds missing variables.

  4. An empty username or password counts as unset.

  5. The host, the port and whether a username is set are logged at INFO level; the username and the password never are.

  6. A missing MQTT_URL/MQTT_PORT, a non-integer or out-of-range port, or an empty host raise ValueError; main() logs it with its traceback and returns ExitCode.ERROR.

Credentials that the broker rejects are not detected here but on connection, as a fatal error (StepLibMqttFatalError) that ends the run with ExitCode.ERROR instead of being retried.

The repository ships a commented template, env/.env.example: download it, save it as .env in the directory step_message_save is launched from and fill in the values. .env is listed in .gitignore; only the template is versioned. See Environment Variables for the file format and the alternatives to the file.

StepLogger

StepLogger is provided by the step_cloud_schemas library (not implemented within step_message_save itself) and is used by STEP Message Save to build and configure its logging.Logger instances. Today it is a thin factory built directly on top of Python’s standard logging module; a future revision is expected to move the underlying implementation to the loguru library while keeping the same StepLogger interface used by step_message_save.

Key features of StepLogger include:

  1. Multiple Handler Types: Builds loggers with one or more of the following handlers, each independently configurable via LogConfig:

    • stream: writes to stderr

    • null: discards all log records

    • file: writes to a single log file (append or overwrite)

    • sizeFileRotate: rotates the log file once it exceeds a configured size

    • timeFileRotate: rotates the log file at a configured time interval

    Rotated log files are automatically compressed with BZIP2. There is no syslog handler.

  2. UTC Timestamp Formatting: Uses a custom UtcFormatter so all log timestamps are rendered in UTC regardless of the local system timezone.

  3. Log Level Management: Supports the standard log levels (DEBUG, INFO, WARNING, ERROR, CRITICAL) per handler and a global logger level, via LogMode.

  4. Configuration Integration: Driven by the LogConfig/LogHandlerConfig models (from step_cloud_schemas), which are carried inside StepMessageSaveConfig.log.

  5. Public API: Exposes two classmethods:

    • get_logger(name, config, instance_name): builds and returns a configured Logger. If config is None, it falls back to a single stderr stream handler at WARNING level with the logger itself at INFO. File-based handlers require instance_name to build the log filename, and raise ValueError if it is missing.

    • logger_force_write(logger, msg): temporarily elevates the logger and all its handlers to INFO to guarantee a message is emitted (used by step_message_save for startup/version banners), then restores the original levels.

There is currently no built-in support for syslog, or for attaching structured context such as component IDs or transaction IDs to log records beyond what the configured format string exposes (e.g. %(module)s, %(funcName)s).

StepException

step_message_save defines a minimal exception hierarchy in step_exception.py, used to distinguish STEP Message Save errors from other unhandled exceptions:

  1. StepMessageSaveError: Base exception for the client. A plain subclass of Exception with no additional attributes; it is raised, for example, by StepBroker.subscribe_execution() when a topic subscription fails or its returned QoS doesn’t match the configured one.

  2. StepCliError: Subclass of StepMessageSaveError raised for CLI-specific errors in main() — such as passing -c/--config without -i/--instance or vice versa, or -x/--convert without -f/--file. main() maps it to ExitCode.USAGE.

  3. LoaderError: Raised by a FileLoader when its input file does not match, or cannot be parsed as, its format, and by FileConverter when no loader accepts the input file.

  4. WriterError: Raised by a FileWriter when its output file cannot be written, and by FileConverter when the output directory cannot be created.

main() maps LoaderError and WriterError to ExitCode.ERROR, logging only the message, without a traceback.

All classes are message-only exceptions (the message is carried via the standard Exception args, not a dedicated attribute); there is no structured error context, error-type classification, or recovery-hint mechanism beyond what the raised message string conveys. Callers catch and log these via the standard Python exception handling already used throughout the application (e.g. the top-level except clauses in main() and the except clause of the reconnect loop in the inherited ReconnectingApp.work() of MessageSaveApp).

File Conversion

The file conversion is independent of the MQTT client: it runs offline, before the client is started, when -f/--file is given. It is built on three components:

  1. FileLoader (loaders/file_loader.py): Abstract base class of the loaders. A loader is a stateless, callable parser for one format: given a file path, it returns the list[FacilityMessage] the file contains, or raises LoaderError if the file does not match its format. The handled extension is declared in the EXTENSION class attribute, checked by __init_subclass__ when the subclass is defined. The protected _build_cam_data() helper builds a CamDataV1 from scalar trajectory values. Concrete loaders:

    • JsonlLoader (.jsonl): one ItsMessageRoot (CAM, CPM, DENM) per line

    • PickleActorLoader (.pkl): vehicle trajectories, one CAM per point

  2. FileWriter (writers/file_writer.py): Abstract base class of the writers, the inverse of a loader: given a file path and a list[FacilityMessage], it writes the messages it can represent, or raises WriterError. Concrete writers:

    • GpxWriter (.gpx): one track per station, built from the CAM messages with a position, in the track format read by step_publisher_pkl

  3. FileConverter (file_converter.py): Chains a loader and a writer. The input format is deduced from the file: the loaders owning the input file extension are tried first, then all the others, and the first one that does not raise LoaderError wins. The output format is selected by name (the writer’s extension without the dot). It also resolves the output file path and creates its missing directories, only after the input file has been loaded.

The loader and writer classes used by the command line are listed in the CONVERSION_LOADERS and CONVERSION_WRITERS constants of __main__.py; the -x/--convert choices are derived from CONVERSION_WRITERS. See Creating a Loader or Writer for how to add a new format.

Sequence Diagram

The sequence diagram below illustrates the single message flow implemented by STEP Message Save: receiving ITS messages from the STEP broker and appending them to the output file. It reflects the actual implementation in message_save_app.py, where config.stepReceiverNumber concurrent _step_receive_run() tasks share a single StepBroker instance and compete for messages from its single underlying MQTT connection, feeding a bounded asyncio.Queue that a single _step_message_write_run() task drains, owning the output file exclusively.

On an unmanaged exception (e.g. a lost MQTT connection), the exception propagates out of the async with StepBroker(...)/TaskGroup block in MessageSaveApp.cycle(), tearing down the current broker and all receiver/writer tasks. The inherited ReconnectingApp.work() then waits reconnectInterval seconds and runs cycle() again, retrying the whole connect-subscribe-receive cycle with a brand-new StepBroker instance. The new writer task reopens the output file in append mode, so messages persisted before the drop are not lost, and drains the shared queue, so messages queued before the drop are not lost either. A StepLibMqttFatalError (the broker refused the client’s authentication or authorization) is not retried: work() returns ExitCode.ERROR.
