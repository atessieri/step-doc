STEP Message Save Usage Guide
=============================

Introduction
------------

STEP Message Save is a Python package designed to subscribe to the STEP (Safer Transport for
Europe Platform) MQTT broker and persist the received ITS (Intelligent Transport Systems)
messages, as JSON lines, to a local output file. This guide walks through the different ways
to use the STEP Message Save client, from basic configuration to advanced usage patterns.

Prerequisites
-------------

Before using STEP Message Save, make sure you have:

    #. Python 3.13 or higher installed
    #. Access to a STEP MQTT broker
    #. The step_message_save package installed in your environment

Installation
------------

You can install the STEP Message Save package using pip:

.. code-block:: bash

   $pip install --extra-index-url https://gitlab.automotive.vodafone.com/api/v4/projects/1472/packages/pypi/simple step_message_save

Or if you're using a development version:

.. code-block:: bash

    pip install -e /path/to/step_message_save

Basic Concepts
--------------

STEP Message Save operates as a client of the STEP MQTT broker, specifically designed for
ITS message capture. Key concepts include:

    * **StepBroker**: Gateway component that handles MQTT communication with the STEP broker
      and subscribes to the configured topics
    * **StepMessageSaveConfig**: Configuration management for the client
    * **ITS Messages**: Standard message formats like CAM (Cooperative Awareness Messages),
      CPM (Cooperative Perception Messages) and DENM (Decentralized Environmental Notification
      Messages)
    * **Output File**: The single JSON-lines file that received messages are appended to
    * **FileConverter**: Converts a saved file into another format, chaining a **loader**
      (``FileLoader`` subclass, which parses a file into ITS messages) and a **writer**
      (``FileWriter`` subclass, which serializes ITS messages into a file); see
      :doc:`loaders_writers` to add a new format

Configuration
-------------

STEP Message Save requires configuration for the MQTT connection and the output file. The
configuration is managed through a JSON file.

Creating a Configuration File
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

To create a default configuration template:

.. code-block:: bash

    step_message_save --conf_template my_config_template

This generates ``my_config_template/step_message_save_config_v1_schema_template.json``,
a template that you can customize for your specific needs.

Key Configuration Parameters
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

* **General Configuration**:

  * outputFile: Path of the file where JSON messages are appended
  * stepReceiverNumber: Number of concurrent STEP receiver tasks (1-50)
  * maxFileWriterQueueRooms: Maximum number of rooms in the queue used to send messages from
    the STEP receiver tasks to the file writer task (1-10000)
  * reconnectInterval: Time between reconnection attempts (seconds); a broker refusing
    the client's authentication or authorization is not retried (exit code ``2``)

* **MQTT Client Configuration** (config file, ``MqttClientConfig``):

  * sslEnable: Whether to use TLS/SSL encryption
  * sslClientCertFile / sslClientKeyFile / sslClientKeyFilePassword: Client certificate
    settings for mutual TLS
  * sslCaCertsFile: CA certificate bundle used to verify the broker
  * sslVerifyServerCert: Whether to verify the broker's certificate

* **MQTT Broker Connection**: host, port and credentials are read from environment
  variables, not from the config file (see `Environment Variables`_).

* **MQTT Protocol Configuration**:

  * keepalive: Keep-alive interval in seconds
  * cleanStart: Whether to start with a clean session
  * subscriptionTopics: List of topics to subscribe to, with the expected message type
    (CAM, CPM or DENM) for each

Environment Variables
---------------------

The MQTT client TLS settings are kept in the JSON configuration file, in the
``stepBroker.mqttClient`` section, while the MQTT broker host, port and credentials are
read from the environment, so that secrets are never written to the configuration file:

.. list-table::
   :header-rows: 1
   :widths: 25 15 60

   * - Variable
     - Required
     - Description
   * - ``MQTT_URL``
     - yes
     - MQTT broker host name or IP address
   * - ``MQTT_PORT``
     - yes
     - MQTT broker port (1-65535); usually 8883 with TLS
       (``stepBroker.mqttClient.sslEnable`` true), 1883 without
   * - ``MQTT_USERNAME``
     - no
     - Username for broker authentication; unset or empty connects anonymously
   * - ``MQTT_PASSWORD``
     - no
     - Password for broker authentication; ignored, with a warning, when
       ``MQTT_USERNAME`` is not set

The ``MessageSaveApp`` constructor reads them once, through step_lib
``MqttCredential.from_env``, before the first connection cycle. A missing ``MQTT_URL``
or ``MQTT_PORT``, a non-integer or out-of-range port, or an empty host raise
``ValueError``: since the credential is read outside the reconnect loop, a
misconfiguration stops the program with exit code ``2`` (``ERROR``) instead of being
retried forever.

**How the variables are read.**

* ``from_env`` first loads the ``.env`` file found in the **current working
  directory** or in its nearest parent directory (``find_dotenv(usecwd=True)``): what
  counts is the directory ``step_message_save`` is launched from, not the directory of
  the installed package. Without a ``.env`` file only the environment is read.
* A variable already set in the environment **wins** over the ``.env`` file:
  ``load_dotenv`` adds the missing variables and never overrides an existing one.
* An empty username or password counts as unset.
* The host and port are logged at INFO level, together with whether a username is
  set; the username and the password never are.

**Format of the .env file.**

* One ``KEY=VALUE`` line per variable, no ``export`` needed;
* ``#`` starts a comment;
* quote a value only if it contains spaces or ``#`` (``MQTT_PASSWORD="a #b"``);
* keep the file out of version control: ``.env`` is listed in ``.gitignore``, only
  the ``.env.example`` template is versioned.

**Template.** ``doc/source/env/.env.example`` is a commented template:

Download the template: :download:`.env.example <env/.env.example>`
(save it as ``.env`` in the directory ``step_message_save`` is launched from). From a
checkout of the repository:

.. tab:: bash

   .. code-block:: bash

       cp doc/source/env/.env.example .env

.. tab:: PowerShell

   .. code-block:: powershell

       Copy-Item doc/source/env/.env.example .env

**Alternatives to the file.** Variables set in the shell or by a container runtime
take precedence over ``.env``:

.. tab:: bash

   .. code-block:: bash

       export MQTT_URL=broker.example.com
       export MQTT_PORT=8883

.. tab:: PowerShell

   .. code-block:: powershell

       $env:MQTT_URL = "broker.example.com"
       $env:MQTT_PORT = "8883"

.. tab:: Docker Compose

   .. code-block:: yaml

       services:
         step_message_save:
           env_file: .env          # or, one by one:
           environment:
             MQTT_URL: broker.example.com
             MQTT_PORT: "8883"

.. note::

   Credentials that the broker rejects are detected on connection, not when the
   variables are read: a CONNACK refusing the MQTT authentication or authorization
   (step_lib ``StepLibMqttFatalError``) cannot be fixed by reconnecting, so the program
   ends with exit code ``2`` (``ERROR``) instead of retrying forever.

Activating the virtual environment
----------------------------------

Before running the client, activate the project virtual environment created in the ``.venv``
folder (see :doc:`package_script`):

.. tab:: Windows

   .. code-block:: console

      $.venv\Scripts\activate

.. tab:: Linux

   .. code-block:: bash

      $source .venv/bin/activate

Running STEP Message Save as a Service
--------------------------------------

To run STEP Message Save as a standalone service:

.. code-block:: bash

    step_message_save --config /path/to/config.json --instance my_instance

This will start the client, which will:

    #. Connect to the configured MQTT broker
    #. Subscribe to the specified topics
    #. Receive ITS messages using the configured number of concurrent receiver tasks
    #. Serialize each received message to JSON and append it to the configured output file

On a graceful shutdown (``SIGINT``/``SIGTERM`` on Linux and macOS, ``SIGBREAK``, i.e.
Ctrl+Break, on Windows) the client disconnects from the broker and appends the messages
still queued to the output file before exiting with exit code ``3`` (ABORTED).

Converting a Saved File
-----------------------

A file of ITS messages can be converted into another format without connecting to the
broker:

.. code-block:: bash

    step_message_save --file /path/to/received.jsonl --convert gpx

The supported formats are:

.. list-table::
   :header-rows: 1
   :widths: 25 15 60

   * - Format
     - Direction
     - Content
   * - JSONL (``.jsonl``)
     - input
     - One ITS message (CAM, CPM, DENM) per line, as written by the client
   * - Pickle actor (``.pkl``)
     - input
     - Vehicle trajectories (``trajectories`` → ``vehicles``), converted into CAM messages
   * - GPX (``.gpx``)
     - output
     - One track per station, named ``Path actor <station_id>_none``, built from the
       CAM messages with a position; heading and speed are stored in the Garmin
       ``TrackPointExtension`` ``course``/``speed`` elements

The input format is deduced from the file, the output format is selected with
``--convert``. The output is written next to the input file, unless ``--output`` gives
another file or directory. See :doc:`commands` for the full rules, and
:doc:`loaders_writers` to add a new input or output format.

The conversion can be combined with ``--config``/``--instance``: the file is converted
first, then the client starts.

Command-Line Options
--------------------

STEP Message Save supports several command-line options:

    * ``--config``, ``-c``: Path to configuration file (requires ``--instance``)
    * ``--instance``, ``-i``: Instance name (required together with ``--config``)
    * ``--conf_schema``, ``-s``: Write the configuration JSON schema into a directory
    * ``--conf_template``, ``-t``: Generate a configuration template into a directory
    * ``--file``, ``-f``: Input file to convert (requires ``--convert``)
    * ``--convert``, ``-x``: Output format of the conversion (requires ``--file``)
    * ``--output``, ``-o``: Output file or directory of the conversion (requires ``--file``)
    * ``--version``, ``-v``: Show version information
    * ``--help``, ``-h``: Show help information
