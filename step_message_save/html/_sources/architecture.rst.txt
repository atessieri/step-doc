Architecture
============

This document describes the architecture of STEP Message Save, a Python package
for communicating with the STEP (Safer Transport for Europe Platform) MQTT broker
to receive ITS (Intelligent Transport Systems) messages.

Overview
--------

STEP Message Save serves as a client of the STEP MQTT broker. It subscribes to the
configured topics, receives ITS messages, and appends them, as JSON lines, to a single
local output file. There is no Redis integration, message publication, or CloudEvents
conversion involved: the client is a receive-only bridge between MQTT and the filesystem.

Next to the client, the package provides an offline file conversion feature: a file of
ITS messages (e.g. the JSON-lines output file, or a pickle actor trajectory file) can be
converted into another format (e.g. GPX) through pluggable file loaders and writers.

Library
-------

The STEP Message Save project leverages several key libraries to provide robust ITS message
communication and file persistence capabilities:

**Direct Dependencies** (declared in ``pyproject.toml`` and imported directly by
step_message_save's own source):

    #. **Pydantic**: Used extensively for configuration management and data
       validation throughout the system. The ``StepMessageSaveConfig`` class and its nested
       configuration models rely on Pydantic's ``BaseModel`` for type-safe configuration
       loading, validation, and JSON schema generation.

    #. **step_cloud_schemas**: Provides standardized data schemas for ITS
       messages including CAM (Cooperative Awareness Messages), CPM (Cooperative
       Perception Messages) and DENM (Decentralized Environmental Notification
       Messages) identifiers, and the ``StepLogger`` logging utility.

    #. **step_lib**: Core library providing fundamental components including:

        * ``AsyncComManager``: Base class for asynchronous communication management
        * ``FacilityMessage``: ITS message handling and encoding/decoding functionality
        * MQTT utilities including ``MqttQoS`` enumerations
        * TLS/SSL security parameter management

    #. **paho-mqtt**: Imported directly in ``StepBroker`` (``ReasonCode``,
       ``SubscribeOptions``) to build MQTT subscription options and interpret SUBACK reason
       codes.

    #. **python-dotenv**: Used by ``MessageSaveApp._get_mqtt_credential()`` in
       ``message_save_app.py`` to load
       the MQTT connection secrets from a ``.env`` file.

    #. **gpx**: Used by ``GpxWriter`` to build and write GPX documents (tracks,
       segments, track points and their extensions).

**Transitive Dependencies Used Indirectly** (not imported by step_message_save's own source,
but relied upon underneath a direct dependency):

    #. **aiomqtt**: Asynchronous MQTT client library with TLS support, used by
       ``step_lib.AsyncComManager`` to implement the actual MQTT connection; step_message_save
       never imports it directly.

This library ecosystem enables STEP Message Save to provide a comprehensive, type-safe,
and highly configurable solution for capturing ITS message traffic within the STEP platform.

Components
----------

The architecture follows a modular design pattern that separates concerns between MQTT
communication, message persistence, and configuration management. This enables flexibility
and maintainability in the system design.

Main Components:

    #. **StepBroker**: Gateway class for MQTT communication with the STEP broker
    #. **Message Pipeline** (``MessageSaveApp`` in ``message_save_app.py``): The
       receiver/writer tasks and the
       ``asyncio.Queue`` connecting them; this is the part of the application that
       actually reads from ``StepBroker`` and appends to the output file
    #. **AppRunner**: Entry-point helper (from the ``step_cloud_schemas`` library)
       that owns the event loop and stops the message pipeline cooperatively on a
       shutdown signal
    #. **StepMessageSaveConfig**: Configuration management for the client
    #. **MQTT Credential Loading** (``MessageSaveApp._get_mqtt_credential()`` in
       ``message_save_app.py``):
       Reads the MQTT broker connection secrets from environment variables
    #. **StepLogger**: Logging utilities used by the client (from the
       ``step_cloud_schemas`` library)
    #. **StepException**: Custom exceptions for error handling
    #. **File Conversion**: ``FileConverter`` with the pluggable ``FileLoader`` and
       ``FileWriter`` subclasses, used by the ``-f``/``-x``/``-o`` command-line options

StepBroker
^^^^^^^^^^

The ``StepBroker`` (STEP Gateway) is a core component of the STEP Message Save architecture
that manages MQTT communication with the STEP broker. Extending the ``AsyncComManager`` class,
it provides an asynchronous interface for secure, reliable message reception from the
STEP ecosystem.

Key responsibilities of ``StepBroker`` include:

    #. **MQTT Connection Setup**: Configures TLS/SSL parameters (when
       ``mqttClient.sslEnable`` is set) and the underlying MQTT v5 connection settings
       for the lifetime of the ``async with StepBroker(...)`` block. ``StepBroker``
       itself has no self-reconnect logic; reconnection after a lost connection is
       handled by the application loop in ``message_save_app.py`` (see `Message Pipeline`_
       below), which discards the broker and constructs a new one after waiting
       ``reconnectInterval`` seconds.
    #. **Topic Subscription**: ``subscribe_execution()`` subscribes to the topics
       configured in ``mqttProtocol.subscriptionTopics`` with a fixed set of MQTT
       options (configured QoS, ``noLocal=False``, ``retainAsPublished=False``,
       ``retainHandling=RETAIN_DO_NOT_SEND``) and raises ``StepMessageSaveError`` if the
       number of results doesn't match the number of topics or if any granted QoS
       doesn't match the one requested.
    #. **ITS Message Access**: Exposes received messages through the inherited
       ``its_messages`` property. Each access returns a new ``ItsMessagesIterator``
       that decodes raw MQTT payloads into ``step_lib.FacilityMessage`` objects, but
       every iterator wraps the *same* underlying incoming-message queue of the
       single MQTT connection — it is a "dynamic view", not an independent stream.
    #. **Context Management**: Implements asynchronous context management through an
       overridden ``__aenter__`` (which delegates to the parent and returns ``self``)
       and the inherited ``__aexit__``, for clean resource handling.

``StepBroker`` is receive-only in this application: ``publish_topics_params`` is never
configured, so the inherited ``publish_its_message()`` would just log a warning and
return if it were ever called, and it never is. The class uses asynchronous patterns
throughout to ensure non-blocking operations, making it suitable for high-throughput
messaging environments in ITS applications.

Message Pipeline
^^^^^^^^^^^^^^^^

The message pipeline is implemented entirely by the ``MessageSaveApp`` class of
``message_save_app.py``, the ``AbstractApp`` workload that ``main()`` hands to
``AppRunner``, on top of the ``StepBroker`` instance and the configuration;
``StepBroker`` itself never touches the queue or the output file. Its constants and
coroutines are private members of the class. It is composed of:

    #. **STEP receiver tasks**: ``config.stepReceiverNumber`` instances of
       ``_step_receive_run()`` are started concurrently in a single ``TaskGroup``, all
       sharing the *same* ``StepBroker`` instance. Each task loops
       ``async for message in step_broker.its_messages`` and puts
       ``message.its_payload.to_json(indent=None)`` onto a shared, bounded
       ``asyncio.Queue[str]``. Because every ``ItsMessagesIterator`` returned by
       ``its_messages`` wraps the same underlying MQTT incoming-message queue, the N
       tasks act as competing consumers (a worker pool) over one physical connection's
       message stream, rather than each receiving an independent copy of all traffic.
    #. **The queue**: A single ``asyncio.Queue[str]``, sized by
       ``config.maxFileWriterQueueRooms``, decouples the receiver tasks from the file
       writer task. It is created once by ``MessageSaveApp.__init__()`` before the
       reconnect loop starts, and that same instance is shared across every reconnect cycle — a
       message already queued when a connection drops is not discarded, it is simply
       drained by the writer task started on the next cycle. A message is only lost if
       a receiver task is cancelled while blocked handing it off to a full queue, or if
       the writer fails to write it to disk.
    #. **The file writer task**: The output file (``config.outputFile``) path is
       resolved once by ``MessageSaveApp.__init__()`` before the reconnect loop starts,
       but the
       file itself is opened, in append mode, by ``_step_message_write_run()`` — once
       per connection cycle, since exactly one instance of that task is (re)started
       per cycle. Append mode means a reconnect, or even a full process restart, never
       truncates the file: messages already on disk are always preserved. Each writer
       instance loops forever, dequeuing one JSON string at a time, writing it followed
       by a newline, and closing the file when the task is cancelled at the end of that
       cycle. Because only one writer task is ever active at a time, writes are
       naturally serialized without a lock. Writes are buffered and are not explicitly
       flushed after each message — they reach disk once the buffer fills or the file
       is closed.
    #. **The reconnect loop**: ``MessageSaveApp.work()`` creates the directory of the
       output file, then awaits ``_step_broker_run()``, which wraps broker creation, subscription, and the
       receiver/writer ``TaskGroup`` in a ``while True`` loop. If an unhandled
       exception propagates out of the broker/task-group block (e.g. a lost MQTT
       connection), it is logged, the broker and all receiver/writer tasks are torn
       down as the ``async with``/``TaskGroup`` blocks exit, the loop sleeps
       ``config.reconnectInterval`` seconds, and then it reconnects by constructing a
       brand-new ``StepBroker`` and starting a fresh ``_step_message_write_run()`` task
       — which reopens the *same* output file in append mode — against the *same*
       shared queue.
    #. **The graceful shutdown**: ``AppRunner`` (from ``step_cloud_schemas``) runs
       ``MessageSaveApp.work()`` as a task of its own ``TaskGroup`` and, on a shutdown
       signal (``SIGINT``/``SIGTERM`` on POSIX, ``SIGINT``/``SIGBREAK`` on Windows),
       cancels it
       wherever ``_step_broker_run()`` is (connecting, subscribing, running its tasks
       or waiting to reconnect), so ``StepBroker`` disconnects cleanly even while the
       broker is unreachable. Once the group has unwound, ``AppRunner`` calls
       ``MessageSaveApp.on_shutdown()``, whose ``_drain_queue()`` appends the messages
       still queued to the output file, and the program exits with
       ``ExitCode.ABORTED``. See `AppRunner`_ below.

AppRunner
^^^^^^^^^

``AppRunner`` is provided by the ``step_cloud_schemas`` library (not implemented within
step_message_save itself). It owns the process-wide plumbing of the entry point: the
``asyncio.Runner`` and its event loop, the loop exception handler,
``sys.unraisablehook``, the shutdown signal handlers and the shutdown watcher.
step_message_save only supplies the workload, as the ``MessageSaveApp`` subclass of
``AbstractApp[ExitCode]``:

    * ``work()``: the coroutine run by ``AppRunner``; it creates the directory of the
      output file and awaits the reconnect loop, so it never returns on its own.
    * ``on_shutdown(stop_signal)``: called by ``AppRunner`` once a shutdown signal has
      stopped ``work()``; it drains the queue to the output file and returns
      ``ExitCode.ABORTED``.

``AppRunner`` is generic in the result type: step_message_save uses
``AppRunner[ExitCode]``, so ``AppRunner.run()`` returns the ``ExitCode`` that ``main()``
turns into the process exit code.

How ``main()`` uses it:

    #. **Construction first**: ``main()`` builds the ``AppRunner`` before parsing the
       command line. The constructor installs the process-wide hooks (the signal
       handlers and ``sys.unraisablehook``), so they cover the whole run, including
       the file conversion and the configuration loading. ``AppRunner`` is a
       singleton: it is constructed once, from the main thread.
    #. **Loop factory**: on Windows ``main()`` passes ``asyncio.SelectorEventLoop`` as
       ``loop_factory``; on the other platforms the asyncio default loop is used.
    #. **Run**: once the configuration is loaded and the ``MessageSaveApp`` is built,
       ``main()`` calls ``app_runner.run(app=app)``, which runs
       ``MessageSaveApp.work()`` on a new event loop.
    #. **Shutdown**: on a shutdown signal (``SIGINT``/``SIGTERM`` on POSIX,
       ``SIGINT``/``SIGBREAK`` on Windows) ``AppRunner`` cancels ``work()`` wherever
       it is. Once every task has unwound, hence once the writer task has closed the
       output file and ``StepBroker`` has disconnected, ``AppRunner`` calls
       ``MessageSaveApp.on_shutdown()`` and returns its result.

The outcome of a run maps to the exit codes as follows:

    * **Shutdown signal during the run**: ``on_shutdown()`` returns
      ``ExitCode.ABORTED``.
    * **Exception raised by** ``work()``: it is not caught by ``AppRunner``; it leaves
      ``run()`` wrapped in an ``ExceptionGroup``, ``on_shutdown()`` is not called, and
      the top-level ``except Exception`` of ``main()`` logs it and returns
      ``ExitCode.ERROR``. Since the reconnect loop retries after any exception, this
      only happens when the directory of the output file cannot be created.
    * **Signal outside the run** (before ``run()`` has started the event loop, or
      after it has returned): ``KeyboardInterrupt`` is raised, which ``main()`` maps
      to ``ExitCode.ABORTED``.

StepMessageSaveConfig
^^^^^^^^^^^^^^^^^^^^^

The ``StepMessageSaveConfig`` component is responsible for configuration management in the
STEP Message Save architecture. Built as a Pydantic ``BaseModel``, it provides a robust,
type-safe mechanism for loading, validating, and accessing configuration settings
throughout the application.

Key features of ``StepMessageSaveConfig`` include:

    #. **JSON Configuration Loading**: Loads configuration settings from a JSON file specified
       at startup, providing a centralized source of configuration for all components.
    #. **Type Validation**: Leverages Pydantic's validation system to ensure all configuration
       values meet the expected types and constraints, preventing configuration errors at runtime.
    #. **Hierarchical Structure**: Organizes configuration in a hierarchical manner, with nested
       models for different aspects of the system:

        * MQTT Client configuration (connection parameters, security settings)
        * MQTT Protocol configuration (QoS, subscription topic management)
        * Logging configuration (handlers, levels, formatting)

    #. **Immutable Configuration**: Once loaded at startup, the configuration becomes immutable,
       ensuring consistency throughout the application's lifecycle.
    #. **Output and Concurrency Settings**: Carries the output file path
       (``outputFile``), the number of concurrent STEP receiver tasks
       (``stepReceiverNumber``), and the maximum size of the file writer queue
       (``maxFileWriterQueueRooms``).
    #. **Default Configuration**: Provides ``get_default()`` methods to generate sensible
       default configurations when specific values are not provided.
    #. **JSON Schema Generation**: Supports generating JSON schemas for configuration
       validation through the ``_ConfigGenerateJsonSchema`` utility class.

The design of ``StepMessageSaveConfig`` emphasizes immutability and strong validation, helping
prevent configuration-related issues during runtime while providing a clear, structured
approach to configuration management.

MQTT Credential Loading
^^^^^^^^^^^^^^^^^^^^^^^

MQTT broker connection secrets are kept out of the (persisted) JSON configuration
file and are instead read from the process environment by
``MessageSaveApp._get_mqtt_credential()`` in ``message_save_app.py``, which is called
once by ``MessageSaveApp.__init__()``, when ``main()`` builds the application right
after the logger is set up and before ``AppRunner.run()`` is started.

Key aspects of this component:

    #. **``.env`` File Support**: Calls ``load_dotenv()`` (from ``python-dotenv``)
       before reading any variable, so the values may come from a ``.env`` file in
       the working directory or from variables already present in the process
       environment.
    #. **Required Variables**: Reads ``MQTT_URL`` and ``MQTT_PORT`` (the
       ``_MQTT_URL_VAR_NAME``/``_MQTT_PORT_VAR_NAME`` class constants); if either is
       unset,
       ``_get_mqtt_credential()`` raises ``ValueError``, which propagates up and is
       caught by the top-level exception handling in ``main()``.
    #. **Optional Variables**: Reads ``MQTT_USERNAME`` and ``MQTT_PASSWORD``
       (``_MQTT_USERNAME_VAR_NAME``/``_MQTT_PASSWORD_VAR_NAME``); both may be absent,
       in which case the broker connection is attempted without authentication.
    #. **MqttCredential**: The four values are assembled into an
       ``MqttCredential`` ``NamedTuple`` (defined in ``step_message_save_config.py``),
       kept separate from ``StepMessageSaveConfig`` specifically so secrets never end
       up embedded in the configuration document. The resulting instance is kept
       by ``MessageSaveApp`` and handed to every ``StepBroker`` it builds, which uses
       it to authenticate the MQTT connection.
    #. **Startup Logging**: Once loaded, the resolved host, port, and username (but
       never the password) are logged at INFO level for diagnostic purposes.

StepLogger
^^^^^^^^^^

``StepLogger`` is provided by the ``step_cloud_schemas`` library (not implemented within
step_message_save itself) and is used by STEP Message Save to build and configure its
``logging.Logger`` instances. Today it is a thin factory built directly on top of
Python's standard ``logging`` module; a future revision is expected to move the
underlying implementation to the ``loguru`` library while keeping the same
``StepLogger`` interface used by step_message_save.

Key features of ``StepLogger`` include:

    #. **Multiple Handler Types**: Builds loggers with one or more of the following
       handlers, each independently configurable via ``LogConfig``:

        * ``stream``: writes to stderr
        * ``null``: discards all log records
        * ``file``: writes to a single log file (append or overwrite)
        * ``sizeFileRotate``: rotates the log file once it exceeds a configured size
        * ``timeFileRotate``: rotates the log file at a configured time interval

       Rotated log files are automatically compressed with BZIP2. There is no syslog
       handler.
    #. **UTC Timestamp Formatting**: Uses a custom ``UtcFormatter`` so all log
       timestamps are rendered in UTC regardless of the local system timezone.
    #. **Log Level Management**: Supports the standard log levels (DEBUG, INFO,
       WARNING, ERROR, CRITICAL) per handler and a global logger level, via
       ``LogMode``.
    #. **Configuration Integration**: Driven by the ``LogConfig``/``LogHandlerConfig``
       models (from ``step_cloud_schemas``), which are carried inside
       ``StepMessageSaveConfig.log``.
    #. **Public API**: Exposes two classmethods:

        * ``get_logger(name, config, instance_name)``: builds and returns a configured
          ``Logger``. If ``config`` is ``None``, it falls back to a single stderr
          stream handler at WARNING level with the logger itself at INFO. File-based
          handlers require ``instance_name`` to build the log filename, and raise
          ``ValueError`` if it is missing.
        * ``logger_force_write(logger, msg)``: temporarily elevates the logger and all
          its handlers to INFO to guarantee a message is emitted (used by step_message_save
          for startup/version banners), then restores the original levels.

There is currently no built-in support for syslog, or for attaching structured
context such as component IDs or transaction IDs to log records beyond what the
configured format string exposes (e.g. ``%(module)s``, ``%(funcName)s``).

StepException
^^^^^^^^^^^^^

step_message_save defines a minimal exception hierarchy in ``step_exception.py``, used to
distinguish STEP Message Save errors from other unhandled exceptions:

    #. **StepMessageSaveError**: Base exception for the client. A plain subclass of
       ``Exception`` with no additional attributes; it is raised, for example, by
       ``StepBroker.subscribe_execution()`` when a topic subscription fails or its
       returned QoS doesn't match the configured one.
    #. **StepCliError**: Subclass of ``StepMessageSaveError`` raised for CLI-specific
       errors in ``main()`` — such as passing ``-c/--config`` without ``-i/--instance``
       or vice versa, or ``-x/--convert`` without ``-f/--file``. ``main()`` maps it to
       ``ExitCode.USAGE``.
    #. **LoaderError**: Raised by a ``FileLoader`` when its input file does not match,
       or cannot be parsed as, its format, and by ``FileConverter`` when no loader
       accepts the input file.
    #. **WriterError**: Raised by a ``FileWriter`` when its output file cannot be
       written, and by ``FileConverter`` when the output directory cannot be created.

``main()`` maps ``LoaderError`` and ``WriterError`` to ``ExitCode.ERROR``, logging only
the message, without a traceback.

All classes are message-only exceptions (the message is carried via the standard
``Exception`` args, not a dedicated attribute); there is no structured error context,
error-type classification, or recovery-hint mechanism beyond what the raised message
string conveys. Callers catch and log these via the standard Python exception handling
already used throughout the application (e.g. the top-level ``except`` clauses in
``main()`` and the ``except*`` clause of the reconnect loop in
``MessageSaveApp._step_broker_run()``).

File Conversion
^^^^^^^^^^^^^^^

The file conversion is independent of the MQTT client: it runs offline, before the
client is started, when ``-f``/``--file`` is given. It is built on three components:

    #. **FileLoader** (``loaders/file_loader.py``): Abstract base class of the loaders.
       A loader is a stateless, callable parser for one format: given a file path, it
       returns the ``list[FacilityMessage]`` the file contains, or raises
       ``LoaderError`` if the file does not match its format. The handled extension is
       declared in the ``EXTENSION`` class attribute, checked by ``__init_subclass__``
       when the subclass is defined. The protected ``_build_cam_data()`` helper builds
       a ``CamDataV1`` from scalar trajectory values. Concrete loaders:

        * ``JsonlLoader`` (``.jsonl``): one ``ItsMessageRoot`` (CAM, CPM, DENM) per line
        * ``PickleActorLoader`` (``.pkl``): vehicle trajectories, one CAM per point

    #. **FileWriter** (``writers/file_writer.py``): Abstract base class of the writers,
       the inverse of a loader: given a file path and a ``list[FacilityMessage]``, it
       writes the messages it can represent, or raises ``WriterError``. Concrete
       writers:

        * ``GpxWriter`` (``.gpx``): one track per station, built from the CAM messages
          with a position, in the track format read by step_publisher_pkl

    #. **FileConverter** (``file_converter.py``): Chains a loader and a writer. The
       input format is deduced from the file: the loaders owning the input file
       extension are tried first, then all the others, and the first one that does
       not raise ``LoaderError`` wins. The output format is selected by name (the
       writer's extension without the dot). It also resolves the output file path and
       creates its missing directories, only after the input file has been loaded.

The loader and writer classes used by the command line are listed in the
``CONVERSION_LOADERS`` and ``CONVERSION_WRITERS`` constants of ``__main__.py``; the
``-x``/``--convert`` choices are derived from ``CONVERSION_WRITERS``. See
:doc:`loaders_writers` for how to add a new format.

Sequence Diagram
----------------

The sequence diagram below illustrates the single message flow implemented by
STEP Message Save: receiving ITS messages from the STEP broker and appending them to the
output file. It reflects the actual implementation in ``message_save_app.py``, where
``config.stepReceiverNumber`` concurrent ``_step_receive_run()`` tasks share a single
``StepBroker`` instance and compete for messages from its single underlying MQTT
connection, feeding a bounded ``asyncio.Queue`` that a single
``_step_message_write_run()`` task drains, owning the output file exclusively.

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      @startuml

      participant "STEP MQTT Broker" as MQTT
      participant "StepBroker" as Gateway
      participant "Receiver Task 1" as Recv1
      participant "Receiver Task N" as RecvN
      queue "asyncio.Queue" as Q
      participant "File Writer Task" as Writer
      database "Output File" as File

      Gateway -> MQTT : SUBSCRIBE (topics, QoS)
      MQTT --> Gateway : SUBACK

      note over Recv1, RecvN
         Both tasks loop
         "async for message in step_broker.its_messages".
         Every its_messages access wraps the same
         underlying incoming-message queue of the one
         MQTT connection, so the tasks are competing
         consumers, not independent subscriptions.
      end note

      loop until cancelled
         MQTT -> Gateway : PUBLISH (topic, ITS_bytes, QoS)
         Gateway -> Gateway : Decode ITS ASN.1 to FacilityMessage
         note over Gateway
            Use step_lib.FacilityMessage
            for decoding
         end note
         alt delivered to Receiver Task 1
            Gateway -> Recv1 : its_payload
            Recv1 -> Recv1 : its_payload.to_json()
            Recv1 -> Q : put(json_line)
         else delivered to Receiver Task N
            Gateway -> RecvN : its_payload
            RecvN -> RecvN : its_payload.to_json()
            RecvN -> Q : put(json_line)
         end
      end

      loop until cancelled
         Writer -> Q : get()
         Writer -> File : write(json_line + "\n")
         note over Writer
            Each writer task opens
            the file itself, in
            append mode, once per
            connection cycle, so a
            reconnect or restart
            never truncates it.
            Writes are buffered and
            not flushed per message
         end note
      end

      @enduml

On an unmanaged exception (e.g. a lost MQTT connection), the exception propagates out of
the ``async with StepBroker(...)``/``TaskGroup`` block in
``MessageSaveApp._step_broker_run()``, tearing down the current broker and all receiver/writer tasks. The reconnect loop then waits
``reconnectInterval`` seconds and retries the whole connect-subscribe-receive cycle with a
brand-new ``StepBroker`` instance. The new writer task reopens the output file in append
mode, so messages persisted before the drop are not lost, and drains the shared queue,
so messages queued before the drop are not lost either.
