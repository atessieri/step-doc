=====================
STEP Connection Guide
=====================

This guide explain how to use the STEP Library to communicate to STEP broker using both asynchronous 
(Coroutine) and synchronous (Non-blocking) approaches.

-------------
Prerequisites
-------------

Before using STEP Library, ensure you have:

- Python 3.11 or higher
- STEP Library installed
- Valid STEP broker credentials

--------------
Basic Concepts
--------------

The main features of the STEP Library include:

    #. Publish ITS Etsi messages to the broker (STEP).
    #. Subscribe to the specific topics in order to receive ITS Etsi messages.

The library supports CAM, CPM and DENM messages.

The library provides two main approaches for MQTT communication:

    #. Synchronous (Non-blocking) using ``SyncComManager``
    #. Asynchronous (Coroutine) using ``AsyncComManager``

It is recommended to provide a *cache* folder during the initialization of the library
for performance reason. 
This folder is used to store the ASN.1 information used during the parsing of the messages.
No any part of the message is stored in the cache folder.

The information in the message is encapsulated and passed to the library using:

    #. The class
    #. A dictionary
    #. A JSON string

The communication session is managed with or without the context manager.

Synchronous Usage
-----------------

The synchronous *Non-blocking* approach uses an transfer thread that manages the communication.
The library create a message FIFO queue to avoid any block due to transmission / reception delay.

Configuration
-------------

The following snippet explains how to create the data-class of parameters.

.. code-block:: python

    import logging
    import ssl

    from aiomqtt import TLSParameters
    from step_cloud_schemas import GenericMessageType, MessageId
    from step_lib import MqttQoS, PublishTopicParams, SyncComManagerParams

    def create_sync_com_manager_params() -> SyncComManagerParams:
        tls_params = TLSParameters(
            ca_certs=None,
            certfile=None,
            keyfile=None,
            cert_reqs=ssl.VerifyMode.CERT_REQUIRED,
            tls_version=ssl.PROTOCOL_TLSv1_2,
            ciphers=None,
            keyfile_password=None,
        )
        return SyncComManagerParams(
            instance_name="step_lib_test_1",
            host="step.example.com",
            port=8883,
            username="your_username",
            password="your_password",
            station_id=123,
            timeout=10,
            keepalive=30,
            bind_address="",
            bind_port=0,
            clean_start=True,
            queue_type=None,
            max_queued_incoming_messages=60,
            max_queued_outgoing_messages=60,
            max_inflight_messages=60,
            max_concurrent_outgoing_calls=60,
            tls_params=tls_params,
            proxy=None,
            socket_options=None,
            session_expiry=0,
            receive_maximum=10,
            maximum_packet_size=4096,
            topic_alias_maximum=0,
            publish_topics_params=[
                PublishTopicParams(
                    message_type=MessageId.CAM_PDU,
                    header_topic="v2x/cam/264421_4",
                    geohash_precision=8,
                    qos=MqttQoS.QOS_0,
                ),
                PublishTopicParams(
                    message_type=MessageId.CPM_PDU,
                    header_topic="v2x/cpm/264421_4",
                    geohash_precision=8,
                    qos=MqttQoS.QOS_0,
                ),
                PublishTopicParams(
                    message_type=GenericMessageType.POSITION_DATA,
                    header_topic="TRIP_SIMULATOR",
                    geohash_precision=8,  # ignored for POSITION_DATA
                    qos=MqttQoS.QOS_0,
                ),
            ],
            cache_dir="./.cache",
            reconnect_interval=2,
            max_incoming_queue_rooms=60,
            max_outgoing_queue_rooms=60,
            publish_worker_count=2,
            publish_worker_startup_timeout=30.0,
            publish_hwm=2000,
            publish_health_check_interval=1.0,
            publish_heartbeat_interval=0.5,
            publish_heartbeat_timeout=30.0,
            publish_parent_watchdog_interval=1.0,
            publish_graceful_shutdown_timeout=5.0,
            publish_forceful_join_timeout=5.0,
            publish_max_connect_attempts=5,
        )

.. note::

    The ``station_id`` field can be None if the library is able to send messages created
    by different stations. If ``station_id`` is None, it isn't used; otherwise, the
    library discards received messages carrying ``station_id`` (the client's own
    echoes) and replaces the station id of the published messages with it. The
    override is performed by ``AsyncComManager.publish_its_message`` (called by the
    publish worker of ``SyncComManager``), before serialization and before the
    position data topic is built; ``FacilitySerializer`` encodes the message's
    station id as is.

.. note::

    The ``GenericMessageType.POSITION_DATA`` entry of ``publish_topics_params`` is
    optional and enables the STEP position data feed: every published CAM is also
    projected onto a ``PositionDataV1`` record and published as JSON on
    ``<header_topic>/<station_id>``, with no geohash levels (``geohash_precision`` is
    ignored for this entry). Without the entry, the CAM is published alone. See
    :doc:`position_data_topic`.

.. note::

    ``SyncComManager`` publishes through a pool of worker processes rather than
    on the calling thread. The ``publish_worker_*`` and ``publish_*`` fields tune
    that pool:

        - ``publish_worker_count``: number of publish worker processes to spawn.
        - ``publish_worker_startup_timeout``: seconds to wait for a spawned worker
          to signal readiness before treating it as failed.
        - ``publish_hwm``: high-water mark for the worker pool's ZMQ PUSH socket.
        - ``publish_health_check_interval``: seconds between periodic worker
          health checks.
        - ``publish_heartbeat_interval``: seconds between worker heartbeat
          refreshes.
        - ``publish_heartbeat_timeout``: seconds of heartbeat staleness after
          which a worker is considered blocked; keep it well above the time a
          worker needs to compile the ASN.1 grammar on its first connect.
        - ``publish_parent_watchdog_interval``: seconds between a worker's checks
          that its parent process is still alive.
        - ``publish_graceful_shutdown_timeout``: bound of each of the two phases
          of a graceful stop: handing the queued messages to the workers, then
          letting every worker publish the messages it already received (drain)
          before exiting. ``stop()`` can therefore wait about twice this value
          before escalating to a forceful termination. If this manager runs inside
          a container/service manager, keep that (plus
          ``publish_forceful_join_timeout``) safely below the manager's own outer
          shutdown grace period.
        - ``publish_forceful_join_timeout``: seconds to wait for a
          forcefully-terminated worker to exit before escalating further.
        - ``publish_max_connect_attempts``: consecutive failed MQTT connect
          attempts a worker tolerates before giving up and exiting, to be picked
          up and restarted by the pool's health check, rather than retrying
          forever. A worker whose restart fails is retried after 1 s, then after
          2, 4, ... seconds, up to 60 s between attempts.
        - ``leap_seconds_source``, ``leap_seconds_urls``,
          ``leap_seconds_allow_download``: configuration of the ``LeapSeconds``
          singleton of each publish worker process (see
          :ref:`step_lib_leap_seconds`).

    Every field must be picklable, since the parameters are sent to the worker
    processes: an unpicklable value (e.g. a ``queue_type`` defined inside a
    function) raises ``ValueError`` naming the field.

.. _step_lib_tls:

TLS configuration
-----------------

TLS is configured only through ``tls_params`` (an ``aiomqtt.TLSParameters``,
re-exported as ``step_lib.TLSParameters``): an ``ssl.SSLContext`` cannot be pickled
to reach the publish worker processes, so the ``tls_context`` field was removed in
3.0.0. Each process builds its own context from the parameters. To migrate a
hand-built ``SSLContext``:

.. list-table::
   :header-rows: 1

   * - From a hand-built ``SSLContext``
     - To ``TLSParameters``
   * - ``load_verify_locations(cafile)``
     - ``ca_certs`` (None uses ``load_default_certs()``)
   * - ``verify_mode=CERT_NONE`` and ``check_hostname=False``
     - ``cert_reqs=ssl.CERT_NONE``
   * - certificate verification enabled
     - ``cert_reqs=None`` (the default, ``CERT_REQUIRED``)
   * - ``load_cert_chain(certfile, keyfile, password)``
     - ``certfile``, ``keyfile``, ``keyfile_password``
   * - ``minimum_version=TLSv1_2``
     - the default of Python 3.10 and later

.. _step_lib_leap_seconds:

Time scale and leap seconds
---------------------------

Since step_cloud_schemas 3.0.0 every ITS timestamp on the wire is TAI (5 seconds
ahead of UTC since the ITS epoch), while the ISO strings of the models stay UTC.
Every station of a deployment must therefore move to step_cloud_schemas 3.0.0 and
step_lib 3.0.0 together: a mixed deployment reads each other's times 5 s apart.

The leap-second table is a ``LeapSeconds`` singleton per process. The application
configures the singleton of its own process (the one running ``SyncComManager`` or
``AsyncComManager``) before any ``ItsTime`` use, e.g.::

    from step_cloud_schemas import LeapSeconds

    LeapSeconds(allow_download=False)

The publish worker processes do not inherit it: each one creates its own from the
``leap_seconds_source``, ``leap_seconds_urls`` and ``leap_seconds_allow_download``
parameters, as the very first thing it does.

Delivery and time notes
-----------------------

    - **At-least-once publishing**: a message whose publish fails with an MQTT
      transport error is published again after the worker reconnects, up to 3
      attempts, so a subscriber can receive it twice. The pending message lives only
      in the worker's memory.
    - **Graceful stop**: ``stop()`` publishes every message already handed to
      ``publish_its_message()`` before returning, within the time budget above.
    - **Sequence numbers**: the GeoNetworking sequence number is assigned by the
      pool, so the worker processes never reuse one; it starts at a random value.
    - **Times rebuilt on reception**: a CAM carries only
      ``generationDeltaTime`` (TAI ms modulo 65536), and the GeoNetworking position
      vector ``TST`` (TAI ms modulo 2^32). Both are rebuilt against the time of
      decoding, so ``creationTime`` is only right when a CAM is decoded within
      +/-32.7 s of its generation (+/-24.8 days for ``TST``); replaying an old
      capture shifts the times.
    - **Standard CPM**: only the custom CPM layout (``CpmMessageV1`` with
      ``is_custom=True``, BTP port 1009) is supported. Publishing a standard CPM
      raises ``StepLibUnsupportedMessageError`` at once; a standard CPM received on
      port 2009 is dropped with an INFO record.

Using Context Manager (Recommended)
-----------------------------------

The context manager can manage resource cleanup automatically. So is recommended.
The following snippet of code:
    
    #. Creates a SyncComManager instance (client) managed by Context Manager
    #. Subscribes to the topics
    #. Publishes CAM, CPM and DENM messages
    #. Processes the received messages in the queue

.. note::

    Subscriptions always use ``noLocal=False``, which MQTT v5 requires for shared
    subscriptions: a ``$share/<group>/<filter>`` topic is passed to the broker
    unchanged, and the broker then delivers each message to one member of the group.
    For example, several processes can split the CAM traffic between them with::

        client.subscribe(topics=["$share/cam_readers/v2x/cam/#"], max_qos=MqttQoS.QOS_1)

    The messages a manager publishes on a topic it is subscribed to are received
    back, unless ``station_id`` is set: the receiver then drops them as echoes. With
    ``station_id=None`` ``subscribe()`` logs this at INFO.

    ``subscribe()`` returns once the command is queued; the SUBACK is logged later by
    the background thread: INFO when the requested QoS was granted, WARNING when the
    broker granted a lower QoS (the subscription works, with weaker delivery
    guarantees), ERROR with the reason (e.g. ``Not authorized``) when it was refused.

Receive Example
---------------

The function to receive messages is Non-blocking and can be used in a loop without 
timing penalty. The subscription is done during the initialization of the library.
The following example demonstrates how to receive a message using the STEP Library.

.. code-block:: python

    for message in client.its_messages_received:
        if logger.isEnabledFor(level=logging.INFO):
            logger.info(msg=f"Message received: {message}")

For more detailed information about specific message types and configurations,
refer to the API Reference section :ref:`step_lib_api`.

------------------
Asynchronous Usage
------------------

Asynchronous approach uses the coroutine feature (*asyncio* library in python).
The *asyncio* module provides tools for creating and managing asynchronous task and 
for developing non-blocking network communication.
In the asynchronous approach, only the communication using context manager is supported.

Configuration
-------------

The following snippet explains how to create the data-class of parameters and use
it to build a ready-to-use ``AsyncComManager`` instance.

.. code-block:: python

    import logging
    import ssl

    from aiomqtt import TLSParameters
    from step_cloud_schemas import GenericMessageType, MessageId
    from step_lib import AsyncComManager, AsyncComManagerParams, MqttQoS, PublishTopicParams

    def create_async_com_manager(logger: logging.Logger) -> AsyncComManager:
        tls_params = TLSParameters(
            ca_certs=None,
            certfile=None,
            keyfile=None,
            cert_reqs=ssl.VerifyMode.CERT_REQUIRED,
            tls_version=ssl.PROTOCOL_TLSv1_2,
            ciphers=None,
            keyfile_password=None,
        )
        params = AsyncComManagerParams(
            instance_name="step_lib_test_1",
            host="step.example.com",
            port=8883,
            username="your_username",
            password="your_password",
            station_id=123,
            timeout=10,
            keepalive=30,
            bind_address="",
            bind_port=0,
            clean_start=True,
            queue_type=None,
            max_queued_incoming_messages=60,
            max_queued_outgoing_messages=60,
            max_inflight_messages=60,
            max_concurrent_outgoing_calls=60,
            tls_params=tls_params,
            proxy=None,
            socket_options=None,
            session_expiry=0,
            receive_maximum=10,
            maximum_packet_size=4096,
            topic_alias_maximum=0,
            publish_topics_params=[
                PublishTopicParams(
                    message_type=MessageId.CAM_PDU,
                    header_topic="v2x/cam/264421_4",
                    geohash_precision=8,
                    qos=MqttQoS.QOS_0,
                ),
                PublishTopicParams(
                    message_type=MessageId.CPM_PDU,
                    header_topic="v2x/cpm/264421_4",
                    geohash_precision=8,
                    qos=MqttQoS.QOS_0,
                ),
                PublishTopicParams(
                    message_type=GenericMessageType.POSITION_DATA,
                    header_topic="TRIP_SIMULATOR",
                    geohash_precision=8,  # ignored for POSITION_DATA
                    qos=MqttQoS.QOS_0,
                ),
            ],
            cache_dir="./.cache",
        )
        return AsyncComManager(params=params, logger=logger)

.. note::

    The ``station_id`` field can be None if the library is able to send messages created
    by different stations. If ``station_id`` is None, it isn't used; otherwise, the
    library discards received messages carrying ``station_id`` (the client's own
    echoes) and ``publish_its_message`` replaces the station id of the message to
    publish with it, before serialization and before the position data topic
    ``<header_topic>/<station_id>`` is built.

.. note::

    Every exception raised by ``publish_its_message`` is a ``StepLibError``, so
    catching it is enough to log a message that was not sent: an MQTT transport
    failure is raised as ``StepLibMqttError`` (chaining the ``aiomqtt.MqttError``),
    and a message that fails ``MAX_TRANSMIT_ERRORS`` consecutive times as a
    ``StepLibError`` chaining the last error. The previous failures are logged by the
    library and the call returns normally. The connection (``async with``) and
    ``subscribe`` are inherited from ``aiomqtt.Client`` and still raise
    ``aiomqtt.MqttError``.
