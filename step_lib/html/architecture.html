Architecture

Overview

The step_lib package is a Python library designed for handling STEP (Safer Transport for Europe Platform) communications in Intelligent Transportation Systems (ITS). It provides a comprehensive solution for MQTT-based V2X (Vehicle-to-Everything) communication, supporting ITS message types including CAM (Cooperative Awareness Message), DENM (Decentralized Environmental Notification Message), and CPM (Collective Perception Message).

Key Features

  • Asynchronous and Synchronous Communication: Supports both async/await patterns and traditional synchronous communication

  • ITS Message Handling: Complete serialization/deserialization of ITS messages following ETSI standards

  • GeoNetworking Protocol: Full implementation of GeoNetworking layers (Basic, Common, Extended headers)

  • BTP Protocol: Basic Transport Protocol for ITS message routing

  • MQTT Integration: Built-in MQTT client with QoS support and automatic reconnection

  • ASN.1 Support: Complete ASN.1 encoding/decoding for ITS messages

Library Dependencies

Core Dependencies

The step_lib package relies on the following third-party libraries:

Communication & Messaging

  • aiomqtt (>=2.5.0, <3.0): Asynchronous MQTT client implementation

    • Provides async MQTT v5 protocol support

    • Used by AsyncComManager for non-blocking communication

    • Handles message queuing and topic subscriptions

Data Encoding & Serialization

  • asn1tools (>=0.167.0, <1.0): ASN.1 compiler and encoder/decoder

    • Compiles ASN.1 schema files from ETSI ITS standards

    • Encodes/decodes CAM, DENM, and CPM messages using UPER (Unaligned Packed Encoding Rules)

    • Used by FacilitySerializer for message transformation

  • bitstring (>=4.3.1, <5.0): Binary data manipulation library

    • Handles bit-level operations for protocol headers

    • Used in GeoNetworkAddress and PositionVector for precise binary field packing

    • Enables compact representation of protocol flags and identifiers

Geospatial & Caching

  • pygeohash (>=3.2.2, <4.0): Geohash encoding for geographic locations

    • Converts GPS coordinates to geohashes for topic organization

    • Enables geographic-based MQTT topic routing

    • Used in AsyncComManager for location-aware message distribution

  • diskcache (>=5.6.3): Persistent disk-based caching

    • Caches compiled ASN.1 schemas for performance optimization

    • Reduces startup time by avoiding repeated schema compilation

    • Used by FacilitySerializer when cache_dir is specified

Schema Validation

  • step_cloud_schemas (>=1.2.29, <2.0): STEP project schema definitions

    • Provides Pydantic models for ITS message validation

    • Contains JSON schemas for CAM, DENM, and CPM messages

    • Defines common data types (ItsTime, ReferencePosition, TrafficParticipantType)

    • Enables bidirectional conversion between ASN.1 and JSON formats

Standard Library Usage

The package also extensively uses Python’s standard library:

  • asyncio: Event loop management, tasks, and queues for async operations

  • threading: Thread management for SyncComManager background operations

  • queue: Synchronous queue for message passing between threads

  • dataclasses: Immutable data structures for protocol messages

  • logging: Comprehensive logging throughout the library

  • ssl: TLS/SSL support for secure MQTT connections

  • io.BytesIO: Efficient binary stream operations for serialization

  • enum: Type-safe enumerations for protocol constants

Component Architecture

The step_lib package is organized into several layers, each with specific responsibilities:

  1. Communication Layer

    • Handles MQTT broker connections (async and sync)

    • Manages message publishing and subscription

    • Implements automatic reconnection logic

    • Provides thread-safe message queuing

  2. Serialization Layer

    • Converts between ITS messages and binary formats

    • Manages protocol stack (GeoNetworking + BTP + Facility)

    • Handles ASN.1 encoding/decoding

    • Caches compiled ASN.1 schemas

  3. Facility Layer

    • Implements ITS message types (CAM, DENM, CPM)

    • Provides format conversions (ASN.1, JSON, dict)

    • Validates message structures

    • Manages message metadata (time, position, station ID)

  4. GeoNetworking Layer

    • Implements geographic addressing

    • Manages packet headers (Basic, Common, Extended)

    • Handles position vectors and location data

    • Supports various routing modes (single-hop, anycast, broadcast)

  5. BTP Layer

    • Implements Basic Transport Protocol

    • Maps message types to well-known ports

    • Supports BTP-A and BTP-B message types

The ITS message processing follows a layered architecture similar to the OSI model:

Message Structure

An ITS message transmitted over MQTT consists of three protocol layers:

┌──────────────────────────────────────────────────────────────┐
│                      MQTT Message                            │
├──────────────────────────────────────────────────────────────┤
│ Topic: /v2x/cam/u33dbw7g (with geohash)                      │
│ Payload:                                                     │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ GeoNetworking Layer (12-40+ bytes)                     │  │
│  │  ├─ Basic Header (4 bytes)                             │  │
│  │  │  - Version, Next Header, Lifetime, Hop Limit        │  │
│  │  ├─ Common Header (8 bytes)                            │  │
│  │  │  - Header Type, Traffic Class, Payload Length       │  │
│  │  └─ Extended Header (variable)                         │  │
│  │     - Position Vector (Source location, speed, etc.)   │  │
│  │     - Destination area (for geo-broadcast)             │  │
│  ├────────────────────────────────────────────────────────┤  │
│  │ BTP Layer (4 bytes)                                    │  │
│  │  - Source Port / Destination Port (BTP-A)              │  │
│  │  - OR Destination Port / Port Info (BTP-B)             │  │
│  │  - Port mapping: CAM=2001, DENM=2002, CPM=2009         │  │
│  ├────────────────────────────────────────────────────────┤  │
│  │ Facility Layer (variable, typically 100-500 bytes)     │  │
│  │  - ASN.1 UPER encoded ITS message                      │  │
│  │  - CAM: Vehicle state, position, speed, heading        │  │
│  │  - DENM: Event notification, hazard information        │  │
│  │  - CPM: Perceived objects, sensor data                 │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘

Protocol Layer Details

GeoNetworking Layer Responsibilities:

  • Geographic addressing and routing

  • Packet lifetime management

  • Hop limit control

  • Traffic class prioritization

  • Source position vector (GPS, speed, heading)

  • Destination area specification (for broadcasts)

BTP Layer Responsibilities:

  • Port-based message type identification

  • Interactive (BTP-A) vs non-interactive (BTP-B) transport

  • Well-known port mapping for ITS message types

  • Minimal overhead (4 bytes)

Facility Layer Responsibilities:

  • Application-specific message content

  • Vehicle/infrastructure status information

  • Event descriptions and metadata

  • ASN.1 encoding for interoperability

  • Validation against ETSI schemas

Usage Patterns

Asynchronous Pattern (Recommended for I/O-bound applications)

from step_lib import AsyncComManager, AsyncComManagerParams, CamMessageV1
from logging import getLogger

async def main():
    # Configure connection
    params = AsyncComManagerParams(
        instance_name="vehicle_001",
        host="mqtt.example.com",
        port=8883,
        username="vehicle",
        password="secret",
        station_id=12345,
        logger=getLogger(__name__)
    )

    # Create and connect
    async with AsyncComManager(params) as client:
        # Subscribe to topics
        await client.subscribe(
            topics=["v2x/cam/#", "v2x/denm/#"],
            qos=MqttQoS.QOS_1
        )

        # Publish a message
        cam_message = CamMessageV1(...)  # Your CAM data
        await client.publish_its_message(
            message=cam_message,
            is_station_mobile=True
        )

        # Receive messages
        async for its_message in client.its_messages:
            facility_msg = its_message.its_payload
            print(f"Received {facility_msg.message_type}")
            print(f"Position: {facility_msg.reference_position}")

Synchronous Pattern (Easier integration with legacy code)

from step_lib import SyncComManager, SyncComManagerParams, DenmMessageV1
from logging import getLogger

# Configure connection
params = SyncComManagerParams(
    instance_name="roadside_unit_001",
    host="mqtt.example.com",
    port=8883,
    username="rsu",
    password="secret",
    station_id=54321,
    reconnect_interval=2,
    logger=getLogger(__name__)
)

# Use as context manager
with SyncComManager(params) as manager:
    # Subscribe to topics
    manager.subscribe(
        topics=["v2x/denm/#"],
        qos=MqttQoS.QOS_2
    )

    # Publish a hazard notification
    denm_message = DenmMessageV1(...)  # Your DENM data
    manager.publish_its_message(
        message=denm_message,
        is_station_mobile=False
    )

    # Receive messages with timeout
    while True:
        facility_msg = manager.get_its_message_received(timeout=1.0)
        if facility_msg:
            print(f"Received {facility_msg.message_type}")
            # Process message
        else:
            # No message received, continue or break

Design Principles

Immutability

Protocol messages use frozen dataclasses to ensure thread safety and prevent accidental modifications:

  • All GeoNetworking structures (BasicHeader, CommonHeader, ExtendedHeader)

  • BTP messages

  • Position vectors and addresses

  • Configuration parameters

Thread Safety

  • AsyncComManager: Uses asyncio for single-thread async operations

  • SyncComManager: Uses explicit locking (RLock) for connection status

  • Message queues are thread-safe by design (asyncio.Queue, queue.Queue)

  • Event loop runs in dedicated background thread

Type Safety

  • Extensive use of type hints for IDE support and validation

  • Enumerations for protocol constants (no magic numbers)

  • Dataclasses with slots for memory efficiency

  • Pydantic models for schema validation

Error Handling

Custom exception hierarchy for specific error scenarios:

  • StepLibError: Base exception

  • StepLibUnsupportedMessageError: Unknown message type

  • StepLibEchoMessageError: Own message received (filtered by station_id)

  • StepCliError: CLI-specific errors

Performance Optimizations

  1. ASN.1 Schema Caching: Compiled schemas stored on disk to avoid recompilation

  2. Lazy Initialization: Resources allocated only when needed

  3. Binary Operations: Direct byte manipulation for protocol headers

  4. Message Queuing: Bounded queues prevent memory overflow

  5. Efficient Serialization: Zero-copy operations where possible

Extension Points

Adding New Message Types

To add support for a new ITS message type (e.g., VAM - Vulnerable Road User Awareness Message):

  1. Create message class inheriting from FacilityMessage

  2. Add ASN.1 schema file to asn1_files/ directory

  3. Update BtpWellKnownPort enumeration

  4. Add mapping in ItsMessageSerializer

  5. Update FacilitySerializer.covert_to_facility_message()

Custom Transport Layer

The serialization layer is independent of MQTT, allowing alternative transports:

  • Replace AsyncComManager with custom transport

  • Keep ItsMessageSerializer for message encoding/decoding

  • Implement your own publish/subscribe mechanism

Testing Strategy

The package should include:

  • Unit Tests: Individual component testing (serializers, messages, headers)

  • Integration Tests: End-to-end message flow testing

  • Protocol Compliance Tests: Validation against ETSI test vectors

  • Performance Tests: Throughput and latency measurements

  • Thread Safety Tests: Concurrent access scenarios

Deployment Considerations

Production Checklist

  1. Security:

    • Use TLS/SSL for MQTT connections (configure tls_context or tls_params)

    • Secure credential management (avoid hardcoded passwords)

    • Validate certificates in production

  2. Logging:

    • Configure appropriate log levels (DEBUG for development, INFO/WARNING for production)

    • Use structured logging for better analysis

    • Monitor exception rates

  3. Resource Limits:

    • Set reasonable queue sizes (max_queued_incoming_messages, max_queued_outgoing_messages)

    • Configure keepalive and timeout based on network conditions

    • Monitor memory usage with many subscriptions

  4. High Availability:

    • Use MQTT broker clustering

    • Configure automatic reconnection (reconnect_interval)

    • Implement message persistence for critical events

    • Handle QoS appropriately (QoS 1 or 2 for important messages)

  5. Monitoring:

    • Track message rates (publish/subscribe)

    • Monitor connection status changes

    • Alert on persistent disconnections

    • Measure end-to-end message latency

Scalability

  • Horizontal Scaling: Multiple instances can share MQTT topics

  • Station ID Filtering: Prevents processing own messages in shared topics

  • Geohash-based Topics: Reduces subscription scope for geographic filtering

  • Message Batching: Consider batching for high-frequency messages

Standards Compliance

The step_lib package implements the following ETSI standards:

  • ETSI TS 103 836-4-1: GeoNetworking protocol (Basic, Common, Extended headers)

  • ETSI TS 103 836-5-1: Basic Transport Protocol (BTP-A and BTP-B)

  • ETSI EN 302 637-2: CAM (Cooperative Awareness Message) specification

  • ETSI EN 302 637-3: DENM (Decentralized Environmental Notification Message) specification

  • ETSI TS 103 324: CPM (Collective Perception Message) specification

ASN.1 Schema Files

The package includes compiled ASN.1 schemas from ETSI:

  • CAM-PDU-Descriptions.asn

  • DENM-PDU-Descriptions.asn

  • CPM-PDU-Descriptions.asn (with sub-containers)

  • ETSI-ITS-CDD.asn (Common Data Dictionary)

  • VAM-PDU-Descriptions.asn
