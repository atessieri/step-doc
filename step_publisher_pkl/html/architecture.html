Architecture

This document describes the architecture of the STEP Publisher Pickle, a Python package for publishing vehicle trajectory data from CARLA simulator to the STEP (Safer Transport for Europe Platform) MQTT broker. It integrates CARLA-generated simulation data with the STEP ecosystem by publishing Cooperative Awareness Messages (CAM) from PKL (Pickle) formatted scenario files generated by the CARLA simulator.

Overview

The STEP Publisher Pickle serves as a bridge between CARLA simulator and the STEP ecosystem, enabling the integration of CARLA-generated vehicle trajectory data with real-world ITS infrastructure. It loads vehicle trajectory data from pickle files generated by CARLA simulations and publishes CAM messages to the STEP MQTT broker with realistic timing and multi-vehicle support. Unlike other STEP components that use Redis streams, this is a standalone publisher focused on translating CARLA simulation data into ITS messages for the STEP platform.

Library

The STEP Publisher Pickle project leverages several key libraries to provide robust ITS message communication capabilities:

Core Dependencies:

  1. Pydantic: Used extensively for configuration management and data validation throughout the system. The StepPublisherPklConfig class and its nested configuration models rely on Pydantic’s BaseModel for type-safe configuration loading, validation, and JSON schema generation.

  2. step_cloud_schemas: Provides standardized data schemas for ITS messages, particularly CAM (Cooperative Awareness Messages) format. Contains CloudEvents message structures and ItsTime for precise timing calculations used for realistic message publishing intervals.

  3. step_lib: Core library providing fundamental components including:

    • AsyncComManager: Base class for asynchronous communication management

    • CamMessageV1: CAM message handling and encoding functionality

    • MQTT utilities including MqttQoS enumerations and PublishTopicParams

    • GPS location and GeoNetwork addressing components

    • TLS/SSL security parameter management

  4. aiomqtt: Asynchronous MQTT client library with TLS support for non-blocking message publishing

  5. paho-mqtt: MQTT protocol implementation providing subscription options and QoS controls

This library ecosystem enables the STEP Publisher Pickle to provide a type-safe, highly configurable solution for simulating vehicle trajectory data within the STEP platform.

Components

The architecture follows a modular design pattern that separates concerns between MQTT communication, scenario data management, and configuration. This enables flexibility and maintainability in the system design.

Main Components:

  1. StepBroker: Gateway class for MQTT communication with the STEP broker

  2. Scenario: Vehicle trajectory data loader and processor for pickle files

  3. StepPublisherPklConfig: Configuration management for the publisher

  4. StepLogger: Logging utilities specific to the STEP publisher

  5. StepPublisherPklError/StepCliError: Custom exceptions for error handling

  6. Main Application (__main__): Asynchronous publisher orchestrator with CLI

StepBroker

The StepBroker is a core component of the STEP Publisher Pickle architecture that manages MQTT communication with the STEP broker. Extending the AsyncComManager class, it provides an asynchronous interface for secure message publishing to the STEP ecosystem.

Key responsibilities of StepBroker include:

  1. MQTT Connection Management: Establishes and maintains secure TLS/SSL connections to the MQTT broker, handling reconnection and error scenarios.

  2. Message Publication: Publishes CAM messages to the STEP broker with appropriate topic selection and message encoding through the client_publish_its_message() method.

  3. Message Encoding: Handles conversion of CamMessageV1 objects to the appropriate ITS message format for MQTT transmission.

  4. GeoNetwork Addressing: Configures GeoNetwork addressing with traffic participant type (PASSENGER_CAR) and MAC ID for proper ITS message routing.

  5. Context Management: Implements asynchronous context management through __aenter__ and __aexit__ methods for clean resource handling.

The StepBroker class uses asynchronous patterns throughout to ensure non-blocking operations, making it suitable for concurrent multi-vehicle publishing scenarios in ITS applications.

Scenario

The Scenario component is responsible for managing and processing vehicle trajectory data loaded from pickle files. It serves as the data source for the publisher, providing vehicle positions with realistic timing for CAM message generation.

Key features of Scenario include:

  1. Pickle File Loading: Loads vehicle trajectory data from pickle files generated by CARLA simulator, stored in a configured folder path, supporting multiple vehicles per scenario.

  2. Time Reference Management: Establishes a mapping between CARLA simulation timestamps and real-world time through the TimeReference dataclass, enabling synchronized playback of CARLA-recorded vehicle movements.

  3. Position Data Queue: Manages vehicle position data as queues (using deque) for efficient sequential access and consumption via the pop_position_arrays() generator method.

  4. CAM Data Conversion: Converts raw trajectory data (coordinates, speed, heading) to structured CamDataV1 format with proper ITS message components:

    • Identification: Station ID and type

    • ItsTime: Precise timestamps for message timing

    • ReferencePosition: GPS coordinates with altitude

    • Speed and Heading: Vehicle dynamics data

  5. Multi-Vehicle Support: Maintains separate position queues for each vehicle ID, allowing concurrent publishing of multiple vehicle trajectories.

  6. Timing Calculation: Provides next_position_time through StationPositionResult to enable realistic delays between position updates.

The Scenario class ensures that vehicle trajectory playback maintains the original CARLA simulation timing characteristics, providing accurate replay of CARLA-generated vehicle movements within the STEP ecosystem.

StepPublisherPklConfig

The StepPublisherPklConfig component is responsible for configuration management in the STEP Publisher Pickle architecture. Built as a Pydantic BaseModel, it provides a robust, type-safe mechanism for loading, validating, and accessing configuration settings throughout the application. Key features of StepPublisherPklConfig include:

  1. JSON Configuration Loading: Loads configuration settings from a JSON file specified via command-line arguments, providing a centralized source of configuration for all components.

  2. Type Validation: Leverages Pydantic’s validation system to ensure all configuration values meet the expected types and constraints, preventing configuration errors at runtime.

  3. Hierarchical Structure: Organizes configuration in a hierarchical manner, with nested models for different aspects of the system:

    • MQTT Client configuration (connection parameters, security settings)

    • MQTT Protocol configuration (QoS, topic management, session parameters)

    • STEP Broker configuration (for MQTT broker integration)

    • Logging configuration (handlers, levels, formatting)

    • Pickle folder path (location of CARLA-generated scenario data files)

  4. Immutable Configuration: Once loaded at startup, the configuration becomes immutable, ensuring consistency throughout the application’s lifecycle.

  5. Configuration Sharing: Acts as a central repository of configuration settings that is shared with other components, providing a single source of truth for system settings.

  6. Default Configuration: Provides get_default() methods to generate sensible default configurations when specific values are not provided.

  7. JSON Schema Generation: Supports generating JSON schemas for configuration validation through the StepConfigGenerateJsonSchema utility class, accessible via the --conf_schema CLI option.

The design of StepPublisherPklConfig emphasizes immutability and strong validation, helping prevent configuration-related issues during runtime while providing a clear, structured approach to configuration management.

StepLogger

The StepLogger component provides specialized logging functionality for the STEP Publisher Pickle architecture, enabling comprehensive and configurable logging throughout the application. It serves as a wrapper around Python’s standard logging facilities with additional features tailored to STEP Publisher Pickle’s needs.

Key features of StepLogger include:

  1. UTC-based Timestamps: Implements UtcFormatter class that uses gmtime for consistent UTC timezone formatting across all log entries, ensuring consistent timestamps regardless of system timezone.

  2. Multi-destination Logging: Supports logging to different output formats and destinations, including:

    • File-based logging for persistent records (FileHandler)

    • Standard output (console) for development and debugging (StreamHandler)

    • Rotating file handlers with size-based (RotatingFileHandler) or time-based (TimedRotatingFileHandler) rotation

    • Null handler (NullHandler) for silent operation

  3. Log Compression: Automatic log file compression using ZIP format via the _rotator() function when log files are rotated, saving disk space for archived logs.

  4. Log Level Management: Provides fine-grained control over logging verbosity with standard log levels (DEBUG, INFO, WARNING, ERROR, CRITICAL).

  5. Structured Formatting: Implements customizable log formats with timestamp, severity level, source component, and structured message content.

  6. Configuration Integration: Leverages the logging configuration section from StepPublisherPklConfig to enable consistent setup across components.

  7. Utility Methods: Offers utility methods like setup_logging() for initial configuration and get_logger() for retrieving appropriately configured logger instances.

The StepLogger component ensures that the STEP Publisher Pickle maintains comprehensive logging capabilities to support monitoring, debugging, and operational insights, particularly for tracking multi-vehicle publishing operations and timing-sensitive position updates.

StepPublisherPklError and StepCliError

The exception handling components provide a structured error handling mechanism for the STEP Publisher Pickle architecture. They define custom exceptions tailored to the specific error conditions that can occur during publisher operations.

Key aspects include:

  1. Exception Hierarchy: Establishes a well-organized hierarchy:

    • StepPublisherPklError: Base exception class for all publisher errors

    • StepCliError: Specialized exception for CLI-specific errors such as argument parsing, command execution failures, and configuration loading issues

  2. Error Classification: Categorizes errors into distinct types such as:

    • CLI argument and configuration errors

    • MQTT broker connection failures

    • Scenario data loading errors

    • Message publishing failures

  3. Integration with Logging: Collaborates with the StepLogger component to ensure that exceptions are properly logged with appropriate severity levels.

The exception components enable robust error handling throughout the STEP Publisher Pickle, allowing application code to catch and handle specific types of exceptions appropriately while providing meaningful information for debugging and system monitoring.

Main Application (__main__)

The main application module provides the command-line interface and orchestrates the asynchronous publishing workflow. It implements the primary execution logic that coordinates all other components.

Key features of the main application include:

  1. Command-Line Interface: Provides comprehensive CLI with options for:

    • --version: Display version information

    • --conf_schema: Generate JSON configuration schema

    • --conf_template: Generate configuration template

    • --config and --instance: Load configuration and run publisher

  2. Asynchronous Task Orchestration: Uses asyncio.TaskGroup to manage concurrent publisher tasks for multiple vehicles, enabling simultaneous publishing while maintaining individual vehicle timing.

  3. Exit Code Management: Defines standard exit codes through ExitCode enum:

    • OK (0): Successful execution

    • USAGE (1): Command-line usage error

    • ERROR (2): Runtime error

    • ABORTED (3): User interruption or signal

  4. Signal Handling: Implements cross-platform signal handling:

    • Windows: SIGBREAK support

    • Unix: SIGINT support (Ctrl+C)

  5. Publisher Task Management: The _publisher_run() coroutine manages individual vehicle publishing by:

    • Consuming vehicle positions via scenario.pop_position_arrays()

    • Publishing CAM messages through client.client_publish_its_message()

    • Calculating sleep intervals using ItsTime.time_difference()

    • Maintaining realistic timing based on scenario timestamps

  6. Resource Management: Utilizes async context managers (async with) for automatic cleanup of MQTT connections and other resources.

  7. Event Loop Configuration: On Windows, uses SelectorEventLoop for optimal compatibility with asyncio operations.

The main application serves as the entry point and coordinator, bringing together configuration, CARLA simulation data, MQTT communication, and logging to deliver a complete integration between CARLA simulator and the STEP platform.
