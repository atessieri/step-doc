Accepted Input Files
=====================

Overview
--------

The STEP Publisher Pickle publishes the entries listed in the ``inputFiles`` configuration
parameter (see the :ref:`STEP Publisher Pickle Configuration Schema<step_publisher_pkl_config_schema>`).
Each entry is automatically inspected by :class:`step_publisher_pkl.scenario.Scenario` and
classified into one of four supported formats. There is no need to declare the format of a
file explicitly: the file loaders are tried in turn and the first one that parses the whole
file is used.

Detection Order
----------------

The publisher configures four file loaders, in this order:

    #. **JSONL ITS messages** (``JsonlLoader``, extension ``.jsonl``): the file is read as
       UTF-8 text and every non-blank line is validated as an ITS message.
    #. **Pickle actor / vehicle trajectories** (``PickleActorLoader``, extension ``.pkl``):
       the file is unpickled and every trajectory point of every vehicle is converted.
    #. **Pickle camera / CPM data** (``PickleCameraLoader``, extension ``.pkl``): the file is
       unpickled and every item is validated as a Collective Perception Message (CPM).
    #. **GPX track files** (``GpxLoader``, extension ``.gpx``): the file is parsed as GPX and
       every track and track point is converted.

For every path listed in ``inputFiles``, the loaders owning the file's extension are tried
first (in the order above), then the remaining loaders as a fallback; a file whose extension
no loader owns is tried against all four loaders in the order above. The first loader that
parses the whole file wins: a loader that rejects the file (``LoaderError``, logged at INFO
level) hands it to the next one. For example, a ``.pkl`` file is tried as pickle actor data,
then as pickle camera data, then as JSONL and GPX.

A file that does not match any of the four formats, or that contains no messages, is
skipped, and a warning is logged; processing continues with the remaining files.

JSONL ITS Messages
-------------------

A UTF-8 text file containing one JSON document per line. Blank lines are skipped; every
other line must validate as an ITS message (``ItsMessageRoot`` holding a ``CamDataV1``,
``CpmDataV1``, or ``DenmDataV1``), following the :doc:`JSON Schemas<schemas_rst/json_schemas>`.

Each line is loaded as-is and published as the corresponding CAM, CPM, or DENM message. The
first line that fails validation, or that resolves to an unsupported message type, rejects
the **whole file** as JSONL (the next loader is then tried).

Pickle Actor / Vehicle Trajectories
-------------------------------------

A binary pickle file (``.pkl``) produced from a CARLA simulation run, containing an
unpickled dictionary shaped as:

.. code-block:: python

    {
        "trajectories": {
            "vehicles": {
                <station_id>: [
                    {
                        "timestamp": datetime.datetime(...),
                        "geo_location": {
                            "latitude": <float>,
                            "longitude": <float>,
                            "altitude": <float>,
                        },
                        "heading": <float>,       # optional
                        "velocity": {"speed": <float>},  # optional
                    },
                    ...
                ],
                ...
            }
        }
    }

Requirements for every trajectory point:

    * ``timestamp`` must be a :class:`datetime.datetime` instance.
    * ``geo_location`` must provide ``latitude``, ``longitude``, and ``altitude`` as
      ``float`` or ``int``.
    * ``heading`` is optional; if present it must be a ``float`` or ``int``.
    * ``velocity.speed`` is optional; if present it must be a ``float`` or ``int``.

The station ID keys must be convertible with ``int()``. Every trajectory point of every
vehicle is converted: a missing required key or a value that cannot be converted rejects
the whole file as pickle actor data. A file with no trajectory points is skipped with a
warning.

Each trajectory point is converted into a Cooperative Awareness Message (CAM) compliant
with ETSI TS 103 900, using ``PASSENGER_CAR`` as the station type; values are passed to the
CAM fields unchanged (no unit conversion). Vehicles whose station ID is listed in
``stationsBlacklist`` are skipped entirely.

Pickle Camera / CPM Data
--------------------------

A binary pickle file (``.pkl``) containing an unpickled **list** of dictionaries, where
each item directly validates against the ``CpmDataV1`` schema (Collective Perception
Message). Every item is validated: a single invalid item rejects the whole file as pickle
camera data. A file with an empty list is skipped with a warning.

Each item is loaded and published as a Collective Perception Message (CPM). Items whose
station ID is listed in ``stationsBlacklist`` are skipped.

GPX Track Files
-----------------

A GPX file where each ``<trk>`` element has a ``<name>`` matching
``Path actor <station_id>_<object_id>``, where ``object_id`` is either the literal ``none``
or an int (matched but not used, as it is not relevant to the CAM data produced). A track
without a matching name is treated as an invalid file.

Each track point (``<trkpt>``, across all ``<trkseg>`` segments of a track) is converted
into a Cooperative Awareness Message (CAM):

    * ``latitude``, ``longitude``, and (when present) elevation come directly from the
      track point.
    * ``heading`` and ``speed`` are read from the point's Garmin ``TrackPointExtension``
      (``course`` and ``speed`` extension elements) when present; otherwise they are
      omitted from the CAM message.
    * The point must have its ``time`` set; a point with no time raises an error and the
      file is treated as invalid.

Every track of the file is validated (name and points): a single invalid track or point
rejects the whole file as GPX. Vehicles whose station ID is listed in ``stationsBlacklist``
are skipped entirely.

Notes
------

    * Once loaded, the creation/reference/detection times of every message are rewritten
      from scenario time to real time, using the earliest message time across all loaded
      files as the scenario time origin and the current time (offset by
      ``waitTimeBeforeStarting``) as the real time origin. This keeps the relative
      timing between messages intact while aligning playback to the moment the publisher
      starts. Messages of an unsupported type are skipped with a warning, and a station
      left with no messages is dropped.
    * Multiple ``inputFiles`` entries, of any of the four supported formats, can be
      combined in a single run; messages from all files are merged per station and
      published in chronological order.
