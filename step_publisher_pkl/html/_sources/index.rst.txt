The **STEP Publisher Pickle** is a specialized component of the STEP (Safer Transport for Europe Platform)
ecosystem, designed to integrate vehicle trajectory/ITS message data with real-world ITS
infrastructure. This MQTT-based publisher translates scenario data stored in JSONL, pickle, or GPX
files into Cooperative Awareness (CAM), Collective Perception (CPM), or Decentralized Environmental
Notification (DENM) messages for the STEP broker, enabling realistic vehicle trajectory
testing within the ITS ecosystem.

Purpose
-------

The **STEP Publisher Pickle** serves as a bridge between recorded/simulated trajectory data and the
STEP platform, publishing vehicle position data from JSONL, pickle, or GPX scenario files as ITS
ETSI messages. It loads vehicle trajectory/message data including GNSS positions, speed, heading,
and timestamp information, then publishes them as CAM, CPM, or DENM messages to the STEP MQTT
broker with realistic timing and multi-vehicle support.

Environment Variables
---------------------

The MQTT connection settings (TLS/SSL files, protocol parameters, publish topics) are kept in
the JSON configuration file, while the MQTT broker host, port and credentials are read from
the environment, so that secrets are never written to the configuration file:

.. list-table::
   :header-rows: 1
   :widths: 25 15 60

   * - Variable
     - Required
     - Description
   * - ``MQTT_URL``
     - yes
     - MQTT broker host name or IP address, without protocol or port
   * - ``MQTT_PORT``
     - yes
     - MQTT broker port (1-65535); usually 8883 with TLS, 1883 without
   * - ``MQTT_USERNAME``
     - no
     - Broker username; unset or empty connects anonymously
   * - ``MQTT_PASSWORD``
     - no
     - Broker password; ignored, with a warning, without ``MQTT_USERNAME``

They are read once at start-up by step_lib ``MqttCredential.from_env()``, which first loads
the ``.env`` file of the current working directory (or its nearest parent); a variable
already set in the environment wins over the file. See :ref:`step_publisher_pkl_credentials`
for the full reference and the commented ``.env`` template.

Goal
----

The **STEP Publisher Pickle** exists so that developers, testers, and CI/CD pipelines can exercise
the STEP ecosystem's ITS message ingestion, MQTT broker, and downstream services with realistic,
repeatable vehicle traffic, without needing a live simulator run or real vehicles on the road.
It replays previously recorded trajectory/message scenarios (JSONL, pickle, or GPX files) as a
stream of ETSI-compliant CAM, CPM, or DENM messages, published to the STEP MQTT broker with the
same timing, multi-vehicle concurrency, and message structure a real deployment would produce.
This gives the rest of the STEP platform a lightweight, deterministic traffic generator for
integration testing and development.

Key Features
------------

Scenario Data Loading
~~~~~~~~~~~~~~~~~~~~~

- **Pluggable File Loaders**: Auto-detects and loads scenario data from JSONL ITS messages,
  pickle actor/vehicle trajectories, pickle camera/CPM data, or GPX track files (see
  :doc:`input_files`)
- **Time Reference Mapping**: Maps scenario timestamps to real-world time (current time plus
  ``waitTimeBeforeStarting``) for synchronized playback of recorded vehicle movements
- **Multi-Vehicle Support**: Processes multiple vehicle trajectories/messages concurrently
- **Station Message Management**: Manages vehicle message data as time-ordered sorted queues
  for sequential access and consumption; stations in ``stationsBlacklist`` are skipped

ITS Message Publishing
~~~~~~~~~~~~~~~~~~~~~~

- **ETSI Compliance**: Publishes Cooperative Awareness (CAM), Collective Perception (CPM), and
  Decentralized Environmental Notification (DENM) messages following ITS standards
- **Message Conversion**: Converts pickle actor and GPX trajectory points into CAM messages
  (Identification, ReferencePosition, Speed, Heading); JSONL and pickle camera data are
  published as-is
- **GeoNetwork Addressing**: Uses a fixed address with traffic participant type and MAC ID
  for ITS message routing
- **Realistic Timing**: Sleeps before each message to keep the original timing, using ItsTime
  calculations

MQTT Communication
~~~~~~~~~~~~~~~~~~

- **Secure Connection**: TLS/SSL connections to STEP MQTT broker with certificate authentication
- **Secrets out of the configuration**: MQTT broker host, port and credentials read from the
  environment or a ``.env`` file
- **Configurable QoS**: Supports Quality of Service levels (0, 1, 2) for reliable message delivery
- **Asynchronous Publishing**: Non-blocking async/await patterns for message publishing
- **Topic Management**: Flexible topic configuration with geohash precision support

Configuration and Monitoring
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Hierarchical Configuration**: Pydantic-based configuration models with input files,
  station blacklist, start delay, MQTT client, MQTT protocol, and logging settings
- **JSON Schema Support**: Configuration validation and template generation via command-line options
- **Comprehensive Logging**: UTC-based timestamps with multiple handlers (stream, file, rotating)
  and automatic compression for rotated logs
- **Signal Handling**: Graceful shutdown through the step_cloud_schemas ``AppRunner``
  (``SIGINT``/``SIGTERM`` on POSIX, ``SIGINT``/``SIGBREAK`` - Ctrl+C/Ctrl+Break - on Windows)

Core Components
---------------

Scenario Management
~~~~~~~~~~~~~~~~~~~

The ``Scenario`` class provides the management of vehicle trajectory/ITS message data for
publishing to the STEP broker and handles:

  - Loading vehicle trajectory/ITS message data through a pluggable set of ``FileLoader``
    implementations (JSONL ITS messages, pickle actor/vehicle trajectories, pickle
    camera/CPM data, and GPX track files), auto-detected per input file
  - Establishing the time reference mapping between scenario time and real-world time and
    rewriting every message time accordingly
  - Managing vehicle message data as sorted queues (using ``SortedList``) for time-ordered
    sequential access
  - Providing vehicle IDs and messages through generator methods (``get_vehicle_ids()``,
    ``pop_message()``)
  - Maintaining a separate message queue for each vehicle, enabling concurrent publishing

STEP Broker Client
~~~~~~~~~~~~~~~~~~

The ``StepBroker`` class provides MQTT communication with the STEP broker for publishing
CAM, CPM, and DENM messages. Extending ``AsyncComManager``, it implements:

  - **Secure MQTT Connection**: TLS/SSL connections with certificate authentication
  - **Message Publication**: Publishing facility messages (CAM/CPM/DENM) via
    ``client_publish_its_message()``, using the message's reference position
  - **Publish Topics**: One topic per configured message type, with geohash precision and QoS
  - **GeoNetwork Configuration**: Setting up addressing with traffic participant type and MAC ID
  - **Context Management**: Asynchronous resource handling through ``async with``

Main Application and Workload
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The main application (``__main__``) is the command-line entry point; the workload lives in
``StepPublisherApp`` (``step_publisher_app``):

- **Command-Line Interface**: Provides CLI for version display, configuration schema/template
  generation, and publisher execution
- **Application Runtime**: ``main()`` runs ``StepPublisherApp``, an ``AbstractApp``, through the
  step_cloud_schemas ``AppRunner``, which owns the event loop (``SelectorEventLoop`` on
  Windows), the signal handlers and the graceful shutdown
- **Environment-Based Credentials**: The ``StepPublisherApp`` constructor reads the
  ``MQTT_*`` variables before the event loop is started
- **Task Orchestration**: ``StepPublisherApp.work()`` uses ``asyncio.TaskGroup`` for one
  concurrent publisher task per vehicle, nested in the broker context, and returns once every
  task has finished
- **Publisher Coordination**: The ``_publisher_run()`` coroutine manages individual vehicle
  publishing with timing calculations and sleep intervals
- **Exit Code Management**: Defines standard exit codes (OK, USAGE, ERROR, ABORTED) via ``ExitCode`` enum

Configuration System
~~~~~~~~~~~~~~~~~~~~

The configuration system (``StepPublisherPklConfig``) offers:

  - **Hierarchical Configuration**: Input files, station blacklist, start delay, STEP broker
    (MQTT client and protocol) and logging settings
  - **Type Safety**: Strong typing and validation via Pydantic models
  - **JSON Schema Generation**: Schema validation and template creation through CLI options
  - **Immutable Design**: Frozen, strict configuration ensuring consistency throughout execution
  - **Default Configurations**: Pre-configured defaults via ``get_default()`` methods

Logging Infrastructure
~~~~~~~~~~~~~~~~~~~~~~

The logging system (``StepLogger``, from ``step_cloud_schemas``) provides:

  - **UTC Formatting**: Consistent UTC timestamps
  - **Multiple Handlers**: Stream, file, rotating file (size/time-based), and null handlers
  - **Log Compression**: Automatic compression of rotated logs
  - **Configurable Levels**: Adjustable logging verbosity (DEBUG, INFO, WARNING, ERROR, CRITICAL)
  - **Structured Logging**: Operation logging with vehicle ID, message type and timing

Exception Handling
~~~~~~~~~~~~~~~~~~

The exception system provides:

  - **Base Exception**: ``StepPublisherPklError`` for all publisher-related errors
  - **CLI Exception**: ``StepCliError`` for command-line misuse (``-c`` without ``-i`` or vice
    versa), logged as a single error line with exit code ``USAGE``
  - **Loader Exception**: ``LoaderError`` raised by a ``FileLoader`` when a file does not
    match, or cannot be parsed as, the format it handles; ``Scenario.load_data()`` catches
    it to try the next candidate loader

Architecture
------------

Event-Driven Processing
~~~~~~~~~~~~~~~~~~~~~~~

The publisher follows an event-driven architecture pattern:

  #. **Configuration Loading**: Loads configuration from JSON file via command-line arguments
  #. **Credential Loading**: Reads the MQTT broker host, port and credentials from the
     environment (``.env`` file optional)
  #. **Broker Connection**: Establishes secure MQTT connection to STEP broker with TLS/SSL
  #. **Scenario Loading**: Reads vehicle trajectory/ITS message data from the configured
     input files (JSONL, pickle actor, pickle camera, or GPX), auto-detected per file
  #. **Task Creation**: Creates concurrent publisher tasks using ``asyncio.TaskGroup`` for
     each vehicle in the scenario
  #. **Message Publishing**: Publishes CAM, CPM, or DENM messages with timing based on ItsTime calculations
  #. **End of Run**: Disconnects from the broker and exits once every message is published,
     or earlier on a shutdown signal

Asynchronous Operations
~~~~~~~~~~~~~~~~~~~~~~~

The architecture utilizes:

  - **Async/await**: Non-blocking operations for concurrent multi-vehicle publishing
  - **TaskGroup**: Concurrent execution of publisher tasks with automatic cancellation on error
  - **Context Managers**: Asynchronous context management for MQTT connection lifecycle
  - **AppRunner**: Event loop, signal handlers and cooperative shutdown owned by the
    step_cloud_schemas application runtime

Message Flow
~~~~~~~~~~~~

#. **Input File Loading**: Vehicle trajectory/ITS message data loaded from the configured
   input files via the pluggable ``FileLoader`` implementations (JSONL, pickle actor, pickle
   camera, GPX)
#. **Time Reference Establishment**: Scenario time mapped to real-world time for synchronized playback
#. **Vehicle Iteration**: For each vehicle, separate concurrent publisher task created
#. **Message Consumption**: Messages consumed in time order via the ``pop_message()`` generator
#. **Timing Calculation**: Time differences calculated using ``ItsTime.time_difference()``
#. **Realistic Delays**: Sleep intervals maintain the original scenario timing
#. **MQTT Publishing**: Messages published to STEP broker via ``client_publish_its_message()``

Standards Compliance
--------------------

The STEP Publisher Pickle adheres to key ITS standards:

- **ETSI TS 103 900**: Cooperative Awareness Messages (CAM) format and encoding
- **ETSI TS 103 324**: Collective Perception Messages (CPM)
- **ETSI TS 103 831**: Decentralized Environmental Notification Messages (DENM)
- **MQTT 5.0**: Message Queuing Telemetry Transport protocol

Dependencies
------------

Core Dependencies
~~~~~~~~~~~~~~~~~

- **step_cloud_schemas**: ITS message schemas (CAM, CPM, DENM), ItsTime for timing
  calculations, StepLogger, and the application runtime (AppRunner, AbstractApp)
- **step_lib**: Core library providing AsyncComManager, CamMessageV1/CpmMessageV1/DenmMessageV1,
  MQTT utilities (MqttQoS, PublishTopicParams, MqttCredential), GPS location, and GeoNetwork
  addressing
- **aiomqtt**: Asynchronous MQTT client library with TLS support for non-blocking publishing
- **paho-mqtt**: MQTT protocol implementation with subscription options and QoS controls
- **pydantic**: Configuration validation and schema generation with type safety
- **sortedcontainers**: Time-ordered per-vehicle message queues
- **gpx**: GPX track file parsing
- **python-dotenv** (through step_lib): ``.env`` file loading for the MQTT credentials

Development Dependencies
~~~~~~~~~~~~~~~~~~~~~~~~

- **pytest**: Testing framework for unit and integration tests
- **ruff**: Code formatting and linting tools
- **mypy**: Static type checking for Python code
- **sphinx**: Documentation generation for code documentation

Deployment
----------

The STEP Publisher Pickle can be deployed as:

- **Command-Line Tool**: Direct execution via ``step_publisher_pkl`` or
  ``python -m step_publisher_pkl`` with configuration file
- **Standalone Application**: Independent process replaying recorded scenario data
- **Integration Component**: Part of a larger STEP testing infrastructure

Configuration options support various deployment scenarios:

- **Development**: Local testing with debug logging and simplified configuration
- **Testing**: Scenario replay with realistic timing for ITS infrastructure validation
- **CI/CD Integration**: Automated testing scenarios with recorded test data

Usage Patterns
--------------

The publisher supports multiple usage patterns:

Publishing Mode
~~~~~~~~~~~~~~~

Run as a publisher of the configured scenario files (MQTT credentials from the environment or
``.env``):

.. code-block:: bash

   step_publisher_pkl --instance step_publisher_pkl --config config.json

Configuration Generation
~~~~~~~~~~~~~~~~~~~~~~~~

Generate configuration templates and schemas into a directory (created if missing):

.. code-block:: bash

   step_publisher_pkl --conf_template ./templates
   step_publisher_pkl --conf_schema ./schemas

Version Information
~~~~~~~~~~~~~~~~~~~

Display the version of the package:

.. code-block:: bash

   step_publisher_pkl --version

Testing
-------

The project includes comprehensive tests covering:

- **Unit Tests**: Individual component functionality including file loaders, scenario
  loading and time reference
- **Configuration Tests**: Validation of configuration schemas and default values
- **Application Tests**: Command-line handling, workload and broker client with mocked MQTT
