Architecture
============

This document describes the architecture of the STEP Publisher Pickle, a Python package
for publishing vehicle position data to the STEP (Safer Transport for Europe Platform)
using JSONL, Pickle (PKL), or GPX formatted scenario files. It simulates real-world Connected
and Autonomous Vehicle (CAV) messaging by publishing CAM, CPM, and DENM ITS messages to an
MQTT broker with realistic timing and multi-vehicle support.

Overview
--------

The STEP Publisher Pickle serves as an example implementation for testing and development
within the STEP ecosystem, showcasing how to integrate vehicle trajectory data with the STEP
cloud infrastructure. It loads vehicle trajectory/ITS message data from JSONL, pickle, or GPX
scenario files (auto-detected per file, see :doc:`input_files`) and publishes CAM, CPM, and
DENM messages to the STEP MQTT broker with realistic timing and multi-vehicle support. It
follows an event-driven architecture built on Python's ``asyncio`` framework, creating a
separate publisher task per vehicle in the scenario so that message publishing proceeds
concurrently while preserving each vehicle's original trajectory timing.

Library
-------

The STEP Publisher Pickle project leverages several key libraries to provide robust ITS
message communication capabilities:

**Core Dependencies:**

    #. **Pydantic**: Used extensively for configuration management and data
       validation throughout the system. The ``StepPublisherPklConfig`` class and its nested
       configuration models rely on Pydantic's ``BaseModel`` for type-safe configuration
       loading, validation, and JSON schema generation.

    #. **step_cloud_schemas**: Provides standardized data schemas for ITS
       messages (CAM, CPM, and DENM), including ``ItsMessageRoot``/``CamDataV1``/``CpmDataV1``/
       ``DenmDataV1`` and ``ItsTime`` for precise timing calculations used for realistic
       message publishing intervals.

    #. **step_lib**: Core library providing fundamental components including:

        * ``AsyncComManager``: Base class for asynchronous communication management
        * ``CamMessageV1``/``CpmMessageV1``/``DenmMessageV1``/``FacilityMessage``: ITS
          facility message handling and encoding functionality
        * MQTT utilities including ``MqttQoS`` enumerations and ``PublishTopicParams``
        * GPS location and GeoNetwork addressing components
        * TLS/SSL security parameter management

    #. **aiomqtt**: Asynchronous MQTT client library with TLS support for
       non-blocking message publishing

    #. **paho-mqtt**: MQTT protocol implementation providing subscription options
       and QoS controls

    #. **python-dotenv**: Loads MQTT broker credentials from a ``.env`` file into the
       process environment at startup (see :doc:`usage`).

    #. **sortedcontainers**: Backs each vehicle's per-station message queue
       (``SortedList``, ordered by ``its_time``) inside ``Scenario``.

This library ecosystem enables the STEP Publisher Pickle to provide a type-safe,
highly configurable solution for simulating vehicle trajectory data within the STEP platform.

Components
----------

The architecture follows a modular design pattern that separates concerns between MQTT
communication, scenario/loader data management, and configuration. This enables flexibility
and maintainability in the system design.

Main Components:

    #. **StepBroker**: Gateway class for MQTT communication with the STEP broker
    #. **Scenario**: Vehicle trajectory/ITS message loader and per-vehicle message queue
    #. **FileLoader implementations**: Pluggable parsers (JSONL, pickle actor, pickle
       camera, GPX) used by ``Scenario.load_data()``
    #. **StepPublisherPklConfig**: Configuration management for the publisher
    #. **StepLogger**: Logging utilities specific to the STEP publisher
    #. **StepPublisherPklError/StepCliError/LoaderError/ShutdownRequestedError**: Custom
       exceptions for error handling
    #. **Main Application** (__main__): Asynchronous publisher orchestrator with CLI

StepBroker
^^^^^^^^^^

The ``StepBroker`` is a core component of the STEP Publisher Pickle architecture
that manages MQTT communication with the STEP broker. Extending the ``AsyncComManager`` class,
it provides an asynchronous interface for secure message publishing to the STEP ecosystem.

Key responsibilities of ``StepBroker`` include:

    #. **MQTT Connection Management**: Establishes and maintains secure TLS/SSL connections
       to the MQTT broker, handling reconnection and error scenarios.
    #. **Message Publication**: Publishes CAM, CPM, and DENM messages to the STEP broker with
       appropriate topic selection and message encoding through the
       ``client_publish_its_message()`` method.
    #. **Message Encoding**: Handles conversion of ``CamMessageV1``/``CpmMessageV1``/
       ``DenmMessageV1`` objects to the appropriate ITS facility message format for MQTT
       transmission.
    #. **GeoNetwork Addressing**: Configures GeoNetwork addressing with traffic
       participant type (PASSENGER_CAR) and a fixed MAC ID (``StepBroker.MAC_ID``) for proper
       ITS message routing.
    #. **Context Management**: Implements asynchronous context management through
       ``__aenter__`` and ``__aexit__`` methods for clean resource handling.

Its ``__init__`` builds one ``PublishTopicParams`` entry per configured publish topic
(time and space complexity O(p), where p is the number of configured publish topics); SSL/TLS
setup is O(1). The ``StepBroker`` class uses asynchronous patterns throughout to ensure
non-blocking operations, making it suitable for concurrent multi-vehicle publishing scenarios
in ITS applications.

Scenario and File Loaders
^^^^^^^^^^^^^^^^^^^^^^^^^

The ``Scenario`` component is responsible for loading vehicle trajectory/ITS message data
and serving it per vehicle in time order. It delegates the actual file parsing to a sequence
of pluggable ``FileLoader`` implementations, has no dependency on any concrete loader, and
serves as the data source for the publisher, providing per-vehicle messages with realistic
timing for CAM/CPM/DENM publishing.

Key features of ``Scenario`` include:

    #. **Pluggable File Loading**: ``load_data()`` tries, for each input file, the loader(s)
       owning that file's extension first, then every other configured loader as a fallback,
       until one successfully parses the file into ``FacilityMessage`` instances; a file that
       fails validation against every loader is skipped with a warning.
    #. **Time Reference Management**: Establishes a mapping between scenario timestamps and
       real-world time through the ``TimeReference`` named tuple, enabling synchronized
       playback of recorded vehicle movements.
    #. **Per-Station Message Queue**: Manages each station's messages in a ``SortedList``
       (ordered by ``its_time``) for efficient sequential access and consumption via the
       ``pop_message()`` generator method; station IDs present in ``stations_blacklist`` are
       skipped.
    #. **Multi-Vehicle Support**: Maintains a separate message queue per station/vehicle ID,
       allowing concurrent publishing of multiple vehicle trajectories.
    #. **Vehicle Enumeration**: Provides ``get_vehicle_ids()`` to enumerate the stations
       loaded from the input files.

Four ``FileLoader`` implementations ship with the package (module ``step_publisher_pkl.loaders``),
each a self-contained parser for one file format that either returns the ``FacilityMessage``
instances a file contains or raises ``LoaderError`` if the file does not match its format:

    * ``JsonlLoader`` (``.jsonl``): Parses one JSON-encoded ITS message per line, each
      validating as an ``ItsMessageRoot`` (``CamDataV1``, ``CpmDataV1``, or ``DenmDataV1``);
      time/space complexity O(l), l = number of lines in the file.
    * ``PickleActorLoader`` (``.pkl``): Parses an unpickled dictionary shaped as
      ``{"trajectories": {"vehicles": {<station_id>: [<point>, ...]}}}`` into CAM messages;
      time/space complexity O(p), p = total number of trajectory points across all vehicles.
    * ``PickleCameraLoader`` (``.pkl``): Parses an unpickled list of dictionaries, each
      directly convertible to a ``CpmDataV1`` (Collective Perception Message); time/space
      complexity O(m), m = number of camera data items in the file.
    * ``GpxLoader`` (``.gpx``): Parses a GPX file containing a vehicle trajectory into CAM
      messages; time/space complexity O(p), p = total number of track points across all
      tracks/segments in the file.

See :doc:`input_files` for the exact file formats accepted.

The ``Scenario`` class ensures that vehicle trajectory playback maintains the original
scenario timing characteristics, providing accurate replay of loaded vehicle movements within
the STEP ecosystem. Across its methods, the worst case (in ``load_data()``/
``_update_time_stations()``) is time O(s) and space O(s), where s is the total number of
trajectory points/messages loaded across all input files.

StepPublisherPklConfig
^^^^^^^^^^^^^^^^^^^^^^

The ``StepPublisherPklConfig`` component is responsible for configuration management in the
STEP Publisher Pickle architecture. Built as a Pydantic ``BaseModel``, it provides a robust,
type-safe mechanism for loading, validating, and accessing configuration settings throughout
the application.

Key features of ``StepPublisherPklConfig`` include:

    #. **JSON Configuration Loading**: Loads configuration settings from a JSON file specified
       via command-line arguments, providing a centralized source of configuration for all
       components.
    #. **Type Validation**: Leverages Pydantic's validation system to ensure all configuration
       values meet the expected types and constraints, preventing configuration errors at
       runtime.
    #. **Hierarchical Structure**: Organizes configuration in a hierarchical manner, with the
       following top-level fields:

        * ``templateVersion``: Configuration data version, matching ``StepConfigVersion.VERSION``
        * ``inputFiles``: List of paths to the JSONL/Pickle/GPX files to read and publish
        * ``stationsBlacklist``: Optional list of station IDs to ignore in the scenario
        * ``waitTimeBeforeStarting``: Time to wait before starting the scenario, in
          milliseconds
        * ``stepBroker`` (``StepBrokerConfig``): MQTT client configuration, MQTT protocol
          configuration (QoS, topic management, session parameters), and cache directory
        * ``log`` (``LogConfig``): Logging configuration (handlers, levels, formatting)

    #. **Immutable Configuration**: The model is declared ``frozen=True`` and ``strict=True``,
       so once loaded at startup it becomes immutable, ensuring consistency throughout the
       application's lifecycle.
    #. **Configuration Sharing**: Acts as a central repository of configuration settings that
       is shared with other components, providing a single source of truth for system settings.
    #. **Default Configuration**: Provides a ``get_default()`` static method to generate
       sensible default configurations when specific values are not provided.
    #. **JSON Schema Generation**: Supports generating JSON schemas via
       ``print_config_schema()``/the internal ``_ConfigGenerateJsonSchema`` utility class,
       accessible via the ``--conf_schema`` CLI option; time/space complexity O(n), n = number
       of configuration fields.

MQTT credentials (``MqttCredential``: ``url``, ``port``, ``username``, ``password``) are kept
separate from ``StepPublisherPklConfig`` and loaded from the environment instead, so secrets
are never embedded in the persisted configuration document (see :doc:`usage`).

The design of ``StepPublisherPklConfig`` emphasizes immutability and strong validation, helping
prevent configuration-related issues during runtime while providing a clear, structured
approach to configuration management.

StepLogger
^^^^^^^^^^

The ``StepLogger`` component provides specialized logging functionality for the STEP Publisher
Pickle architecture, enabling comprehensive and configurable logging throughout the application.
It serves as a wrapper around Python's standard logging facilities with additional features
tailored to STEP Publisher Pickle's needs.

Key features of ``StepLogger`` include:

    #. **UTC-based Timestamps**: Implements a ``UtcFormatter`` class that uses ``gmtime`` for
       consistent UTC timezone formatting across all log entries, ensuring consistent
       timestamps regardless of system timezone.
    #. **Multi-destination Logging**: Supports logging to different output formats and
       destinations, including:

        * File-based logging for persistent records (``FileHandler``)
        * Standard output (console) for development and debugging (``StreamHandler``)
        * Rotating file handlers with size-based (``RotatingFileHandler``) or
          time-based (``TimedRotatingFileHandler``) rotation
        * Null handler (``NullHandler``) for silent operation

    #. **Log Compression**: Automatic log file compression using ZIP format via the
       ``_rotator()`` function when log files are rotated, saving disk space for
       archived logs.
    #. **Log Level Management**: Provides fine-grained control over logging verbosity
       with standard log levels (DEBUG, INFO, WARNING, ERROR, CRITICAL).
    #. **Structured Formatting**: Implements customizable log formats with timestamp,
       severity level, source component, and structured message content.
    #. **Configuration Integration**: Leverages the ``log`` configuration section
       from ``StepPublisherPklConfig`` to enable consistent setup across components.
    #. **Utility Methods**: Offers utility methods like ``setup_logging()`` for initial
       configuration and ``get_logger()`` for retrieving appropriately configured
       logger instances.

The ``StepLogger`` component ensures that the STEP Publisher Pickle maintains comprehensive
logging capabilities to support monitoring, debugging, and operational insights, particularly
for tracking multi-vehicle publishing operations and timing-sensitive position updates.

Exceptions
^^^^^^^^^^

The exception handling components provide a structured error handling mechanism
for the STEP Publisher Pickle architecture. They define custom exceptions tailored
to the specific error conditions that can occur during publisher operations.

Key aspects include:

    #. **Exception Hierarchy**: Establishes a well-organized hierarchy, all deriving from
       ``StepPublisherPklError`` (the package's base exception):

        * ``StepCliError``: Specialized exception for CLI-specific errors such as
          argument parsing, command execution failures, and configuration loading issues
        * ``LoaderError``: Raised by a ``FileLoader`` when a file does not match, or cannot
          be parsed as, the format that loader handles; wraps the underlying cause
          (``OSError``, Pydantic ``ValidationError``, ``UnpicklingError``, etc.).
          ``Scenario.load_data()`` catches this to try the next candidate loader.
        * ``ShutdownRequestedError``: Internal signal raised to unwind ``_main_async``'s
          ``TaskGroup`` once a graceful shutdown has been requested via
          SIGINT/SIGTERM/SIGBREAK; never raised across module boundaries.

    #. **Error Classification**: Categorizes errors into distinct types such as:

        * CLI argument and configuration errors
        * MQTT broker connection failures
        * Scenario/loader data parsing errors
        * Message publishing failures

    #. **Integration with Logging**: Collaborates with the ``StepLogger`` component to
       ensure that exceptions are properly logged with appropriate severity levels.

All exception classes are O(1) in time and space: plain marker subclasses of ``Exception``
with no added fields or logic.

Main Application (__main__)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The main application module provides the command-line interface and orchestrates the
asynchronous publishing workflow. It implements the primary execution logic that
coordinates all other components.

Key features of the main application include:

    #. **Command-Line Interface**: Provides comprehensive CLI with options for:

        * ``--version``/``-v``: Display version information
        * ``--conf_schema``/``-s``: Generate JSON configuration schema
        * ``--conf_template``/``-t``: Generate configuration template
        * ``--config``/``-c`` and ``--instance``/``-i``: Load configuration and run publisher

    #. **Environment-Based Credentials**: ``_get_mqtt_credential()`` loads a ``.env`` file
       via ``load_dotenv()`` and reads ``MQTT_URL``, ``MQTT_PORT``, ``MQTT_USERNAME``, and
       ``MQTT_PASSWORD`` from the environment into an ``MqttCredential`` (see :doc:`usage`).
    #. **Asynchronous Task Orchestration**: Uses ``asyncio.TaskGroup`` to manage
       concurrent publisher tasks for multiple vehicles, enabling simultaneous
       publishing while maintaining individual vehicle timing; time O(v)/space O(v) for task
       creation, where v is the number of vehicles.
    #. **Exit Code Management**: Defines standard exit codes through the ``ExitCode`` enum:

        * OK (0): Successful execution
        * USAGE (1): Command-line usage error
        * ERROR (2): Runtime error
        * ABORTED (3): User interruption or signal

    #. **Signal Handling**: Implements cross-platform signal handling:

        * Windows: SIGBREAK support (via ``WindowsOsShutdownState``)
        * Unix: SIGINT/SIGTERM support (Ctrl+C / termination)

    #. **Publisher Task Management**: The ``_publisher_run()`` coroutine manages
       individual vehicle publishing by:

        * Consuming a vehicle's messages via ``scenario.pop_message(vehicle_id)``
        * Publishing CAM/CPM/DENM messages through ``client.client_publish_its_message()``
        * Calculating sleep intervals using ``ItsTime.time_difference()``
        * Maintaining realistic timing based on scenario timestamps

    #. **Resource Management**: Utilizes async context managers (``async with``)
       for automatic cleanup of MQTT connections and other resources.
    #. **Event Loop Configuration**: On Windows, uses ``SelectorEventLoop`` for
       optimal compatibility with asyncio operations.

The main application serves as the entry point and coordinator, bringing together
configuration, scenario data, MQTT communication, and logging to deliver a
complete integration between JSONL/pickle/GPX scenario data and the STEP platform.
