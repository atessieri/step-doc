Architecture
============

This document describes the architecture of the STEP Publisher Pickle, a Python package
for publishing vehicle position data to the STEP (Safer Transport for Europe Platform)
using JSONL, Pickle (PKL), or GPX formatted scenario files. It simulates real-world Connected
and Autonomous Vehicle (CAV) messaging by publishing CAM, CPM, and DENM ITS messages to an
MQTT broker with realistic timing and multi-vehicle support.

Overview
--------

The STEP Publisher Pickle serves as an example implementation for testing and development
within the STEP ecosystem, showcasing how to integrate vehicle trajectory data with the STEP
cloud infrastructure. It loads vehicle trajectory/ITS message data from JSONL, pickle, or GPX
scenario files (auto-detected per file, see :doc:`input_files`) and publishes CAM, CPM, and
DENM messages to the STEP MQTT broker with realistic timing and multi-vehicle support. The run
ends on its own once every vehicle has published all its messages.

The package is split into a small number of modules:

    * ``__main__``: command-line entry point. It parses the arguments, writes the
      configuration JSON schema/template on request, loads the configuration and the
      logger, and runs ``StepPublisherApp`` through ``AppRunner``.
    * ``step_publisher_app``: the ``StepPublisherApp`` workload (the STEP broker connection,
      the scenario and one publisher task per vehicle) and the ``ExitCode`` enumeration.
    * ``step_broker``: the ``StepBroker`` MQTT gateway (publish only).
    * ``scenario``: the ``Scenario`` loader and per-vehicle message queue, and the
      ``TimeReference`` named tuple.
    * ``loaders``: the pluggable ``FileLoader`` implementations (``JsonlLoader``,
      ``PickleActorLoader``, ``PickleCameraLoader``, ``GpxLoader``).
    * ``step_publisher_pkl_config``: the Pydantic configuration models.
    * ``step_exception``: the ``StepPublisherPklError`` exception hierarchy.

Library
-------

The STEP Publisher Pickle project leverages several key libraries to provide robust ITS
message communication capabilities:

**Core Dependencies:**

    #. **Pydantic**: Used extensively for configuration management and data
       validation throughout the system. The ``StepPublisherPklConfig`` class and its nested
       configuration models rely on Pydantic's ``BaseModel`` for type-safe configuration
       loading, validation, and JSON schema generation.

    #. **step_cloud_schemas**: Provides standardized data schemas for ITS messages (CAM,
       CPM, and DENM), including ``ItsMessageRoot``/``CamDataV1``/``CpmDataV1``/
       ``DenmDataV1``. It also provides the runtime used by the STEP Publisher Pickle:

        * ``AppRunner``/``AbstractApp``: asyncio application runner with a cooperative
          shutdown on ``SIGINT``/``SIGTERM`` (``SIGINT``/``SIGBREAK`` on Windows)
        * ``StepLogger``/``LogConfig``: logger factory and logging configuration
        * ``ItsTime``: ITS timestamps and time differences, used to rewrite the message
          times and to compute the publishing intervals
        * ``MessageId``, ``GenericMessageType``, ``TrafficParticipantType`` and
          ``IS_WINDOWS``

    #. **step_lib**: Core library providing fundamental components including:

        * ``AsyncComManager``/``AsyncComManagerParams``: base class for asynchronous
          MQTT communication management and its parameters
        * ``FacilityMessage``, ``CamMessageV1``, ``CpmMessageV1``, ``DenmMessageV1``:
          ITS message handling and encoding functionality
        * MQTT utilities including ``MqttQoS`` enumerations and ``PublishTopicParams``
        * ``GpsLocation`` and ``GeoNetworkAddress`` components
        * ``TLSParameters``: picklable TLS/SSL security parameters
        * ``MqttCredential``: the MQTT broker host, port and authentication, read
          from the environment by ``from_env()``

    #. **aiomqtt**: Asynchronous MQTT client library with TLS support for
       non-blocking message publishing

    #. **paho-mqtt**: MQTT protocol implementation providing QoS controls

    #. **python-dotenv** (through step_lib): ``MqttCredential.from_env()`` loads the
       ``.env`` file found in the current working directory (or an ancestor of it) into the
       environment before the credential is read

    #. **sortedcontainers**: Backs each vehicle's per-station message queue
       (``SortedList``, ordered by ``its_time``) inside ``Scenario``.

    #. **gpx**: Parses GPX track files for ``GpxLoader``.

This library ecosystem enables the STEP Publisher Pickle to provide a type-safe,
highly configurable solution for simulating vehicle trajectory data within the STEP platform.

Components
----------

The architecture follows a modular design pattern that separates concerns between process
lifecycle, MQTT communication, scenario/loader data management, and configuration. This
enables flexibility and maintainability in the system design.

Main Components:

    #. **main / AppRunner**: CLI entry point and process runner (``AppRunner`` from the
       ``step_cloud_schemas`` library)
    #. **AbstractApp**: Abstract workload class (from the ``step_cloud_schemas`` library)
       that ``StepPublisherApp`` derives from
    #. **StepPublisherApp**: Workload of the program: scenario loading and one concurrent
       publisher task per vehicle
    #. **StepBroker**: Gateway class for MQTT communication with the STEP broker
    #. **Scenario**: Vehicle trajectory/ITS message loader and per-vehicle message queue
    #. **FileLoader implementations**: Pluggable parsers (JSONL, pickle actor, pickle
       camera, GPX) used by ``Scenario.load_data()``
    #. **StepPublisherPklConfig**: Configuration management for the publisher
    #. **MqttCredential**: MQTT broker host, port and credentials read from the environment
       (from the ``step_lib`` library)
    #. **StepLogger**: Logging utilities used by the publisher (from the
       ``step_cloud_schemas`` library)
    #. **StepException**: Custom exceptions for error handling

Entry Point and AppRunner
^^^^^^^^^^^^^^^^^^^^^^^^^

``step_publisher_pkl.__main__.main()`` is the console script entry point. It:

    #. Builds a default ``StepLogger`` logger (stderr, WARNING) and an
       ``AppRunner[ExitCode]``, before parsing the arguments. On Windows the runner uses
       ``asyncio.SelectorEventLoop``, because the default ``ProactorEventLoop`` does not
       implement ``add_reader``/``add_writer``, which ``aiomqtt`` relies on.
    #. Prints the help and returns ``ExitCode.USAGE`` when no argument is given.
    #. Writes the configuration JSON schema (``-s/--conf_schema``) and/or the
       configuration template (``-t/--conf_template``) to the given directories (created
       if missing).
    #. Raises ``StepCliError`` when only one of ``-c/--config`` and ``-i/--instance``
       is given.
    #. With both, validates the configuration file into ``StepPublisherPklConfig``, rebuilds
       the logger from ``config.log`` with the instance name, force-writes the program and
       library versions (``step_cloud_schemas``, ``step_lib``), builds ``StepPublisherApp``
       (which reads the MQTT credential from the environment, see
       `Environment Variables`_) and runs it with ``AppRunner.run()``, returning its exit
       code.

``AppRunner`` (from ``step_cloud_schemas``) owns the process-wide plumbing: the
``asyncio.Runner``, the loop exception handler, ``sys.unraisablehook`` and the shutdown
signal handlers. It runs ``StepPublisherApp.work()`` next to a shutdown watcher task in a
``TaskGroup``: when a shutdown signal arrives the watcher raises an internal
``_ShutdownRequestedError``, the ``TaskGroup`` cancels ``work`` wherever it is and, once
every task has unwound, ``StepPublisherApp.on_shutdown()`` is called with the signal.

``main()`` maps the outcome to an ``ExitCode``:

    * ``OK`` (0): success: every message published, or only schema/template generation
      requested, including ``-h/--help`` and ``-v/--version``
    * ``USAGE`` (1): no argument, an invalid or unknown option, or ``StepCliError``
      (logged as a plain error line)
    * ``ERROR`` (2): any other unhandled exception, logged with its traceback: an invalid
      configuration file, a missing or invalid environment variable (``ValueError`` raised
      by the ``StepPublisherApp`` constructor, see `Environment Variables`_), or an error
      raised by ``work`` (e.g. a broker connection error), wrapped in an ``ExceptionGroup``
    * ``ABORTED`` (3): shutdown signal (returned by ``on_shutdown``) or
      ``KeyboardInterrupt``

Application Runtime (step_cloud_schemas)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. note::
   ``AppRunner`` and ``AbstractApp`` are not part of the ``step_publisher_pkl`` package: they
   are imported from the external ``step_cloud_schemas`` dependency, shared by the STEP
   programs. Only their public interface, the part used by the STEP Publisher Pickle, is
   described here.

The two classes split a long-running program in two parts: the process-wide plumbing (event
loop, signal handlers, exception hooks), owned by ``AppRunner``, and the workload, supplied by
the program as an ``AbstractApp`` subclass. ``R`` is the program's result type: for the STEP
Publisher Pickle, ``ExitCode``.

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - Class
     - Role
   * - ``AbstractApp[R]``
     - Abstract base class of a workload run by ``AppRunner``. It declares the two methods
       ``AppRunner`` needs and holds no state (empty ``__slots__``, so a subclass declares its own).
   * - ``AppRunner[R]``
     - Singleton that runs an ``AbstractApp`` on a new event loop until it ends or a shutdown
       signal stops it.

The STEP Publisher Pickle does not use ``ReconnectingApp`` (the reconnecting ``AbstractApp``
subclass of ``step_cloud_schemas``): its workload publishes a finite scenario, and a broker
error ends the run instead of being retried.

The class diagram below shows the public interface of the two classes and how
``StepPublisherApp`` plugs into them:

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      !theme plain
      skinparam classAttributeIconSize 0

      package "step_cloud_schemas" #LightGray {

         class "AppRunner[R]" as AppRunner <<singleton>> {
            +__init__(logger_param : Logger, loop_factory = None, exception_handler = None, unraisable_handler = None)
            +logger : Logger <<property>>

**AbstractApp: public interface**

   * ``async work() -> R`` (abstract): The workload, called once per run as a task of the
     ``AppRunner`` ``TaskGroup``; it returns the result when it ends on its own. On a shutdown
     signal it is cancelled at the ``await`` it is suspended on, so it has to be
     cancellation-safe. ``StepPublisherApp.work()`` returns ``ExitCode.OK`` once every
     publisher task has finished.
   * ``on_shutdown(stop_signal: Signals) -> R`` (abstract): Called by ``AppRunner`` after a
     shutdown signal stopped ``work``, once every task has unwound (the resources held by ``work``
     are already released); it runs on the event loop thread and cannot ``await``. Its value is
     the result of the run. ``StepPublisherApp`` logs the signal name and returns
     ``ExitCode.ABORTED``.

**AppRunner: public interface**

   * ``AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None)``:

        - ``logger_param``: Logger used by the default exception and unraisable handlers.
        - ``loop_factory``: Factory of the event loop created by every ``run``, forwarded to
          ``asyncio.Runner``; ``None`` uses the asyncio default loop. The STEP Publisher Pickle
          passes ``asyncio.SelectorEventLoop`` on Windows (``IS_WINDOWS``), because the default
          ``ProactorEventLoop`` lacks the ``add_reader``/``add_writer`` that ``aiomqtt`` needs.
        - ``exception_handler``: Event loop exception handler; ``None`` logs the exception on
          the logger.
        - ``unraisable_handler``: Installed as ``sys.unraisablehook``; ``None`` logs the exception
          on the logger.

     The constructor installs the process-wide hooks (signal handlers, ``sys.unraisablehook``): it
     is called from the main thread as early as possible, which is why ``main()`` builds it before
     parsing the arguments, so that a signal received before ``run`` is still handled. Being a
     singleton, only the first construction takes effect; the arguments of later calls are ignored.
   * ``logger`` (property): The logger given to the constructor.
   * ``run(app: AbstractApp[R]) -> R``: Opens an ``asyncio.Runner``, installs the exception handler
     and the shutdown handlers (``SIGINT``/``SIGTERM`` on POSIX, ``SIGINT``/``SIGBREAK`` on
     Windows), then runs ``app.work()`` next to a shutdown watcher in a ``TaskGroup``. It returns
     the value of ``app.work()`` when the workload ends on its own, or the value of
     ``app.on_shutdown(stop_signal)`` when a shutdown signal stops it. Any other exception raised
     by ``work`` propagates wrapped in an ``ExceptionGroup``, which ``main()`` logs and maps to
     ``ExitCode.ERROR``.

   A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only
   sets an event, the watcher task turns it into an exception, and the ``TaskGroup`` cancels
   ``work`` at the ``await`` it is suspended on.

StepPublisherApp
^^^^^^^^^^^^^^^^

``StepPublisherApp`` (``step_publisher_app.py``) is the ``AbstractApp[ExitCode]`` subclass
(step_cloud_schemas, see `Application Runtime (step_cloud_schemas)`_) run by ``AppRunner``.
It holds the state shared by ``work`` and ``on_shutdown``: the instance name (also used as the
MQTT client instance name), the ``StepPublisherPklConfig``, the logger and the
``MqttCredential``. The module also defines the ``ExitCode`` enumeration.

Key responsibilities of ``StepPublisherApp`` include:

    #. **Credential Loading**: The constructor calls step_lib ``MqttCredential.from_env()``
       once (``MQTT_URL``, ``MQTT_PORT``, ``MQTT_USERNAME``, ``MQTT_PASSWORD``), see
       `Environment Variables`_. The URL and port are required (``ValueError`` otherwise);
       the username and password are optional, an empty value counting as unset. Reading
       them at construction rather than in ``work()`` makes a missing variable end the
       program before the event loop is started: raised before ``AppRunner.run()``, the
       ``ValueError`` ends it with ``ExitCode.ERROR``.
    #. **Asynchronous Task Orchestration**: ``work()`` opens a ``StepBroker`` and, nested in
       its context, a ``TaskGroup``; it builds a ``Scenario`` with the four loaders
       (``JsonlLoader``, ``PickleActorLoader``, ``PickleCameraLoader``, ``GpxLoader``), the
       ``stationsBlacklist`` and the ``waitTimeBeforeStarting`` of the configuration, loads
       the ``inputFiles`` and creates one ``_publisher_run()`` task per vehicle. The broker
       only disconnects once the group has unwound.
    #. **Publisher Task**: ``_publisher_run()`` consumes the vehicle's messages with
       ``scenario.pop_message(vehicle_id)``; for each one it computes the delta between the
       message time and the current ``ItsTime``, sleeps for it when positive (converted from
       milliseconds to seconds) and publishes the message with
       ``client_publish_its_message()``.
    #. **End of Run**: ``work()`` returns ``ExitCode.OK`` once every publisher task has
       published all its messages. An exception raised by a publisher task cancels the other
       tasks and propagates wrapped in an ``ExceptionGroup``: there is no reconnection.
    #. **Shutdown**: ``on_shutdown()`` only logs the signal and returns
       ``ExitCode.ABORTED``; the publisher tasks are cancelled and the broker disconnected by
       the ``async with`` blocks of ``work()``. The messages not yet published are dropped.
    #. **Exit Code Management**: Defines standard exit codes through the ``ExitCode`` enum:

        * OK (0): Successful execution
        * USAGE (1): Invalid command-line usage
        * ERROR (2): General execution error
        * ABORTED (3): Process interrupted by signal

``work()`` is time O(s log s) and space O(s), where s is the total number of messages loaded
and published across all vehicles (excluding the wall-clock time spent sleeping and on the
network): every message is held in memory until it is published.

StepBroker
^^^^^^^^^^

The ``StepBroker`` (module ``step_broker``) is the STEP broker client: it extends the
step_lib ``AsyncComManager`` class and provides an asynchronous interface for secure
message publishing to the STEP ecosystem.

Key responsibilities of ``StepBroker`` include:

    #. **MQTT Connection Parameters**: Builds the ``AsyncComManagerParams`` from the
       ``StepBrokerConfig`` (``mqttProtocol`` timeouts, keepalive, session and queue
       limits, ``cacheDir``) and from the ``MqttCredential`` (host, port, username,
       password); the station ID is not set, so every station of the scenario can be
       published through the same client.
    #. **TLS/SSL**: When ``mqttClient.sslEnable`` is true, builds the picklable
       ``TLSParameters`` (CA certificates, client certificate and key, key password); with
       ``sslVerifyServerCert`` false the server certificate is not verified
       (``ssl.CERT_NONE``) and a warning is logged.
    #. **Publish Topics**: Builds one step_lib ``PublishTopicParams`` per configured
       ``mqttProtocol.publishTopics`` entry, mapping its ``messageType`` through
       ``MessageType.orm_to_enum()`` and its ``qos`` to ``MqttQoS``.
    #. **Message Publication**: ``client_publish_its_message()`` publishes a CAM, CPM, or
       DENM ``FacilityMessage`` with ``publish_its_message()``, using the message's own
       reference latitude/longitude, stamped with the current ``ItsTime``, as the current
       position.
    #. **GeoNetwork Addressing**: Uses a fixed GeoNetwork address with traffic participant
       type ``PASSENGER_CAR`` and a fixed MAC ID (``StepBroker.MAC_ID``).
    #. **Context Management**: Overrides ``__aenter__`` only to return the broker instance
       after the parent ``AsyncComManager`` has connected; ``__aexit__`` is inherited
       unchanged for clean resource handling.

Its ``__init__`` builds one ``PublishTopicParams`` entry per configured publish topic
(time and space complexity O(p), where p is the number of configured publish topics); SSL/TLS
setup is O(1).

Scenario and File Loaders
^^^^^^^^^^^^^^^^^^^^^^^^^

The ``Scenario`` component (module ``scenario``) is responsible for loading vehicle
trajectory/ITS message data and serving it per vehicle in time order. It delegates the
actual file parsing to a sequence of pluggable ``FileLoader`` implementations, received in
its constructor, and has no dependency on any concrete loader.

Key features of ``Scenario`` include:

    #. **Pluggable File Loading**: ``load_data()`` tries, for each input file, the loader(s)
       owning that file's extension first, then every other configured loader as a fallback
       (every loader, in the given order, for an extension no loader owns), until one
       successfully parses the file into ``FacilityMessage`` instances. A file that no
       loader accepts, or that contains no messages, is skipped with a warning.
    #. **Time Reference Management**: Once every file is loaded, maps scenario time to real
       time through the ``TimeReference`` named tuple: the earliest message time across all
       stations becomes the scenario time origin, and the current time plus
       ``wait_time_before_starting_ms`` the real time origin. Every message is then
       rebuilt with its time fields (CAM ``creationTime``; CPM ``referenceTime`` and
       perceived objects' ``measurementTime``/predicted path points; DENM management
       container ``detectionTime``/``referenceTime`` and pre-crash container perceived
       object) rewritten to real time. Messages of an unsupported type are skipped with a
       warning, and a station left with no messages is dropped.
    #. **Per-Station Message Queue**: Manages each station's messages in a ``SortedList``
       (ordered by ``its_time``); messages of station IDs present in ``stations_blacklist``
       are skipped. Every loaded message is held in memory until it is popped.
    #. **Vehicle Enumeration**: ``get_vehicle_ids()`` yields the stations loaded from the
       input files.
    #. **Message Consumption**: ``pop_message(vehicle_id)`` is a generator that removes and
       yields the vehicle's earliest message until its queue is empty.

Four ``FileLoader`` implementations ship with the package (subpackage
``step_publisher_pkl.loaders``), each a self-contained parser for one file format that either
returns the ``FacilityMessage`` instances a file contains or raises ``LoaderError`` if the
file does not match its format. Every concrete loader declares the extension it handles in
the ``EXTENSION`` class attribute, checked by ``FileLoader.__init_subclass__``:

    * ``JsonlLoader`` (``.jsonl``): Parses one JSON-encoded ITS message per line, each
      validating as an ``ItsMessageRoot`` (``CamDataV1``, ``CpmDataV1``, or ``DenmDataV1``);
      blank lines are skipped, and the first invalid line rejects the whole file;
      time/space complexity O(l), l = number of lines in the file.
    * ``PickleActorLoader`` (``.pkl``): Parses an unpickled dictionary shaped as
      ``{"trajectories": {"vehicles": {<station_id>: [<point>, ...]}}}`` into CAM messages;
      time/space complexity O(p), p = total number of trajectory points across all vehicles.
    * ``PickleCameraLoader`` (``.pkl``): Parses an unpickled list of dictionaries, each
      directly convertible to a ``CpmDataV1`` (Collective Perception Message); time/space
      complexity O(m), m = number of camera data items in the file.
    * ``GpxLoader`` (``.gpx``): Parses a GPX file whose tracks are named
      ``Path actor <station_id>_<object_id>`` into CAM messages; time/space complexity O(p),
      p = total number of track points across all tracks/segments in the file.

The pickle actor and GPX loaders build their CAM data through the shared
``FileLoader._build_cam_data()`` helper: values are passed to the CAM fields unchanged (no
unit conversion), and every field not derived from a trajectory point is ``None``. See
:doc:`input_files` for the exact file formats accepted.

Across its methods, the worst case of ``Scenario`` (in ``load_data()``/
``_update_time_stations()``) is time O(s log s) and space O(s), where s is the total number
of trajectory points/messages loaded across all input files: each message is inserted into
a sorted collection in O(log s).

StepPublisherPklConfig
^^^^^^^^^^^^^^^^^^^^^^

The ``StepPublisherPklConfig`` component (module ``step_publisher_pkl_config``) is
responsible for configuration management in the STEP Publisher Pickle architecture. Built as
a Pydantic ``BaseModel``, it provides a robust, type-safe mechanism for loading, validating,
and accessing configuration settings throughout the application.

Key features of ``StepPublisherPklConfig`` include:

    #. **JSON Configuration Loading**: ``main()`` loads it from the JSON file given with
       ``-c``/``--config`` through ``model_validate_json()``.
    #. **Type Validation**: Every model is ``strict`` (no type coercion) and
       ``extra="forbid"``, so all configuration values must meet the expected types and
       constraints, preventing configuration errors at runtime. ``templateVersion`` must
       match ``StepConfigVersion.VERSION``.
    #. **Hierarchical Structure**: Organizes configuration in a hierarchical manner, with the
       following top-level fields:

        * ``templateVersion``: Configuration data version, matching ``StepConfigVersion.VERSION``
        * ``inputFiles``: List of paths to the JSONL/Pickle/GPX files to read and publish; at
          least one is required
        * ``stationsBlacklist``: Optional list of station IDs to ignore in the scenario
        * ``waitTimeBeforeStarting``: Time to wait before starting the scenario, in
          milliseconds (0-5000)
        * ``stepBroker`` (``StepBrokerConfig``): MQTT client configuration
          (``MqttClientConfig``: TLS/SSL settings), MQTT protocol configuration
          (``MqttProtocolConfig``: session, timeouts, queues, publish topics), and cache
          directory
        * ``log`` (``LogConfig`` from ``step_cloud_schemas``): Logging configuration
          (handlers, levels, formatting)

    #. **Immutable Configuration**: Every model is ``frozen``, so once loaded at startup the
       configuration is immutable, ensuring consistency throughout the application's lifecycle.
    #. **Default Configuration**: Provides ``get_default()`` static methods (enumerations
       excluded) used to write the configuration template.
    #. **JSON Schema and Template Generation**: ``print_config_schema(path)`` writes
       ``<STEP_CONFIG_SCHEMA>.json`` using the internal ``_ConfigGenerateJsonSchema``
       generator (time/space complexity O(n), n = number of configuration fields);
       ``print_config_example(path)`` writes ``<STEP_CONFIG_SCHEMA>_template.json`` from
       ``get_default()``.

Credentials are deliberately not part of ``StepPublisherPklConfig``: step_lib
``MqttCredential`` is a frozen dataclass (``mqtt_url``, ``mqtt_port``, ``mqtt_username``,
``mqtt_password``), filled from environment variables by its ``from_env()`` method when
``StepPublisherApp`` is built, so secrets are not embedded in the persisted configuration
document. Its ``__post_init__`` rejects an empty URL and a port outside the 1-65535 range.

Environment Variables
^^^^^^^^^^^^^^^^^^^^^

The MQTT broker address and credentials are the only settings not taken from the JSON
configuration file: they are read from the environment, so that secrets are never written to
a configuration document.

.. list-table::
   :header-rows: 1
   :widths: 22 12 22 44

   * - Variable
     - Required
     - Read by
     - Description
   * - ``MQTT_URL``
     - yes
     - step_lib ``MqttCredential``
     - MQTT broker host name or IP address
   * - ``MQTT_PORT``
     - yes
     - step_lib ``MqttCredential``
     - MQTT broker port (1-65535); usually 8883 with TLS
       (``stepBroker.mqttClient.sslEnable`` true), 1883 without
   * - ``MQTT_USERNAME``
     - no
     - step_lib ``MqttCredential``
     - Broker username; unset or empty connects anonymously
   * - ``MQTT_PASSWORD``
     - no
     - step_lib ``MqttCredential``
     - Broker password; ignored, with a WARNING, when ``MQTT_USERNAME`` is not set

How they are read:

    #. ``StepPublisherApp.__init__()`` calls ``MqttCredential.from_env()`` once, before
       ``AppRunner.run()``.
    #. ``from_env()`` first loads the ``.env`` file found in the **current working
       directory** or its nearest parent (``load_dotenv(find_dotenv(usecwd=True))``): what
       counts is the directory ``step_publisher_pkl`` is launched from, not the directory of
       the installed package. Without a ``.env`` file only the environment is read.
    #. A variable already set in the environment (shell, container) wins over the ``.env``
       file: ``load_dotenv`` only adds missing variables.
    #. An empty username or password counts as unset.
    #. The host, the port and whether a username is set are logged at INFO level; the
       username and the password never are.
    #. A missing ``MQTT_URL``/``MQTT_PORT``, a non-integer or out-of-range port, or an empty
       host raise ``ValueError``; ``main()`` logs it with its traceback and returns
       ``ExitCode.ERROR``.

Credentials that the broker rejects are not detected here but on connection, by
``StepBroker``: the error propagates out of ``work()`` and ends the run with
``ExitCode.ERROR``, without retrying.

The repository ships a commented template,
:download:`env/.env.example <env/.env.example>`: download it, save it as ``.env`` in the
directory ``step_publisher_pkl`` is launched from and fill in the values. ``.env`` is listed
in ``.gitignore``; only the template is versioned. See :ref:`step_publisher_pkl_credentials`
for the file format and the alternatives to the file.

StepLogger
^^^^^^^^^^

``StepLogger`` is provided by the ``step_cloud_schemas`` library (not implemented within
step_publisher_pkl itself) and is used by the STEP Publisher Pickle to build and configure
its ``logging.Logger``. ``main()`` first creates a default logger, then, once the
configuration is loaded, rebuilds it from the ``log`` section of ``StepPublisherPklConfig``
with the instance name, and force-writes the program, ``step_cloud_schemas`` and ``step_lib``
versions.

Key features of ``StepLogger`` include:

    #. **Multiple Handler Types**: Builds loggers with one or more of the following
       handlers, each independently configurable via ``LogConfig``:

        * ``stream``: writes to stderr
        * ``null``: discards all log records
        * ``file``: writes to a single log file (append or overwrite)
        * ``sizeFileRotate``: rotates the log file once it exceeds a configured size
        * ``timeFileRotate``: rotates the log file at a configured time interval

       Rotated log files are automatically compressed.
    #. **UTC Timestamp Formatting**: All log timestamps are rendered in UTC regardless of
       the local system timezone.
    #. **Log Level Management**: Supports the standard log levels (DEBUG, INFO,
       WARNING, ERROR, CRITICAL) per handler and a global logger level.
    #. **Public API**: Exposes two classmethods:

        * ``get_logger(name, config, instance_name)``: builds and returns a configured
          ``Logger``. If ``config`` is ``None``, it falls back to a single stderr
          stream handler at WARNING level. File-based handlers require
          ``instance_name`` to build the log filename.
        * ``logger_force_write(logger, msg)``: temporarily elevates the logger and all
          its handlers to INFO to guarantee a message is emitted (used for the
          startup/version banners), then restores the original levels.

StepException
^^^^^^^^^^^^^

step_publisher_pkl defines a minimal exception hierarchy in ``step_exception.py`` (three
plain classes, O(1) in time and space, with no added fields or logic):

    #. **StepPublisherPklError**: Base exception of the STEP Publisher Pickle. A plain
       subclass of ``Exception`` with no additional attributes.
    #. **StepCliError**: Subclass of ``StepPublisherPklError`` raised for command line
       misuse in ``main()`` (only one of ``-c/--config`` and ``-i/--instance``). ``main()``
       logs it as a plain error line (no traceback) and returns ``ExitCode.USAGE``.
    #. **LoaderError**: Subclass of ``StepPublisherPklError`` raised by a ``FileLoader``
       when a file does not match, or cannot be parsed as, the format that loader handles;
       it wraps the underlying cause (``OSError``, Pydantic ``ValidationError``,
       ``UnpicklingError``, etc.). ``Scenario.load_data()`` catches it to try the next
       candidate loader.

The graceful shutdown signal is not part of this hierarchy: it is the internal
``_ShutdownRequestedError`` of ``AppRunner`` (``step_cloud_schemas``), which never leaves
that module.

Sequence Diagrams
-----------------

The sequence diagrams below illustrate the application lifecycle and the message publishing
flow of the STEP Publisher Pickle. These diagrams show the sequence of interactions between
components and the temporal flow of operations as messages move through the system.

Sequence Diagram - Lifecycle
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The following sequence diagram depicts the startup, the run and the graceful shutdown:
``main`` builds ``AppRunner`` first, then ``StepPublisherApp``, which reads the MQTT
credential from the environment, and hands it to ``AppRunner``; ``work()`` returns
``ExitCode.OK`` once every publisher task has finished, an error raised by ``work()`` ends the
run with ``ExitCode.ERROR``, while a shutdown signal cancels ``work()`` and returns
``on_shutdown()``.

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      @startuml

      participant "main" as Main
      participant "AppRunner" as Runner
      participant "StepPublisherApp" as App
      participant "StepBroker" as Broker

      Main -> Runner : AppRunner[ExitCode](logger, loop_factory)
      Main -> Main : StepPublisherPklConfig.model_validate_json()
      Main -> App : StepPublisherApp(instance_name, config, logger)
      App -> App : MqttCredential.from_env()
      note right of App
         .env loaded first; a missing or invalid
         variable raises ValueError and main()
         returns ExitCode.ERROR before run()
      end note
      Main -> Runner : run(app)
      Runner -> App : work() (TaskGroup with shutdown watcher)
      App -> Broker : async with StepBroker(...)
      Broker -> Broker : MQTT CONNECT
      App -> App : load scenario, one _publisher_run() task per vehicle

      alt every publisher task finished
         App -> Broker : exit context (disconnect)
         App --> Runner : ExitCode.OK
      else error (e.g. broker connection)
         App --> Runner : raise ExceptionGroup
         Runner --> Main : ExceptionGroup
         note right of Main
            Logged with traceback,
            ExitCode.ERROR
         end note
      else SIGINT / SIGTERM (SIGBREAK on Windows)
         Runner -> App : cancel work()
         App -> Broker : exit context (disconnect)
         Runner -> App : on_shutdown(stop_signal)
         App --> Runner : ExitCode.ABORTED
      end
      Runner --> Main : ExitCode

      @enduml

Sequence Diagram - ITS Message Publishing from Scenario Files
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The following sequence diagram depicts the complete process of publishing CAM/CPM/DENM
messages from JSONL, pickle, or GPX scenario data to the STEP MQTT broker, inside
``StepPublisherApp.work()``: the loading of vehicle trajectories/messages via the configured
FileLoaders, the timing intervals computed with ItsTime, and the concurrent publishing for
multiple vehicles in a TaskGroup.

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      @startuml

      participant "StepPublisherApp" as App
      participant "Scenario" as Scenario
      participant "FileLoaders" as Loaders
      participant "StepBroker" as Broker
      participant "STEP MQTT Broker" as MQTT
      participant "Scenario Files" as PKL

      App -> Broker : async with StepBroker(...)
      Broker -> MQTT : connect
      note over App
         TaskGroup nested in the
         broker context
      end note
      App -> Scenario : load_data(inputFiles)
      loop For each input file
         Scenario -> Loaders : loaders by extension, then fallback
         Loaders -> PKL : parse JSONL/pickle/GPX file
         Loaders --> Scenario : FacilityMessage list (or LoaderError)
      end
      Scenario -> Scenario : rewrite times to real time
      Scenario --> App : data loaded

      App -> Scenario : get_vehicle_ids()
      Scenario --> App : [vehicle_id_1, vehicle_id_2, ...]

      loop For each vehicle_id
         App -> App : create _publisher_run(vehicle_id) task
      end

      note over App
         Tasks run concurrently
         in the TaskGroup
      end note

      loop For each message of the vehicle
         App -> Scenario : pop_message(vehicle_id)
         Scenario --> App : FacilityMessage (CAM/CPM/DENM)
         App -> App : delta = message time - now
         alt delta > 0
            App -> App : asyncio_sleep(delta)
         end
         App -> Broker : client_publish_its_message(message)
         Broker -> MQTT : publish ITS message
      end

      App -> Broker : exit context (disconnect)
      App --> App : ExitCode.OK

      @enduml
