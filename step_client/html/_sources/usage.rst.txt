STEP Client Usage Guide
=======================

Introduction
------------

STEP Client is a Python package designed to facilitate communication between 
the STEP (Safer Transport for Europe Platform) MQTT broker and Redis streams for 
ITS (Intelligent Transport Systems) message processing. This guide walks 
through the different ways to use the STEP Client, from basic configuration 
to advanced usage patterns.

Prerequisites
-------------

Before using the STEP Client, make sure you have:

    #. Python 3.13 or higher installed
    #. Access to a STEP MQTT broker
    #. A Redis server for stream processing (required)
    #. The step_client package installed in your environment

Installation
------------

You can install the STEP Client package using pip:

.. code-block:: bash

   $pip install --extra-index-url https://gitlab.automotive.vodafone.com/api/v4/projects/961/packages/pypi/simple step_client

Or if you're using a development version:

.. code-block:: bash

    pip install -e /path/to/step_client

Basic Concepts
--------------

STEP Client operates as a bridge between MQTT messaging and 
Redis streams, specifically designed for ITS message exchange. 
Key concepts include:

    * **StepClientApp**: Workload run by ``AppRunner`` (step_cloud_schemas); it bridges the
      STEP broker and the Redis streams and reconnects after any non-fatal failure
    * **StepBroker**: Gateway component that handles MQTT communication with the STEP broker
    * **StepClientConfig**: Configuration management for the client
    * **StepRedisPool/StepClientRedisStream**: Redis integration for message queuing
    * **ITS Messages**: Standard message formats like CAM (Cooperative Awareness Messages),
      DENM (Decentralized Environmental Notification Messages) and CPM (Collective Perception Messages)

Configuration
-------------

STEP Client requires configuration for both MQTT and Redis connections. The
configuration is managed through a JSON file, while the broker and Redis
addresses and credentials are read from environment variables (see
`Environment Variables`_).

Creating a Configuration File
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

To create a default configuration template:

.. code-block:: bash

    step_client --conf_template my_config_template_dir

This creates the directory (if missing) and writes
``step_client_config_v1_schema_template.json`` in it, a template that you can
customize for your specific needs.

Key Configuration Parameters
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

* **MQTT Client Configuration** (config file, ``MqttClientConfig``):

  * sslEnable: Whether to use TLS/SSL encryption
  * sslClientCertFile / sslClientKeyFile / sslClientKeyFilePassword: Client certificate
    settings for mutual TLS
  * sslCaCertsFile: CA certificate bundle used to verify the broker
  * sslVerifyServerCert: Whether to verify the broker's certificate

* **MQTT Broker and Redis Server Connection**: host, port and credentials are read from
  environment variables, not from the config file (see `Environment Variables`_).

* **MQTT Protocol Configuration**:

  * keepalive: Keep-alive interval in seconds
  * cleanStart: Whether to start with a clean session
  * maxSubscriptionQos: QoS used for every subscription (a granted QoS above it is an error)
  * subscriptionTopics: List of topics to subscribe to (``messageType`` is informational:
    received messages are routed by their decoded type)
  * publishTopics: Configuration for topics to publish to (the client only publishes DENMs)

* **Redis Configuration** (required):

  * connection: Redis connection settings (database, socket, TLS, health check, pool and
    retry settings, step_redis ``RedisConnection``)
  * streams: Configuration for Redis streams (``input`` and ``outputs.adapter`` /
    ``outputs.producer``)
  * ``connection.socketTimeout`` (seconds) must be at least ``streams.input.waitTimeout``
    + 5000 ms, otherwise the configuration is rejected: the blocking stream read must end
    before the socket times out

* **General Configuration**:

  * stationId: Station identification number
  * latitude / longitude: Position of the station in degrees
  * reconnectInterval: Time in seconds between reconnection attempts

  The instance name is not part of the configuration file; it is supplied on the
  command line via ``-i/--instance`` (required together with ``-c/--config``).

Environment Variables
---------------------

The MQTT client TLS settings and the Redis connection settings (database, timeouts,
keepalive, SSL, pool) are kept in the JSON configuration file, in the
``stepBroker.mqttClient`` and ``redis.connection`` sections, while the MQTT broker and
Redis server host, port and credentials are read from the environment, so that secrets
are never written to the configuration file:

.. list-table::
   :header-rows: 1
   :widths: 25 15 60

   * - Variable
     - Required
     - Description
   * - ``MQTT_URL``
     - yes
     - MQTT broker host name or IP address
   * - ``MQTT_PORT``
     - yes
     - MQTT broker port (1-65535); usually 8883 with TLS
       (``stepBroker.mqttClient.sslEnable`` true), 1883 without
   * - ``MQTT_USERNAME``
     - no
     - Username for broker authentication; unset or empty connects anonymously
   * - ``MQTT_PASSWORD``
     - no
     - Password for broker authentication; ignored, with a warning, when
       ``MQTT_USERNAME`` is not set
   * - ``REDIS_URL``
     - yes
     - Redis server host name or IP address
   * - ``REDIS_PORT``
     - yes
     - Redis server port (1-65535); usually 6380 with TLS
       (``redis.connection.sslEnable`` true), 6379 without
   * - ``REDIS_USERNAME``
     - no
     - ACL username; unset or empty authenticates as the ``default`` user (or not at
       all when the password is unset too)
   * - ``REDIS_PASSWORD``
     - no
     - Password, when the server requires authentication

The ``StepClientApp`` constructor reads them once, through step_lib
``MqttCredential.from_env`` and step_redis ``RedisCredential.from_env``, before the
first connection cycle. A missing ``*_URL`` or ``*_PORT``, a non-integer or
out-of-range port, or an empty host raise ``ValueError``: since the credentials are
read outside the reconnect loop, a misconfiguration stops the program with exit code
``2`` (``ERROR``) instead of being retried forever.

**How the variables are read.**

* Each ``from_env`` first loads the ``.env`` file found in the **current working
  directory** or in its nearest parent directory (``find_dotenv(usecwd=True)``): what
  counts is the directory ``step_client`` is launched from, not the directory of the
  installed package. Without a ``.env`` file only the environment is read.
* A variable already set in the environment **wins** over the ``.env`` file:
  ``load_dotenv`` adds the missing variables and never overrides an existing one.
* An empty username or password counts as unset.
* The host and port are logged at INFO level, together with whether a username is
  set; the username and the password never are.

**Format of the .env file.**

* One ``KEY=VALUE`` line per variable, no ``export`` needed;
* ``#`` starts a comment;
* quote a value only if it contains spaces or ``#`` (``REDIS_PASSWORD="a #b"``);
* keep the file out of version control: ``.env`` is listed in ``.gitignore``, only
  the ``.env.example`` template is versioned.

**Template.** ``doc/source/env/.env.example`` is a commented template:

.. literalinclude:: env/.env.example
   :language: bash

Download the template: :download:`.env.example <env/.env.example>`
(save it as ``.env`` in the directory ``step_client`` is launched from). From a
checkout of the repository:

.. tab:: bash

   .. code-block:: bash

       cp doc/source/env/.env.example .env

.. tab:: PowerShell

   .. code-block:: powershell

       Copy-Item doc/source/env/.env.example .env

**Alternatives to the file.** Variables set in the shell or by a container runtime
take precedence over ``.env``:

.. tab:: bash

   .. code-block:: bash

       export MQTT_URL=broker.example.com
       export MQTT_PORT=8883
       export REDIS_URL=redis.example.com
       export REDIS_PORT=6380

.. tab:: PowerShell

   .. code-block:: powershell

       $env:MQTT_URL = "broker.example.com"
       $env:MQTT_PORT = "8883"
       $env:REDIS_URL = "redis.example.com"
       $env:REDIS_PORT = "6380"

.. tab:: Docker Compose

   .. code-block:: yaml

       services:
         step_client:
           env_file: .env          # or, one by one:
           environment:
             MQTT_URL: broker.example.com
             MQTT_PORT: "8883"
             REDIS_URL: redis.example.com
             REDIS_PORT: "6380"

.. note::

   Credentials that the server rejects are detected on connection, not when the
   variables are read: a CONNACK refusing the MQTT authentication or authorization
   (step_lib ``StepLibMqttFatalError``) and rejected Redis credentials, an ACL denial,
   a missing SSL file or an untrusted certificate (step_redis ``StepRedisFatalError``)
   cannot be fixed by reconnecting, so the program ends with exit code ``2``
   (``ERROR``) instead of retrying forever.

Running STEP Client as a Service
--------------------------------

To run the STEP Client as a standalone service:

.. code-block:: bash

    step_client --config /path/to/config.json --instance my_instance

This will start the client, which will:

    #. Read the MQTT and Redis credentials from the environment (and the ``.env`` file,
       see `Environment Variables`_)
    #. Open the Redis connection pool
    #. Connect to the configured STEP MQTT broker
    #. Subscribe to the specified topics
    #. Process ITS messages between MQTT and Redis

The DENM messages read from the Redis input stream keep the stationId set by the producer: it
should equal ``stationId`` of the client configuration, otherwise their echo is not filtered and,
with a DENM subscription, the client forwards its own DENMs back to the producer stream.

Command-Line Options
--------------------

The STEP Client supports several command-line options:

    * ``--config``, ``-c``: Path to configuration file
    * ``--instance``, ``-i``: Instance name (required together with ``--config``)
    * ``--conf_schema``, ``-s``: Write the configuration JSON schema into a directory
    * ``--conf_template``, ``-t``: Generate a configuration template into a directory
    * ``--version``, ``-v``: Show version information
    * ``--help``, ``-h``: Show help information
