Architecture
============

This document describes the architecture of the STEP Client, a Python package 
for communicating with the STEP (Safer Transport for Europe Platform) MQTT broker 
to receive and send ITS (Intelligent Transport Systems) messages.

Overview
--------

The STEP Client serves as an interface between the STEP MQTT broker and Redis 
streams for message processing. It provides functionality for subscribing to MQTT topics, 
publishing ITS messages, and managing message queuing.

Library
-------

The STEP Client project leverages several key libraries to provide robust ITS message 
communication and Redis integration capabilities:

**Core Dependencies:**

    #. **Pydantic**: Used extensively for configuration management and data 
       validation throughout the system. The ``StepClientConfig`` class and its nested 
       configuration models rely on Pydantic's ``BaseModel`` for type-safe configuration 
       loading, validation, and JSON schema generation.

    #. **step_cloud_schemas**: Provides standardized data schemas for ITS 
       messages including CAM (Cooperative Awareness Messages), DENM (Decentralized 
       Environmental Notification Messages) and CPM formats. Contains CloudEvents 
       message structures used for message conversion between different system components.

    #. **step_lib**: Core library providing fundamental components including:
       
        * ``AsyncComManager``: Base class for asynchronous communication management
        * ``FacilityMessage``: ITS message handling and encoding/decoding functionality  
        * MQTT utilities including ``MqttQoS`` enumerations and ``PublishTopicParams``
        * GPS location and GeoNetwork addressing components
        * TLS/SSL security parameter management

    #. **step_redis**: Redis integration library providing:
       
        * ``StepRedisPool``: Connection pooling for Redis database connections
        * ``StepRedisStream``: Stream handling for message queuing and distribution
        * Redis stream parameter management and configuration
    
    #. **aiomqtt**: Asynchronous MQTT client library with TLS support
    
    #. **paho-mqtt**: MQTT protocol implementation providing subscription options and QoS controls

This library ecosystem enables the STEP Client to provide a comprehensive, type-safe, 
and highly configurable solution for ITS message communication within the STEP platform.

Components
----------

The architecture follows a modular design pattern that separates concerns between MQTT 
communication, Redis integration, and configuration management. This enables flexibility 
and maintainability in the system design.

Main Components:

    #. **StepBroker**: Gateway class for MQTT communication with the STEP broker
    #. **StepClientConfig**: Configuration management for the client
    #. **StepRedisPool/StepClientRedisStream**: Redis integration
       for message queuing (from the ``step_redis`` library)
    #. **StepLogger**: Logging utilities used by the STEP client (from the
       ``step_cloud_schemas`` library)
    #. **StepException**: Custom exceptions for error handling

StepBroker
^^^^^^^^^^

The ``StepBroker`` (STEP Gateway) is a core component of the STEP Client architecture
that manages MQTT communication with the STEP broker. Extending the ``AsyncComManager`` class, 
it provides an asynchronous interface for secure, reliable message exchange between 
client applications and the STEP ecosystem.

Key responsibilities of ``StepBroker`` include:

    #. **MQTT Connection Management**: Establishes and maintains secure TLS/SSL connections 
       to the MQTT broker, handling reconnection and error scenarios.
    #. **Topic Subscription**: Manages subscriptions to MQTT topics with configurable 
       Quality of Service (QoS) levels to receive ITS messages from the STEP broker.
    #. **Message Publication**: Publishes ITS messages to the STEP broker with
       appropriate topic selection and message encoding.
    #. **ITS Message Encoding/Decoding**: Encodes and decodes ITS messages to and from
       ASN.1 wire format via ``step_lib.FacilityMessage``. CloudEvents envelope
       conversion is handled separately, by ``StepClientRedisStream`` and the
       application's message-dispatch logic in ``__main__.py``, not by ``StepBroker``
       itself.
    #. **Integration with Redis**: Coordinates with ``StepClientRedisStream`` to queue
       received messages in Redis streams and publish client-generated messages.
    #. **Context Management**: Implements asynchronous context management through 
       ``__aenter__`` and ``__aexit__`` methods for clean resource handling.

The ``StepBroker`` class uses asynchronous patterns throughout to ensure non-blocking operations, 
making it suitable for high-throughput messaging environments in ITS applications.

StepClientConfig
^^^^^^^^^^^^^^^^

The ``StepClientConfig`` component is responsible for configuration management in the STEP Client architecture. 
Built as a Pydantic ``BaseModel``, it provides a robust, type-safe mechanism for loading,
validating, and accessing configuration settings throughout the application. 

Key features of ``StepClientConfig`` include:

    #. **JSON Configuration Loading**: Loads configuration settings from a JSON file specified 
       at startup, providing a centralized source of configuration for all components.
    #. **Type Validation**: Leverages Pydantic's validation system to ensure all configuration 
       values meet the expected types and constraints, preventing configuration errors at runtime.
    #. **Hierarchical Structure**: Organizes configuration in a hierarchical manner, with nested 
       models for different aspects of the system:
       
        * MQTT Client configuration (connection parameters, security settings)
        * MQTT Protocol configuration (QoS, topic management)
        * Redis Client configuration (for message broker integration)
        * Logging configuration (handlers, levels, formatting)
    
    #. **Immutable Configuration**: Once loaded at startup, the configuration becomes immutable, 
       ensuring consistency throughout the application's lifecycle.
    #. **Configuration Sharing**: Acts as a central repository of configuration settings that 
       is shared with other components, providing a single source of truth for system settings.
    #. **Default Configuration**: Provides ``get_default()`` methods to generate sensible 
       default configurations when specific values are not provided.
    #. **JSON Schema Generation**: Supports generating JSON schemas for configuration 
       validation through the ``StepConfigGenerateJsonSchema`` utility class.

The design of ``StepClientConfig`` emphasizes immutability and strong validation, helping prevent 
configuration-related issues during runtime while providing a clear, structured 
approach to configuration management.

StepRedis
^^^^^^^^^

The step_redis library provides the foundational Redis integration layer for the STEP 
ecosystem, enabling asynchronous Redis connectivity and stream-based message processing. 
This library implements a reusable framework for Redis Streams communication that is 
extended by multiple STEP components including ``step_client``, ``step_adapter``, 
``step_producer``, and ``step_crash_prediction``.

**Library Architecture**

The step_redis library is organized around two core base classes and five specialized
implementations:

**Base Classes:**

    #. **StepRedisPool**: Extends redis-py's ``BlockingConnectionPool`` to provide 
       asynchronous connection pooling with SSL/TLS support, TCP keepalive configuration, 
       and async context manager protocol.
    
    #. **StepRedisStream**: Abstract base implementation for Redis Streams operations, 
       providing message publishing, consumer group management, stream creation, and 
       asynchronous message consumption.

**Specialized Implementations:**

    #. **StepClientRedisStream**: Handles DENM (Decentralized Environmental Notification 
       Messages) for the STEP Client
    
    #. **StepAdapterRedisStream**: Manages CAM (Cooperative Awareness Messages) and CPM 
       (Collective Perception Messages) for the STEP Adapter
    
    #. **StepProducerRedisStream**: Processes DENM and station collision arrays for the 
       STEP Producer
    
    #. **StepCrashPredictionRedisStream**: Handles crash prediction data streams

    #. **StepMonitoringRedisStream**: Publishes forecasted trajectory data and
       receives monitoring messages for the STEP Monitoring service

**StepRedisPool - Connection Management**

``StepRedisPool`` provides comprehensive connection pooling capabilities:

**Configuration Parameters:**

The pool is configured through ``StepRedisPoolParams``, a frozen dataclass containing:

    * **Connection Settings**: host, port, database index, username, password
    * **Socket Configuration**: connection timeout, keepalive settings (idle time, 
      interval, probe count)
    * **SSL/TLS Support**: optional SSL with client certificates, CA certificates, 
      and certificate verification
    * **Pool Behavior**: maximum connections, connection timeout, health check interval
    * **Protocol Settings**: Redis protocol version (default: 3)

**SSL/TLS Implementation:**

When SSL is enabled (``ssl_enable=True``), the pool uses ``SSLConnection`` with:

    * TLS version 1.2 as minimum (``ssl_min_version=PROTOCOL_TLSv1_2``)
    * Optional client certificate authentication (``ssl_keyfile``, ``ssl_certfile``)
    * CA certificate validation (``ssl_ca_certs``)
    * Hostname verification when certificates are required
    * Optional client key password protection

**TCP Keepalive:**

All connections (SSL and non-SSL) configure TCP keepalive using:

    * ``TCP_KEEPIDLE``: Seconds before sending keepalive probes
    * ``TCP_KEEPINTVL``: Interval between keepalive probes
    * ``TCP_KEEPCNT``: Maximum number of keepalive probes

**Resource Management:**

The pool implements the async context manager protocol:

    * ``__aenter__``: Returns the pool instance and logs entry
    * ``__aexit__``: Calls ``aclose()`` to properly disconnect all connections and 
      release resources

**StepRedisStream - Stream Operations**

``StepRedisStream`` provides the core Redis Streams functionality:

**Configuration:**

Configured through ``StepRedisStreamParams``, a frozen dataclass with validation:

    * ``stream_id``: Stream identifier (minimum 1 character)
    * ``group_id``: Consumer group identifier (optional, required for consumption)
    * ``wait_timeout_ms``: Blocking read timeout in milliseconds (optional, required 
      for consumption)
    * ``max_length``: Maximum stream length for XADD approximate trimming (optional, 
      required for publishing)
    * ``consumer_name``: Unique consumer identifier (minimum 1 character)
    * ``ttl_seconds``: Time-to-live for stream key expiration (optional, positive integer)

**Stream Creation:**

The ``create_input_stream()`` method:

    #. Creates a Redis stream if it doesn't exist (``mkstream=True``)
    #. Creates a consumer group using ``XGROUP CREATE``
    #. Handles ``BUSYGROUP`` error if the group already exists
    #. Updates stream TTL if ``ttl_seconds`` is configured

**Message Publishing:**

The ``publish_message(message: str)`` method:

    #. Validates that ``max_length`` is configured
    #. Uses ``XADD`` to append the message to the stream
    #. Stores message as ``{"payload": message}`` field
    #. Applies approximate trimming with ``maxlen`` to maintain stream size
    #. Returns the message ID assigned by Redis

**Message Consumption:**

The ``receive_message()`` async generator:

    #. Validates that ``group_id`` and ``wait_timeout_ms`` are configured
    #. Uses ``XREADGROUP`` with blocking reads to consume messages
    #. Reads from consumer group position ``">"`` (only new messages)
    #. Sets ``noack=True`` for automatic message acknowledgment
    #. Processes one message at a time (``count=1``)
    #. Yields message payload as string
    #. Updates stream TTL after each read attempt if configured
    #. Handles ``RedisTimeoutError`` when no messages arrive within timeout

**TTL Management:**

The stream provides methods for Time-To-Live management:

    * ``update_stream_ttl(ttl_seconds)``: Sets stream expiration using ``EXPIRE`` command
    * ``get_stream_ttl()``: Returns remaining TTL using ``TTL`` command (returns -2 
      if stream doesn't exist, -1 if no expiration set)

**Health Checking:**

The ``ping()`` method sends a ``PING`` command to verify Redis connectivity.

**StepClientRedisStream - STEP Client Integration**

The STEP Client uses ``StepClientRedisStream`` from the step_redis package, which 
extends ``StepRedisStream`` for DENM message handling:

**DENM Message Publishing:**

The ``publish_denm_message(message: DenmDataV1)`` method:

    #. Wraps the DENM in a CloudEvents envelope (``ClientCloudEventsDenmDataV1``)
    #. Assigns a unique UUID identifier
    #. Sets the source to the consumer name
    #. Uses CloudEvents spec version 1.0
    #. Sets message type to ``ClientMessageType.DENM``
    #. Adds schema reference (``ClientDataSchemaType.DENM_DATA_V1_SCHEMA``)
    #. Sets content type to ``application/json``
    #. Adds ITS timestamp
    #. Serializes to JSON using Pydantic's ``model_dump_json()``
    #. Publishes to the configured stream

**DENM Message Reception:**

The ``receive_client_message()`` async generator:

    #. Calls the parent ``receive_message()`` method
    #. Validates received JSON using ``ClientCloudEventsJsonRoot.model_validate_json()``
    #. Enforces strict validation (``strict=True``)
    #. Yields validated CloudEvents message objects

**Usage in STEP Client Application**

The STEP Client application (__main__.py) demonstrates the integration pattern:

**Outbound Flow (Redis → MQTT):**

In ``_stream_receive_run()``:

    #. Creates ``StepClientRedisStream`` with configuration from ``RedisStreams.input``
    #. Calculates TTL as 2× the wait timeout
    #. Creates the input stream with consumer group
    #. Continuously receives messages using ``receive_client_message()``
    #. Extracts DENM data from CloudEvents envelope
    #. Publishes to MQTT broker via ``step_broker.client_publish_its_message()``

**Inbound Flow (MQTT → Redis):**

In ``_step_receive_run()``:

    #. Creates ``StepAdapterRedisStream`` for CAM and CPM messages
    #. Creates ``StepProducerRedisStream`` for DENM messages
    #. Receives ITS messages from ``step_broker.its_messages`` async generator
    #. Pattern matches message type (CAM, CPM, or DENM)
    #. Publishes to appropriate stream using ``publish_cam_message()``,
       ``publish_cpm_message()``, or ``publish_denm_message()``

**Redis Connection Pool Setup:**

The application creates ``StepRedisPool`` by:

    #. Converting ``RedisConnection`` config to ``StepRedisPoolParams``
    #. Including all SSL/TLS settings from configuration
    #. Setting up TCP keepalive parameters
    #. Specifying maximum connections and timeouts
    #. Using async context manager for proper resource cleanup

**Consumer Group Strategy:**

The STEP Client implements the following consumer group pattern:

    * **Consumer Name**: Uses the instance name as the unique consumer identifier
    * **Group ID**: Configured in ``RedisStreams.input.groupId``
    * **Stream Position**: Reads from ``">"`` to receive only new messages
    * **Acknowledgment**: Uses ``noack=True`` for automatic acknowledgment
    * **Horizontal Scaling**: Multiple instances with the same group ID share message 
      load
    * **Independent Processing**: Different group IDs can consume the same stream 
      independently

**Configuration Integration:**

Redis configuration is managed through ``StepClientConfig``:

    * **RedisConnection**: Host, port, credentials, SSL settings, socket parameters
    * **RedisStreams**: Input and output stream configurations
    * **RedisStreamInput**: Stream ID, group ID, wait timeout for incoming messages
    * **RedisStreamOutputs**: Separate configurations for adapter and producer streams
    * **RedisStreamOutput**: Stream ID and max length for each output stream

**Performance Characteristics:**

The Redis integration in STEP Client provides:

    * **Asynchronous I/O**: Non-blocking operations using redis-py's asyncio support
    * **Connection Reuse**: Persistent connections maintained through the pool
    * **Approximate Trimming**: XADD with ``approximate=True`` for efficient stream 
      size management
    * **Blocking Reads**: XREADGROUP blocks until messages arrive or timeout expires, 
      avoiding polling overhead
    * **Automatic Decoding**: ``decode_responses=True`` eliminates manual byte-to-string 
      conversion
    * **Health Checks**: Periodic connection health verification at configured intervals
    * **Resource Cleanup**: Proper connection disposal through async context managers

**Error Handling:**

The implementation handles Redis-specific errors:

    * **RedisResponseError**: Catches ``BUSYGROUP`` when consumer group already exists
    * **RedisTimeoutError**: Logged when no messages arrive within timeout period
    * **KeyError**: Handles missing keys in stream response with warnings
    * **ValueError**: Raises when required configuration parameters are missing

Together, the step_redis library and StepClientRedisStream provide a robust, production-ready 
framework for Redis Streams integration in ITS applications, supporting high-throughput 
message processing, reliable delivery, and horizontal scalability through consumer groups.

StepLogger
^^^^^^^^^^

``StepLogger`` is provided by the ``step_cloud_schemas`` library (not implemented within
step_client itself) and is used by the STEP Client to build and configure its
``logging.Logger`` instances. Today it is a thin factory built directly on top of
Python's standard ``logging`` module; a future revision is expected to move the
underlying implementation to the ``loguru`` library while keeping the same
``StepLogger`` interface used by step_client.

Key features of ``StepLogger`` include:

    #. **Multiple Handler Types**: Builds loggers with one or more of the following
       handlers, each independently configurable via ``LogConfig``:

        * ``stream``: writes to stderr
        * ``null``: discards all log records
        * ``file``: writes to a single log file (append or overwrite)
        * ``sizeFileRotate``: rotates the log file once it exceeds a configured size
        * ``timeFileRotate``: rotates the log file at a configured time interval

       Rotated log files are automatically compressed with BZIP2. There is no syslog
       handler.
    #. **UTC Timestamp Formatting**: Uses a custom ``UtcFormatter`` so all log
       timestamps are rendered in UTC regardless of the local system timezone.
    #. **Log Level Management**: Supports the standard log levels (DEBUG, INFO,
       WARNING, ERROR, CRITICAL) per handler and a global logger level, via
       ``LogMode``.
    #. **Configuration Integration**: Driven by the ``LogConfig``/``LogHandlerConfig``
       models (from ``step_cloud_schemas``), which are carried inside
       ``StepClientConfig.log``.
    #. **Public API**: Exposes two classmethods:

        * ``get_logger(name, config, instance_name)``: builds and returns a configured
          ``Logger``. If ``config`` is ``None``, it falls back to a single stderr
          stream handler at WARNING level with the logger itself at INFO. File-based
          handlers require ``instance_name`` to build the log filename, and raise
          ``ValueError`` if it is missing.
        * ``logger_force_write(logger, msg)``: temporarily elevates the logger and all
          its handlers to INFO to guarantee a message is emitted (used by step_client
          for startup/version banners), then restores the original levels.

There is currently no built-in support for syslog, or for attaching structured
context such as component IDs or transaction IDs to log records beyond what the
configured format string exposes (e.g. ``%(module)s``, ``%(funcName)s``).

StepException
^^^^^^^^^^^^^

step_client defines a minimal exception hierarchy in ``step_exception.py``, used to
distinguish STEP Client errors from other unhandled exceptions:

    #. **StepClientError**: Base exception for the STEP Client. A plain subclass of
       ``Exception`` with no additional attributes; it is raised, for example, by
       ``StepBroker.subscribe_execution()`` when a topic subscription fails or its
       returned QoS doesn't match the configured one.
    #. **StepCliError**: Subclass of ``StepClientError`` raised for CLI-specific
       errors in ``main()`` — such as passing ``-c/--config`` without ``-i/--instance``
       or vice versa.

Both classes are message-only exceptions (the message is carried via the standard
``Exception`` args, not a dedicated attribute); there is no structured error context,
error-type classification, or recovery-hint mechanism beyond what the raised message
string conveys. Callers catch and log these via the standard Python exception handling
already used throughout ``__main__.py`` (e.g. the top-level ``except Exception`` in
``main()`` and ``_main_async()``).
