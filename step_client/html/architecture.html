STEP Client

Architecture

This document describes the architecture of the STEP Client, a Python package for communicating with the STEP (Safer Transport for Europe Platform) MQTT broker to receive and send ITS (Intelligent Transport Systems) messages.

Overview

The STEP Client serves as a bridge between the STEP MQTT broker and Redis streams for message processing. It subscribes to MQTT topics and forwards the received CAM/CPM messages to the adapter Redis stream and the DENM messages to the producer Redis stream; in the opposite direction it reads DENM messages from an input Redis stream and publishes them to the STEP broker.

The package is split into a small number of modules:

  • __main__: command-line entry point. It parses the arguments, writes the configuration JSON schema/template on request, loads the configuration and the logger, and runs StepClientApp through AppRunner.

  • step_client_app: the StepClientApp workload (the reconnecting broker/Redis bridge) and the ExitCode enumeration.

  • step_broker: the StepBroker MQTT gateway.

  • step_client_config: the Pydantic configuration models (the MQTT client TLS model MqttClientConfig comes from step_lib and the Redis connection model RedisConnection from step_redis).

  • step_exception: the StepClientError exception hierarchy.

Library

The STEP Client project leverages several key libraries to provide robust ITS message communication and Redis integration capabilities:

Core Dependencies:

  1. Pydantic: Used extensively for configuration management and data validation throughout the system. The StepClientConfig class and its nested configuration models rely on Pydantic’s BaseModel for type-safe configuration loading, validation, and JSON schema generation.

  2. step_cloud_schemas: Provides standardized data schemas for ITS messages including CAM (Cooperative Awareness Messages), DENM (Decentralized Environmental Notification Messages) and CPM formats, and the CloudEvents message structures used for message conversion between system components. It also provides the runtime used by the STEP Client:

    • AppRunner/AbstractApp: asyncio application runner with a cooperative shutdown on SIGINT/SIGTERM (SIGINT/SIGBREAK on Windows)

    • ReconnectingApp: the AbstractApp running cycle() forever, with the reconnect loop and the fatal error handling

    • StepLogger/LogConfig: logger factory and logging configuration

    • LoggingTimer: logging of the processing time of each message

    • ItsTime, MessageId, TrafficParticipantType and IS_WINDOWS

  3. step_lib: Core library providing fundamental components including:

    • AsyncComManager/AsyncComManagerParams: base class for asynchronous MQTT communication management and its parameters

    • FacilityMessage, CamMessageV1, CpmMessageV1, DenmMessageV1: ITS message handling and encoding/decoding functionality

    • MQTT utilities including MqttQoS enumerations and PublishTopicParams

    • GpsLocation and GeoNetworkAddress components

    • TLSParameters: picklable TLS/SSL security parameters

    • MqttClientConfig: the MQTT client TLS settings of the configuration, turned into TLSParameters by to_tls_params()

    • MqttCredential: the MQTT broker host, port and authentication, read from the environment by from_env()

    • StepLibMqttFatalError: the MQTT connection refusals a reconnect cannot fix

  4. step_redis: Redis integration library providing:

    • StepRedisPool/StepRedisPoolParams: connection pooling for Redis

    • StepRedisStream/StepRedisStreamParams: stream handling for message queuing and distribution

    • StepClientRedisStream, StepAdapterRedisStream, StepProducerRedisStream: the CloudEvents-aware streams used by the client

    • RedisConnection/RedisCredential: the Redis connection settings of the configuration and the Redis host, port and authentication read from the environment by RedisCredential.from_env()

    • StepRedisFatalError: the Redis failures a reconnect cannot fix

  5. aiomqtt: Asynchronous MQTT client library with TLS support

  6. paho-mqtt: MQTT protocol implementation providing subscription options and QoS controls

  7. python-dotenv (through step_lib and step_redis): MqttCredential.from_env() and RedisCredential.from_env() load the .env file found in the current working directory (or an ancestor of it) into the environment before the credentials are read

This library ecosystem enables the STEP Client to provide a comprehensive, type-safe, and highly configurable solution for ITS message communication within the STEP platform.

Components

The architecture follows a modular design pattern that separates concerns between process lifecycle, MQTT communication, Redis integration, and configuration management. This enables flexibility and maintainability in the system design.

Main Components:

  1. main / AppRunner: CLI entry point and process runner (AppRunner from the step_cloud_schemas library)

  2. AbstractApp / ReconnectingApp: Abstract workload classes (from the step_cloud_schemas library) that StepClientApp derives from

  3. StepClientApp: Workload bridging the STEP broker and the Redis streams, with reconnect handling

  4. StepBroker: Gateway class for MQTT communication with the STEP broker

  5. StepClientConfig: Configuration management for the client

  6. MqttCredential / RedisCredential: MQTT and Redis credentials read from the environment (from the step_lib and step_redis libraries)

  7. StepRedisPool/StepClientRedisStream: Redis integration for message queuing (from the step_redis library)

  8. StepLogger: Logging utilities used by the STEP client (from the step_cloud_schemas library)

  9. StepException: Custom exceptions for error handling

Entry Point and AppRunner

step_client.__main__.main() is the console script entry point. It:

  1. Builds a default StepLogger logger (stderr, WARNING) and an AppRunner[ExitCode]. On Windows the runner uses asyncio.SelectorEventLoop, because the default ProactorEventLoop does not implement add_reader/add_writer, which aiomqtt’s socket needs to detect the CONNACK response.

  2. Prints the help and returns ExitCode.USAGE when no argument is given.

  3. Writes the configuration JSON schema (-s/--conf_schema) and/or the configuration template (-t/--conf_template) to the given directories.

  4. Raises StepCliError when only one of -c/--config and -i/--instance is given.

  5. With both, validates the configuration file into StepClientConfig, rebuilds the logger from config.log, force-writes the client and library versions (step_cloud_schemas, step_lib, step_redis) and runs StepClientApp with AppRunner.run(), returning its exit code.

AppRunner (from step_cloud_schemas) owns the process-wide plumbing: the asyncio.Runner, the loop exception handler, sys.unraisablehook and the shutdown signal handlers. It runs StepClientApp.work() (inherited from ReconnectingApp) next to a shutdown watcher task in a TaskGroup: when a shutdown signal arrives the watcher raises an internal _ShutdownRequestedError, the TaskGroup cancels work wherever it is and, once every task has unwound, StepClientApp.on_shutdown() is called with the signal.

main() maps the outcome to an ExitCode:

  • OK (0): success (e.g. only schema/template generation was requested), including -h/--help and -v/--version

  • USAGE (1): no argument, an invalid or unknown option, or StepCliError (logged as a plain error line)

  • ERROR (2): any other unhandled exception, logged with its traceback: an invalid configuration file, a missing or invalid environment variable (ValueError raised by the StepClientApp constructor, see Environment Variables), or an error that a reconnect cannot fix (fatal_result())

  • ABORTED (3): shutdown signal (returned by on_shutdown) or KeyboardInterrupt

Application Runtime (step_cloud_schemas)

Note

AppRunner, AbstractApp and ReconnectingApp are not part of the step_client package: they are imported from the external step_cloud_schemas dependency, shared by the STEP programs. Only their public interface, the part used by the STEP Client, is described here.

The three classes split a long-running program in two parts: the process-wide plumbing (event loop, signal handlers, exception hooks), owned by AppRunner, and the workload, supplied by the program as an AbstractApp subclass. R is the program’s result type: for the STEP Client, ExitCode.

Class

Role

AbstractApp[R]

Abstract base class of a workload run by AppRunner. It declares the two methods AppRunner needs and holds no state (empty __slots__, so a subclass declares its own).

ReconnectingApp[R]

Abstract AbstractApp subclass that implements work as a reconnect loop around a connection cycle (cycle), implemented by the program.

AppRunner[R]

Singleton that runs an AbstractApp on a new event loop until it ends or a shutdown signal stops it.

The class diagram below shows the public interface of the three classes and how StepClientApp plugs into them:

AbstractApp: public interface

  • async work() -> R (abstract): The workload, called once per run as a task of the AppRunner TaskGroup; it returns the result when it ends on its own. On a shutdown signal it is cancelled at the await it is suspended on, so it has to be cancellation-safe.

  • on_shutdown(stop_signal: Signals) -> R (abstract): Called by AppRunner after a shutdown signal stopped work, once every task has unwound (the resources held by work are already released); it runs on the event loop thread and cannot await. Its value is the result of the run. StepClientApp logs the signal name and returns ExitCode.ABORTED.

ReconnectingApp: public interface

  • ReconnectingApp(logger, reconnect_interval): logger is used for the start, error and retry messages, reconnect_interval is the number of seconds to wait before the next cycle. StepClientApp passes its own logger and config.reconnectInterval.

  • async cycle() -> None (abstract): Opens the connections and runs the tasks until one of them fails; returns only if every task ends normally, and then the next cycle starts at once. Like work, it has to be cancellation-safe. StepClientApp.cycle() opens the StepRedisPool and the StepBroker and runs the three bridge tasks.

  • fatal_result() -> R (abstract): The result returned by work after an error that a reconnect cannot fix (StepClientApp: ExitCode.ERROR).

  • async work() -> R: Logs Program started, then runs cycle in a loop. When cycle raises:

    • while a shutdown cancellation is in progress, the error is logged at INFO level and CancelledError is restored, so the shutdown goes on without an ERROR traceback;

    • otherwise the error is logged with its traceback, and if it, or any error nested in an ExceptionGroup (as raised by a TaskGroup), is one of the subclass’s fatal error types, work logs a CRITICAL line and returns fatal_result();

    • otherwise work waits reconnect_interval seconds and runs cycle again.

    It never returns otherwise: the loop ends only when AppRunner cancels it.

The fatal error types are the _FATAL_ERRORS class attribute that each subclass sets (StepClientApp: step_redis StepRedisFatalError and step_lib StepLibMqttFatalError); with none set, every error is retried.

AppRunner: public interface

  • AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None):

    • logger_param: Logger used by the default exception and unraisable handlers.

    • loop_factory: Factory of the event loop created by every run, forwarded to asyncio.Runner; None uses the asyncio default loop. The STEP Client passes asyncio.SelectorEventLoop on Windows (IS_WINDOWS), because the default ProactorEventLoop lacks the add_reader/add_writer that aiomqtt needs.

    • exception_handler: Event loop exception handler; None logs the exception on the logger.

    • unraisable_handler: Installed as sys.unraisablehook; None logs the exception on the logger.

    The constructor installs the process-wide hooks (signal handlers, sys.unraisablehook): it is called from the main thread as early as possible, which is why main() builds it before parsing the arguments, so that a signal received before run is still handled. Being a singleton, only the first construction takes effect; the arguments of later calls are ignored.

  • logger (property): The logger given to the constructor.

  • run(app: AbstractApp[R]) -> R: Opens an asyncio.Runner, installs the exception handler and the shutdown handlers (SIGINT/SIGTERM on POSIX, SIGINT/SIGBREAK on Windows), then runs app.work() next to a shutdown watcher in a TaskGroup. It returns the value of app.work() when the workload ends on its own, or the value of app.on_shutdown(stop_signal) when a shutdown signal stops it. Any other exception raised by work propagates wrapped in an ExceptionGroup, which main() logs and maps to ExitCode.ERROR.

A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only sets an event, the watcher task turns it into an exception, and the TaskGroup cancels work at the await it is suspended on.

StepClientApp

StepClientApp (step_client_app.py) is the ReconnectingApp[ExitCode] subclass (step_cloud_schemas, see Application Runtime (step_cloud_schemas)) run by AppRunner. It holds the state shared by every connection cycle: the instance name (also used as the MQTT client instance name and the Redis stream consumer name), the StepClientConfig, the logger, the MqttCredential and the RedisCredential. It implements one connection cycle (cycle()) and the result of a fatal error (fatal_result()); the reconnect loop is the inherited work().

Key responsibilities of StepClientApp include:

  1. Credential Loading: The constructor calls step_lib MqttCredential.from_env() (MQTT_URL, MQTT_PORT, MQTT_USERNAME, MQTT_PASSWORD) and step_redis RedisCredential.from_env() (REDIS_URL, REDIS_PORT, REDIS_USERNAME, REDIS_PASSWORD), see Environment Variables. URLs and ports are required (ValueError otherwise); usernames and passwords are optional, an empty value counting as unset. The credentials are read once at construction rather than in cycle(), because work() retries on every non-fatal exception and a missing variable would never end the program: raised before AppRunner.run(), the ValueError ends it with ExitCode.ERROR.

  2. Connection Cycle: Each cycle() opens a StepRedisPool (at most _REDIS_MAX_CONNECTIONS = 3 connections, parameters built by StepRedisPoolParams.from_connection() from RedisConnection and the RedisCredential) and a StepBroker, then awaits StepBroker.subscribe_execution().

  3. Concurrent Tasks: Runs three tasks in a TaskGroup:

    • _step_receive_run(): STEP broker → adapter/producer Redis streams

    • _stream_receive_run(): input Redis stream → STEP broker

    • _redis_health_check_run(): periodic Redis PING

  4. Message Dispatch: _its_message_dispatch() matches each received ITS payload by type (CamMessageV1, CpmMessageV1, DenmMessageV1) and delegates to _cam_message_manage(), _cpm_message_manage() or _denm_message_manage(), which log the message and publish its payload; messages of unknown type are skipped with a warning. The processing time of each message is logged through a LoggingTimer.

  5. Per-message Failures: A single message that cannot be forwarded does not tear the cycle down. In _step_receive_run() a pydantic.ValidationError raised while building the CloudEvents envelope is logged and the message dropped; in _denm_publish() (input stream → STEP broker) any StepLibError other than StepLibMqttError (encoding, unsupported type, backpressure) is logged and the DENM dropped. Transport failures (Redis errors, StepLibMqttError) still propagate and trigger a reconnect; the message being forwarded at that moment is logged and lost, since both the MQTT subscription and the Redis input stream (read with noack) have already acknowledged it — delivery is at-most-once.

  6. Reconnection: Any exception raised by cycle() is logged by the inherited work() and the next cycle starts after config.reconnectInterval seconds. If the current task is being cancelled (shutdown in progress), a CancelledError is raised instead, without an ERROR traceback, so the shutdown is not turned into a reconnect.

  7. Permanent Errors: An error that a reconnect cannot fix (_FATAL_ERRORS: step_redis StepRedisFatalError - rejected Redis credentials, ACL denial, missing SSL file, untrusted certificate - and step_lib StepLibMqttFatalError - CONNACK refusing the MQTT authentication or authorization) ends the run with fatal_result() (ExitCode.ERROR) instead of retrying forever.

  8. Shutdown: on_shutdown() only logs the signal and returns ExitCode.ABORTED; the pool, the broker and the stream clients are released by their async context managers in cycle().

work() returns only after a fatal error; otherwise it runs until AppRunner cancels it.

StepBroker

The StepBroker (STEP Gateway) is a core component of the STEP Client architecture that manages MQTT communication with the STEP broker. Extending the AsyncComManager class, it provides an asynchronous interface for secure, reliable message exchange between client applications and the STEP ecosystem.

Key responsibilities of StepBroker include:

  1. MQTT Connection Management: Builds the AsyncComManagerParams from the StepBrokerConfig (MQTT protocol settings and publish topics) and the MqttCredential (host, port, username, password). When sslEnable is set, step_lib MqttClientConfig.to_tls_params() builds picklable TLSParameters (the SSLContext is built from them on connect); with sslVerifyServerCert disabled it logs a warning and uses ssl.CERT_NONE.

  2. Topic Subscription: subscribe_execution() subscribes to every configured subscriptionTopics entry with SubscribeOptions built from maxSubscriptionQos (noLocal=False, retainAsPublished=False, retainHandling=RETAIN_DO_NOT_SEND); nothing is subscribed when the list is None.

  3. Message Publication: Publishes ITS messages to the STEP broker with the topics converted from publishTopics into step_lib.PublishTopicParams.

  4. ITS Message Encoding/Decoding: Encodes and decodes ITS messages to and from ASN.1 wire format via step_lib.FacilityMessage. CloudEvents envelope conversion is handled separately, by the step_redis streams and StepClientApp, not by StepBroker itself.

  5. Sender Location: client_publish_its_message() publishes as a stationary station with a fixed road-side-unit GeoNetworkAddress (MAC id = stationId) and a GpsLocation at the configured latitude and longitude, built by _current_position() on every publish so that its timestamp (the GeoNetworking position vector time and the envelope positionTime) is current. It returns True when the message is published and False when step_lib skips it because no publish topic is configured for its type; it logs nothing itself (step_lib logs the publish at INFO and the skip at WARNING).

  6. Context Management: Overrides __aenter__ only to return the broker instance after the parent AsyncComManager has connected; it does not subscribe. subscribe_execution() must be awaited explicitly afterwards (StepClientApp.cycle() does so). __aexit__ is inherited unchanged from the parent AsyncComManager for clean resource handling.

StepBroker has no Redis awareness: forwarding received messages to Redis streams (StepAdapterRedisStream/StepProducerRedisStream) and reading client messages from Redis (StepClientRedisStream) is done by StepClientApp.

The StepBroker class uses asynchronous patterns throughout to ensure non-blocking operations, making it suitable for high-throughput messaging environments in ITS applications.

StepClientConfig

The StepClientConfig component is responsible for configuration management in the STEP Client architecture. Built as a Pydantic BaseModel, it provides a robust, type-safe mechanism for loading, validating, and accessing configuration settings throughout the application.

Key features of StepClientConfig include:

  1. JSON Configuration Loading: Loads configuration settings from a JSON file specified at startup (model_validate_json()), providing a centralized source of configuration for all components.

  2. Type Validation: Every model is strict (no type coercion) and extra="forbid", so all configuration values must meet the expected types and constraints, preventing configuration errors at runtime. templateVersion must match StepConfigVersion.VERSION.

  3. Hierarchical Structure: Organizes configuration in a hierarchical manner, with nested models for different aspects of the system:

    • Top level: templateVersion, stationId, latitude, longitude, reconnectInterval

    • stepBroker (StepBrokerConfig): mqttClient (MqttClientConfig from step_lib, TLS settings), mqttProtocol (MqttProtocolConfig: session, queues, QoS, SubscriptionTopicParams/PublishTopicParams lists) and cacheDir

    • redis (RedisClientConfig): connection (RedisConnection from step_redis) and streams (RedisStreams: input and outputs.adapter/outputs.producer)

    • log (LogConfig from step_cloud_schemas): handlers, levels, formatting

  4. Cross-field Validation: RedisClientConfig checks that connection.socketTimeout (seconds) is at least streams.input.waitTimeout plus READ_TIMEOUT_MARGIN_MS (5000 ms): the blocking XREADGROUP read is bounded by the socket timeout, and a read that times out first drops the connection and loses any message delivered in that instant (the input stream is read with noack). RedisStreamInput.waitTimeout is at least 10000 ms, so the stream TTL (twice waitTimeout) always exceeds the blocking read.

  5. Immutable Configuration: Every model is frozen, so once loaded at startup the configuration is immutable, ensuring consistency throughout the application’s lifecycle.

  6. Configuration Sharing: Acts as a central repository of configuration settings that is shared with other components, providing a single source of truth for system settings.

  7. Default Configuration: Provides get_default() methods to generate sensible default configurations when specific values are not provided.

  8. JSON Schema and Template Generation: print_config_schema(path) writes <STEP_CONFIG_SCHEMA>.json using the internal _ConfigGenerateJsonSchema generator; print_config_example(path) writes <STEP_CONFIG_SCHEMA>_template.json from get_default().

Credentials are deliberately not part of StepClientConfig: step_lib MqttCredential and step_redis RedisCredential are frozen dataclasses, filled from environment variables by their from_env() methods when StepClientApp is built, so secrets are not embedded in the persisted configuration document. Their __post_init__ rejects empty URLs and ports outside the 1-65535 range.

The design of StepClientConfig emphasizes immutability and strong validation, helping prevent configuration-related issues during runtime while providing a clear, structured approach to configuration management.

StepRedis

The step_redis library provides the foundational Redis integration layer for the STEP ecosystem, enabling asynchronous Redis connectivity and stream-based message processing. This library implements a reusable framework for Redis Streams communication that is extended by multiple STEP components including step_client, step_adapter, step_producer, and step_crash_prediction.

Library Architecture

The step_redis library is organized around two core base classes and five specialized implementations:

Base Classes:

  1. StepRedisPool: Extends redis-py’s BlockingConnectionPool to provide asynchronous connection pooling with SSL/TLS support, TCP keepalive configuration, and async context manager protocol.

  2. StepRedisStream: Base implementation for Redis Streams operations (concrete, not abstract), providing message publishing, consumer group management, stream creation, asynchronous message consumption, TTL management and health checking.

Specialized Implementations:

  1. StepClientRedisStream: Handles DENM (Decentralized Environmental Notification Messages) for the STEP Client

  2. StepAdapterRedisStream: Manages CAM (Cooperative Awareness Messages) and CPM (Collective Perception Messages) for the STEP Adapter

  3. StepProducerRedisStream: Processes DENM and station collision arrays for the STEP Producer

  4. StepCrashPredictionRedisStream: Handles crash prediction data streams

  5. StepMonitoringRedisStream: Publishes forecasted trajectory data and receives monitoring messages for the STEP Monitoring service

StepRedisPool - Connection Management

StepRedisPool provides comprehensive connection pooling capabilities:

Configuration Parameters:

The pool is configured through StepRedisPoolParams, a frozen dataclass containing:

  • Connection Settings: host, port, database index, username, password

  • Socket Configuration: connection timeout, keepalive settings (idle time, interval, probe count)

  • SSL/TLS Support: optional SSL with client certificates, CA certificates, and certificate verification

  • Pool Behavior: maximum connections, connection-available timeout, health check interval

  • Protocol Settings: Redis protocol version

  • Retry Behavior: retry_count retries (with jittered exponential backoff) of a command after a ConnectionError only, e.g. when the server closed an idle connection; TimeoutError is deliberately not retried so a blocking XREADGROUP timeout surfaces immediately. 0 disables retries.

SSL/TLS Implementation:

When SSL is enabled (ssl_enable=True), the pool uses SSLConnection with:

  • TLS version 1.2 as minimum (ssl_min_version=ssl.TLSVersion.TLSv1_2)

  • Optional client certificate authentication (ssl_keyfile, ssl_certfile)

  • CA certificate validation (ssl_ca_certs)

  • Hostname verification when certificates are required

  • Optional client key password protection

TCP Keepalive:

All connections (SSL and non-SSL) configure TCP keepalive using:

  • TCP_KEEPIDLE (TCP_KEEPALIVE on macOS): Seconds before sending keepalive probes

  • TCP_KEEPINTVL: Interval between keepalive probes

  • TCP_KEEPCNT: Maximum number of keepalive probes

Resource Management:

The pool implements the async context manager protocol:

  • __aenter__: Returns the pool instance and logs entry (debug level)

  • __aexit__: Calls aclose() to properly disconnect all connections and release resources

StepRedisStream - Stream Operations

StepRedisStream provides the core Redis Streams functionality:

Configuration:

Configured through StepRedisStreamParams, a frozen dataclass with validation:

  • stream_id: Stream identifier (minimum 1 character)

  • group_id: Consumer group identifier (optional, required for consumption)

  • wait_timeout_ms: Blocking read timeout in milliseconds (optional, non-negative, required for consumption)

  • published_message_max_retained: Maximum stream length for XADD approximate trimming (optional, positive integer, required for publishing)

  • consumer_name: Unique consumer identifier (minimum 1 character)

  • ttl_seconds: Time-to-live for stream key expiration (optional, positive integer; when wait_timeout_ms is also set it must be strictly greater than wait_timeout_ms converted to seconds)

Stream Creation:

The create_input_stream() method:

  1. Creates a Redis stream if it doesn’t exist (mkstream=True)

  2. Raises ValueError if group_id is not configured

  3. Creates a consumer group using XGROUP CREATE

  4. Handles BUSYGROUP error if the group already exists

  5. Updates stream TTL if ttl_seconds is configured

Message Publishing:

The publish_message(message: str) method:

  1. Raises ValueError if published_message_max_retained is not configured

  2. Uses XADD to append the message to the stream

  3. Stores message as {"payload": message} field

  4. Applies approximate trimming with maxlen to maintain stream size

  5. Returns None; the message ID assigned by Redis is only logged (debug level)

Message Consumption:

The receive_message() async generator:

  1. Validates that group_id and wait_timeout_ms are configured

  2. Uses XREADGROUP with blocking reads to consume messages

  3. Reads from consumer group position ">" (only new messages)

  4. Sets noack=True for automatic message acknowledgment

  5. Processes one message at a time (count=1)

  6. Yields message payload as string

  7. Updates stream TTL after each read attempt if configured

  8. Handles RedisTimeoutError when no messages arrive within timeout

  9. Recreates the consumer group and retries on a NOGROUP error

TTL Management:

The stream provides methods for Time-To-Live management:

  • update_stream_ttl(ttl_seconds): Sets stream expiration using EXPIRE command

  • get_stream_ttl(): Returns remaining TTL using TTL command (returns -2 if stream doesn’t exist, -1 if no expiration set)

Health Checking:

The ping() method sends a PING command to verify Redis connectivity, logging and re-raising the error (translated by step_redis into StepRedisConnectionError or StepRedisFatalError).

The run_health_check() method loops forever, sleeping for the pool’s health_check_interval seconds and then calling ping(). An interval of 0 disables it (it just blocks). The STEP Client runs it in StepClientApp._redis_health_check_run() as a sibling task in the TaskGroup, so a failed ping cancels the other tasks and triggers the reconnect logic of the inherited StepClientApp.work().

StepClientRedisStream - STEP Client Integration

The STEP Client uses StepClientRedisStream from the step_redis package, which extends StepRedisStream for DENM message handling:

DENM Message Publishing:

The publish_denm_message(message: DenmDataV1) method:

  1. Wraps the DENM in a CloudEvents envelope (ClientCloudEventsDenmDataV1)

  2. Assigns a unique UUID identifier

  3. Sets the source to the consumer name

  4. Uses CloudEvents spec version 1.0

  5. Sets message type to ClientMessageType.DENM

  6. Adds schema reference (ClientDataSchemaType.DENM_DATA_V1_SCHEMA)

  7. Sets content type to application/json

  8. Adds ITS timestamp

  9. Serializes to JSON using Pydantic’s model_dump_json()

  10. Publishes to the configured stream

DENM Message Reception:

The receive_client_message() async generator:

  1. Calls the parent receive_message() method

  2. Validates received JSON using ClientCloudEventsJsonRoot.model_validate_json()

  3. Enforces strict validation (strict=True)

  4. Yields validated CloudEvents message objects; a message failing validation is logged and discarded without stopping the iteration

Usage in STEP Client Application

StepClientApp (step_client_app.py) demonstrates the integration pattern:

Outbound Flow (Redis → MQTT):

In _stream_receive_run():

  1. Creates StepClientRedisStream with configuration from RedisStreams.input (no published_message_max_retained: the stream is only read)

  2. Sets the stream TTL to twice the wait timeout, in seconds, rounded up and at least 1 (max(1, ceil(waitTimeout * 2 / 1000)))

  3. Creates the input stream with consumer group

  4. Continuously receives messages using receive_client_message()

  5. Matches ClientCloudEventsDenmDataV1 and wraps its data in a DenmMessageV1; any other message type is skipped with a warning

  6. Publishes to MQTT broker via step_broker.client_publish_its_message()

Inbound Flow (MQTT → Redis):

In _step_receive_run():

  1. Creates StepAdapterRedisStream for CAM and CPM messages (RedisStreams.outputs.adapter)

  2. Creates StepProducerRedisStream for DENM messages (RedisStreams.outputs.producer)

  3. Receives ITS messages from step_broker.its_messages async generator

  4. Pattern matches message type (CAM, CPM, or DENM)

  5. Publishes to appropriate stream using publish_cam_message(), publish_cpm_message(), or publish_denm_message()

Redis Connection Pool Setup:

StepClientApp.cycle() creates StepRedisPool at each connection cycle by:

  1. Converting the RedisConnection config and the RedisCredential to StepRedisPoolParams (step_redis StepRedisPoolParams.from_connection(), which logs a warning when TLS is enabled without server certificate verification)

  2. Including all SSL/TLS settings from configuration

  3. Setting up TCP keepalive parameters

  4. Limiting the pool to _REDIS_MAX_CONNECTIONS (3) connections: one held by the blocking stream read, the others for publishing and the health check

  5. Using async context manager for proper resource cleanup

Consumer Group Strategy:

The STEP Client implements the following consumer group pattern:

  • Consumer Name: Uses the instance name as the unique consumer identifier

  • Group ID: Configured in RedisStreams.input.groupId

  • Stream Position: Reads from ">" to receive only new messages

  • Acknowledgment: Uses noack=True for automatic acknowledgment

  • Horizontal Scaling: Multiple instances with the same group ID share message load

  • Independent Processing: Different group IDs can consume the same stream independently

Configuration Integration:

Redis configuration is managed through StepClientConfig:

  • RedisConnection: Database index, socket parameters, SSL settings, health check interval, connection-available timeout, protocol and retry count (host, port and credentials come from step_redis RedisCredential)

  • RedisStreams: Input and output stream configurations

  • RedisStreamInput: Stream ID, group ID, wait timeout for incoming messages

  • RedisStreamOutputs: Separate configurations for adapter and producer streams

  • RedisStreamOutput: Stream ID and max length for each output stream

Performance Characteristics:

The Redis integration in STEP Client provides:

  • Asynchronous I/O: Non-blocking operations using redis-py’s asyncio support

  • Connection Reuse: Persistent connections maintained through the pool

  • Approximate Trimming: XADD with approximate=True for efficient stream size management

  • Blocking Reads: XREADGROUP blocks until messages arrive or timeout expires, avoiding polling overhead

  • Automatic Decoding: decode_responses=True eliminates manual byte-to-string conversion

  • Health Checks: Periodic connection health verification at configured intervals

  • Resource Cleanup: Proper connection disposal through async context managers

Error Handling:

The implementation handles Redis-specific errors:

  • RedisResponseError: Catches BUSYGROUP when consumer group already exists

  • RedisResponseError (NOGROUP): The consumer group is recreated and the read retried

  • RedisTimeoutError: Logged when no messages arrive within timeout period

  • RedisConnectionError: Retried by the pool up to retry_count times; from ping()/run_health_check() it is logged and re-raised

  • Every redis-py error leaving a step_redis method is translated into StepRedisFatalError (a reconnect cannot fix it: the run ends with ExitCode.ERROR), StepRedisConnectionError or StepRedisCommandError

  • KeyError: Handles missing keys in stream response with warnings

  • ValueError: Raises when required configuration parameters are missing

Together, the step_redis library and StepClientRedisStream provide a robust, production-ready framework for Redis Streams integration in ITS applications, supporting high-throughput message processing, reliable delivery, and horizontal scalability through consumer groups.

StepLogger

StepLogger is provided by the step_cloud_schemas library (not implemented within step_client itself) and is used by the STEP Client to build and configure its logging.Logger instances. Today it is a thin factory built directly on top of Python’s standard logging module; a future revision is expected to move the underlying implementation to the loguru library while keeping the same StepLogger interface used by step_client.

Key features of StepLogger include:

  1. Multiple Handler Types: Builds loggers with one or more of the following handlers, each independently configurable via LogConfig:

    • stream: writes to stderr

    • null: discards all log records

    • file: writes to a single log file (append or overwrite)

    • sizeFileRotate: rotates the log file once it exceeds a configured size

    • timeFileRotate: rotates the log file at a configured time interval

    Rotated log files are automatically compressed with BZIP2. There is no syslog handler.

  2. UTC Timestamp Formatting: Uses a custom UtcFormatter so all log timestamps are rendered in UTC regardless of the local system timezone.

  3. Log Level Management: Supports the standard log levels (DEBUG, INFO, WARNING, ERROR, CRITICAL) per handler and a global logger level, via LogMode.

  4. Configuration Integration: Driven by the LogConfig/LogHandlerConfig models (from step_cloud_schemas), which are carried inside StepClientConfig.log.

  5. Public API: Exposes two classmethods:

    • get_logger(name, config, instance_name): builds and returns a configured Logger. If config is None, it falls back to a single stderr stream handler at WARNING level with the logger itself at INFO. File-based handlers require instance_name to build the log filename, and raise ValueError if it is missing.

    • logger_force_write(logger, msg): temporarily elevates the logger and all its handlers to INFO to guarantee a message is emitted (used by step_client for startup/version banners), then restores the original levels.

There is currently no built-in support for syslog, or for attaching structured context such as component IDs or transaction IDs to log records beyond what the configured format string exposes (e.g. %(module)s, %(funcName)s).

StepException

step_client defines a minimal exception hierarchy in step_exception.py, used to distinguish STEP Client errors from other unhandled exceptions:

  1. StepClientError: Base exception for the STEP Client. A plain subclass of Exception with no additional attributes; it is raised by StepBroker.subscribe_execution() when the number of subscription results differs from the number of configured topics, or a granted QoS exceeds the configured maxSubscriptionQos. Raised by StepClientApp.cycle(), it is handled by the inherited work() like any other non-fatal exception: logged, then a reconnect after reconnectInterval.

  2. StepCliError: Subclass of StepClientError raised for CLI-specific errors in main() — such as passing -c/--config without -i/--instance or vice versa. main() logs it as a plain error line (no traceback) and returns ExitCode.USAGE.

The graceful shutdown signal is no longer part of this hierarchy: it is the internal _ShutdownRequestedError of AppRunner (step_cloud_schemas), which never leaves that module.

All classes are message-only exceptions (the message is carried via the standard Exception args, not a dedicated attribute); there is no structured error context, error-type classification, or recovery-hint mechanism beyond what the raised message string conveys. Callers catch and log these via the standard Python exception handling (the top-level except clauses in main() and the reconnect loop of the inherited StepClientApp.work()).
