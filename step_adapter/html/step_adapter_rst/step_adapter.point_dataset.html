step_adapter.point_dataset module

Position dataset management with cubic spline interpolation.

This module provides a comprehensive framework for managing position datasets with advanced interpolation capabilities. It serves as a high-level interface for processing tracking data, performing temporal validation, and generating smooth position trajectories using cubic spline interpolation techniques.

Module Purpose:

The module is designed for real-time tracking applications where raw position measurements need to be processed into smooth, regularly-sampled position data suitable for analysis, visualization, or further processing. It handles common challenges in position data processing including temporal irregularities, data validation, and cross-actor data contamination prevention through multi-stage validation and bounded resource management.

Architecture Overview:

The module implements a stateful processing pipeline with two main components:

  1. PointDatasetConfig: Configuration and validation dataclass that defines processing parameters including:

    • Input queue size bounds (5-30 points)

    • Temporal constraints (period limits, local time deviation)

    • Output frequency configuration (100-1000ms nominal period)

    • Period deviation tolerance for interpolation

  2. PointDataset: Main dataset manager that orchestrates:

    • Position validation and temporal consistency checking

    • Cubic spline interpolation processing

    • Actor metadata management (vehicle dimensions)

    • Multi-path execution based on temporal characteristics

The architecture follows a layered approach where PointDataset provides a user-friendly interface while delegating core interpolation work to internal methods that handle array population, spline construction, and position list generation.

Performance Characteristics:

Let:

  • n = input queue size (bounded by input_max_point_number)

  • k = number of interpolated output points

  • m = current queue length at operation time

Time Complexity Analysis:

  • add_point() Method:

    • Overall: O(n + k*log(n) + k) worst case

    • No Interpolation: O(1)

    • Interpolation: O(n + k*log(n) + k) for 10-20% of calls

    • Components:

      • Coherence validation: O(1) including haversine distance

      • Spline construction: O(n) for 3 dimensions

      • Spline evaluation: O(k*log(n)) binary search + polynomial evaluation

      • Position list construction: O(k)

  • Property Accessors: O(1) constant time for all properties

  • Configuration Validation: O(1) constant time operations

Space Complexity Analysis:

  • Persistent Storage: O(n) - Configuration-bounded:

    • Input queue: ~258n bytes for position records

    • Pre-allocated numpy arrays: ~32(n+1) bytes

    • Total: ~290n bytes per actor

  • Transient Allocations (per add_point() call):

    • Fast path: O(1) → ~30 bytes (80-90% of calls)

    • Interpolation path: O(n + k) → ~(128n + 290k) bytes (10-20% of calls)

  • Overall System: O(n + k) with bounded growth

    • n ≤ input_max_point_number (typically 5-30)

    • k ≤ input_max_period_ms / output_nominal_period_ms (typically 1-30)

Memory Growth Characteristics:

  • Bounded Growth: Memory usage limited by configuration parameters, not by total processing duration

  • Predictable Footprint: Maximum memory calculated from input_max_point_number and output_nominal_period_ms

  • No Memory Leaks: Automatic cleanup via deque maxlen and garbage collection of transient allocations

  • Typical Footprint:

    • n=30, k=20: ~8.7KB persistent, ~10KB transient peak

    • n=10, k=50: ~2.9KB persistent, ~16KB transient peak

Key Features:

  • Temporal Coherence Validation: Multi-stage validation ensuring positions are temporally consistent (minimum/maximum period, local time deviation, speed coherence)

  • Cubic Spline Interpolation: Generates smooth C² continuous trajectories between irregular position measurements using scipy’s CubicSpline

  • Configurable Output Frequency: Supports flexible interpolation rates from 1Hz to 10Hz or higher based on configuration

  • Actor Metadata Management: Tracks and updates actor dimensions (length, width) alongside position data

  • Temporal Consistency: Validates and maintains proper time sequencing, rejecting out-of-order or temporally inconsistent data

  • Gap Detection and Recovery: Automatically handles large data gaps by clearing history to prevent unrealistic interpolation across discontinuities

  • Resource Bounded Processing: Guarantees predictable memory and computational resource usage through configuration-driven limits

  • Multi-Path Execution: Optimizes for high-frequency regular data (fast path) while handling edge cases (validation failures, interpolation needs)

Thread Safety: This module is NOT thread-safe. Applications requiring concurrent access from multiple threads must implement external synchronization mechanisms:

  • Recommended strategies:

    • Thread-local instances (one PointDataset per thread per actor)

    • External mutex/lock for shared instance

    • Message passing architecture for concurrent systems

  • Consider using thread-local storage or explicit locking strategies for multi-threaded environments

Performance Recommendations:

  • Configuration Tuning: Balance input_max_point_number vs memory usage and output_nominal_period_ms based on downstream consumer needs

  • Memory Monitoring: Monitor memory usage in long-running applications, especially with high-frequency configurations or many actors

  • Logging Levels: Adjust logging verbosity in production to minimize I/O overhead from validation warnings

  • Profiling: Monitor interpolation path frequency and validation failure rates for optimization opportunities

Notes

The interpolation quality is directly dependent on the density and temporal distribution of input position points. Applications should ensure sufficient point coverage within the configured period constraints for optimal results.

Large temporal gaps exceeding input_max_period_ms will trigger history clearing, which is necessary to prevent unrealistic interpolation across discontinuous data but may result in temporary output gaps. Consider application-level buffering for continuous output requirements.

class step_adapter.point_dataset.PointDataset(actor_par: ActorId, config: PointDatasetConfig, logger: Logger)[source]

Bases: object

Dataset manager for position tracking with cubic spline interpolation.

This class provides a comprehensive, high-level interface for managing position data from a specific actor (vehicle/object), performing cubic spline interpolation to generate smooth position trajectories at regular time intervals. It orchestrates position validation, temporal consistency checking, interpolation processing, and actor metadata management in a unified, cohesive system.

Architecture & Design:

PointDataset implements a stateful processing pipeline that maintains:

  1. Input Queue: Bounded deque storing recent position measurements

  2. Interpolation Buffers: Pre-allocated numpy arrays for spline computation

  3. Actor Metadata: Vehicle dimensions (length, width) tracking

  4. Configuration: Immutable parameters controlling behavior

The class uses a multi-path execution model where incoming positions flow through validation gates and branch into different processing paths based on temporal characteristics, optimizing for the common case of high-frequency regular data while handling edge cases like data gaps, validation failures, and first positions.

Key Features:

  • Temporal Coherence Validation: Multi-stage validation ensuring positions are temporally consistent (minimum/maximum period, local time deviation, speed)

  • Cubic Spline Interpolation: Generates smooth C² continuous trajectories between irregular position measurements using scipy’s CubicSpline

  • Actor Metadata Tracking: Maintains vehicle dimensions alongside position data

  • Configurable Output Frequency: Supports flexible interpolation rates from 1Hz to 10Hz or higher based on configuration

  • Temporal Consistency: Validates and maintains proper time sequencing, rejecting out-of-order or temporally inconsistent data

  • Gap Detection & Recovery: Automatically handles large data gaps by clearing history to prevent unrealistic interpolation across discontinuities

  • Bounded Resource Usage: Configuration-driven limits ensure predictable memory and computational footprint

Processing Pipeline:

The add_point() method implements the core processing pipeline:

  1. Metadata Update: Update vehicle dimensions if provided

  2. Time Conversion: Convert ISO 8601 timestamp to epoch milliseconds

  3. First Position Handling: Initialize queue if empty

  4. Coherence Validation: Check temporal and spatial consistency

  5. Branching Logic:

    • Path A (First Position): O(1) - Initialize queue

    • Path B (Too Short): O(1) - Reject position

    • Path C (Too Long/Error): O(m) - Clear history, reinitialize

    • Path D (Success): O(n + k*log(n) + k) - Interpolate trajectory

Performance Characteristics:

Let:

  • n = number of input points in queue (≤ input_max_point_number)

  • k = number of interpolated output points generated

  • m = current queue length at operation time

Time Complexity Analysis:

  1. add_point() Method:

    • Overall: O(n + k*log(n) + k) worst case

    • Typical Case: O(1) for 80-90% of calls (fast path, rejections)

    • Interpolation Case: O(n + k*log(n) + k) for 10-20% of calls

    • Breakdown:

      • Metadata update: O(1)

      • Time conversion: O(1)

      • Coherence validation: O(1) including haversine distance

      • History clear: O(m) ≈ O(n)

      • Interpolation pipeline: O(n + k*log(n) + k)

        • Array population: O(n)

        • Spline construction: O(n) for 3 dimensions

        • Spline evaluation: O(k*log(n)) for k points

        • Position list construction: O(k)

  2. Property Accessors (actor, vehicle_length, vehicle_width, last_record_time):

    • Time Complexity: O(1) - Direct attribute access or deque[-1] lookup

    • Space Complexity: O(1) - Return references, no allocation

  3. Internal Methods:

    • _clear_history(): O(m) - Deque clear operation

    • _find_optimal_period(): O(1) - Arithmetic operations only

    • _create_interpolated_timestamp_array(): O(k) - Generate k timestamps

    • _create_interpolated_arrays(): O(n + k*log(n)) - Core interpolation

    • _create_interpolated_position(): O(1) - Single position with motion

    • _create_positions_list(): O(n + k*log(n) + k) - Full trajectory

    • _check_position_coherence(): O(1) - Validation checks

Space Complexity Analysis:

  1. Persistent Storage: O(n) - Configuration-bounded

    • Input queue: n PositionInfoRecord references (~258n bytes)

    • Pre-allocated numpy arrays: 4 * (n+1) * 8 bytes = ~32(n+1) bytes

    • Actor metadata: O(1) - Two optional references

    • Configuration: O(1) - Immutable frozen dataclass

    • Geocode helper: O(1) - Single instance

    • Total Persistent: O(n) → ~290n bytes

  2. Transient Allocations (per add_point() call):

    • Fast Path (80-90% of calls): O(1) → ~30 bytes

    • Interpolation Path (10-20% of calls): O(n + k) → ~(128n + 290k) bytes

      • Interpolated arrays: ~(128n + 32k) bytes

      • Position list: ~258k bytes

      • Local variables: ~30 bytes

  3. Memory Bounds (typical configurations):

    • n=30, k=20: Persistent ~8.7KB, Transient peak ~10KB

    • n=10, k=50: Persistent ~2.9KB, Transient peak ~16KB

    • Predictable: Memory usage bounded by configuration parameters

    • No Leaks: Automatic cleanup via deque maxlen and GC of transients

Overall System Complexity:

  • Time Complexity: O(n + k*log(n) + k) worst case, O(1) typical case

  • Space Complexity: O(n + k) transient, O(n) persistent

  • Dominant Operations:

    • Cubic spline construction: O(n) - Thomas algorithm for tridiagonal system

    • Spline evaluation: O(k*log(n)) - Binary search + polynomial evaluation

  • Performance Profile: Optimized for high-frequency regular data with occasional interpolation needs

Thread Safety:

This class is NOT thread-safe. Concurrent access from multiple threads requires external synchronization:

add_point(new_position: PositionInfo, vehicle_length: VehicleLength | None, vehicle_width: int | None) → list[PositionInfo] | None[source]

Add a new position point to the dataset and update actor dimensions.

This method processes incoming GNSS position data through a multi-stage pipeline that includes metadata updates, time conversion, coherence validation, and trajectory interpolation. It serves as the primary entry point for adding position measurements to the dataset and generating smooth interpolated trajectories.

Processing Pipeline:

  1. Actor ID Validation: Verifies the position belongs to this dataset’s actor; returns None immediately on mismatch

  2. Time Conversion: Converts ISO 8601 timestamp to epoch milliseconds

  3. Coherence Validation: Validates temporal and spatial consistency

  4. Trajectory Generation / First Position Handling: Creates interpolated positions, initializes queue on first position, or handles errors; vehicle dimensions updated on SUCCESS or history-reset paths

Execution Paths:

The method branches into several distinct paths based on validation results:

  • Path A - First Position (queue empty): Complexity: O(1) - Appends position to queue - Returns single-element list

  • Path B - Validation Failure (period too short): Complexity: O(1) - Performs coherence check - Returns None without queue modification

  • Path C - History Reset (period too long or position error): Complexity: O(m) where m = queue length - Clears history (deque.clear()) - Appends new position - Returns single-element list

  • Path D - Successful Interpolation (coherence check passes): Complexity: O(n + k*log(n) + k) - Generates interpolated positions - Returns list of k+1 positions

Time Complexity Analysis:

Let:

  • n = number of input points in queue (≤ input_max_point_number)

  • k = number of interpolated output points generated

  • m = current queue length at method invocation

Overall Worst-Case Complexity: O(n + k*log(n) + k)

Detailed Component Breakdown:

  1. Metadata Update: O(1) - Conditional assignments for vehicle_length and vehicle_width - Direct attribute access, no iteration

  2. Time Conversion & Record Creation: O(1) - ISO time parsing to epoch milliseconds - PositionInfoRecord instantiation

  3. First Position Check: O(1) - Queue length check: len(deque) is O(1) - Queue append: O(1) amortized - List creation: O(1)

  4. Coherence Validation (_check_position_coherence): O(1)

    • Time difference calculation: O(1)

    • Minimum/maximum period checks: O(1) each

    • Local time deviation check: O(1)

    • Speed coherence check:

      • Geocode distance calculation (haversine): O(1)

      • Speed computation: O(1)

    • Total: O(1) - All operations are constant time

  5. Match Statement Branching: O(1) - Pattern matching on InsertPointResult enum

  6. History Clear (Path C): O(m) - _clear_history() calls deque.clear(): O(m) - Resets vehicle dimensions: O(1) - Total: O(m) where m ≤ input_max_point_number

  7. Trajectory Generation (Path D - _create_positions_list): O(n + k*log(n) + k)

    • Fast path (no interpolation): O(1)

    • Interpolation path: O(n + k*log(n) + k)

      • Array interpolation: O(n + k*log(n))

      • Position list construction: O(k)

    • Total: O(n + k*log(n) + k) worst case

Complexity by Execution Path:

  • Path A (First Position): O(1)

  • Path B (Too Short): O(1)

  • Path C (Reset): O(m) ≈ O(n) since m ≤ n

  • Path D (Interpolation): O(n + k*log(n) + k)

Overall Time Complexity: O(n + k*log(n) + k) - Dominated by Path D when interpolation is triggered - Most real-world calls follow Path A or B with O(1) performance

Space Complexity Analysis:

Let:

  • n = number of input points in queue

  • k = number of interpolated output points

Overall Worst-Case Complexity: O(n + k)

Detailed Component Breakdown:

  1. Local Variables: O(1) - vehicle_length, vehicle_width: references only - new_position_time: single ItsTime object (~16 bytes) - new_position_record: single PositionInfoRecord (~8 bytes reference) - position_record: reference to existing queue element - Total: O(1) → ~30 bytes

  2. Queue Storage: O(n) - Persistent storage in _input_points_queue (deque) - Maximum size bounded by input_max_point_number - Each element is a PositionInfoRecord reference (~8 bytes) - Actual PositionInfoRecord objects: ~250 bytes each - Total: O(n) → ~(8n + 250n) = 258n bytes - Note: This is persistent storage, not allocated by this method

  3. Return Value Space (varies by path):

    • Path A, C: O(1)

      • Single-element list: 8 bytes + 1 reference

      • Total: ~16 bytes

    • Path B: O(1)

      • Returns None: 0 bytes

      • Total: 0 bytes

    • Path D: O(k)

      • List of k+1 PositionInfo objects

      • Each PositionInfo: ~250 bytes

      • List overhead: ~8 + 8*(k+1) bytes

      • Total: O(k) → ~(258k + 258) bytes

  4. Interpolation Path Space (Path D only): O(n + k)

    • Calls _create_positions_list() which uses O(n + k):

      • Interpolated arrays: O(n + k) → ~(128n + 32k) bytes

      • Position list construction: O(k) → ~258k bytes

      • Temporary variables: O(1)

    • Total: O(n + k) → ~(128n + 290k) bytes

  5. History Clear Space (Path C only): O(1) - _clear_history() deallocates m queue elements - Net effect: frees ~258m bytes - Method only allocates O(1) for new position - Total: O(1) allocated, O(m) deallocated

Space Complexity by Path:

  • Path A: O(1) local + O(1) return = O(1) transient

  • Path B: O(1) local + O(1) return = O(1) transient

  • Path C: O(1) local + O(1) return = O(1) transient

  • Path D: O(1) local + O(n + k) computation + O(k) return = O(n + k) transient

Overall Space Complexity: O(n + k) - Dominated by Path D interpolation - Most paths use only O(1) transient space - Persistent storage (queue) not counted as method allocation

Memory Characteristics:

  • Bounded Growth: All allocations bounded by configuration:

    • n ≤ input_max_point_number (typically 5-30)

    • k ≤ input_max_period_ms / output_nominal_period_ms (typically 1-30)

    • Maximum transient allocation: ~(128*30 + 290*30) = ~12.5KB

  • Allocation Patterns:

    • Path A, B, C: Minimal allocation (~16-30 bytes)

    • Path D: Significant transient allocation for interpolation

    • Allocations are short-lived, returned to caller immediately

  • Memory Pressure:

    • High-frequency operation (called for each GNSS measurement)

    • Most calls (80-90%) follow fast paths with O(1) space

    • Interpolation path (10-20%) creates temporary pressure

    • No memory leaks - all allocations either returned or GC-eligible

Performance Characteristics:

  • Typical Case (high-frequency sampling): O(1) time, O(1) space Most consecutive positions arrive at expected intervals, triggering either Path A (first position) or the fast path in Path D

  • Interpolation Case (data gaps): O(n + k*log(n) + k) time, O(n + k) space Occurs during recovery from communication loss or irregular sampling

  • Error Case (validation failure): O(1) time, O(1) space Invalid positions rejected with minimal overhead

  • Reset Case (large gaps): O(m) time, O(1) space History cleared to prevent unrealistic interpolation across discontinuities

Parameters:

  • new_position (PositionInfo) – Complete position information including coordinates, speed, heading, station info, and ISO 8601 timestamp. Must contain valid latitude, longitude, and properly formatted time.

  • vehicle_length (Optional[VehicleLength]) – Actor length information. If provided, updates the dataset’s actor length. If None, existing actor length is preserved.

  • vehicle_width (Optional[int]) – Actor width in appropriate units (centimeters). If provided, updates the dataset’s actor width. If None, existing actor width is preserved.

Returns:

Result depends on validation outcome:

  • None: Position rejected due to temporal coherence failure (too short period)

  • Single-element list: First position, or history reset, or no interpolation needed

  • Multi-element list: Successful interpolation with k+1 positions where: * First k positions are interpolated (POSITION_GNSS_ESTIMATED) * Last position is the new_position (original position type)

Return type:

Optional[list[PositionInfo]]

Raises:

  • ValidationError – If ISO time parsing fails or position data is malformed.

  • StepAdapterError – If internal state becomes inconsistent (e.g., empty queue when interpolation is expected).

Note

Coherence Validation Details:

The method performs comprehensive validation before accepting a position:

  • Minimum Period: Rejects positions arriving too quickly (< output_nominal_period_ms - output_max_period_deviation_ms)

  • Maximum Period: Triggers history reset if gap is too large (> input_max_period_ms)

  • Local Time Deviation: Ensures position timestamp is reasonable compared to system clock (within input_max_local_time_deviation_ms)

  • Speed Coherence: Validates that implied speed between positions doesn’t exceed SPEED_COHERENCE_THRESHOLD (120 m/s)

Thread Safety: This method is NOT thread-safe. External synchronization required for concurrent access.

Logging: Debug logs emitted for first positions; warning logs for validation failures. Consider log volume in high-throughput scenarios.

Example

>>> # Normal high-frequency operation (Path A or fast Path D)
>>> config = PointDatasetConfig(...)
>>> dataset = PointDataset(actor_id, config, logger)
>>> # First position
>>> result = dataset.add_point(pos1, length, width)
>>> len(result)  # Returns 1
1
>>> # Subsequent position within nominal period (fast path)
>>> result = dataset.add_point(pos2, length, width)
>>> len(result)  # Returns 1
1
>>> # Position with large temporal gap (interpolation path)
>>> result = dataset.add_point(pos3_delayed, length, width)
>>> len(result)  # Returns k+1 interpolated positions
15
>>> result[0].positionType
<PositionType.POSITION_GNSS_ESTIMATED: 1>
>>> # Position arriving too quickly (rejected)
>>> result = dataset.add_point(pos4_too_soon, length, width)
>>> result is None
