STEP Adapter: Overview

Back to STEP Documentation

The step_adapter is a component of the STEP (Safer Transport for Europe Platform) ecosystem, specifically designed for real-time position processing and Crash Prediction data preparation within Intelligent Transportation Systems (ITS) environments. This Redis-based microservice converts CAM and CPM messages into regularly-sampled position arrays for the crash prediction algorithms.

Environment Variables

The Redis host, port and credentials are kept out of the JSON configuration file and are read from the environment once at startup (step_redis RedisCredential.from_env), after loading the .env file of the launch directory or its nearest parent, if any; a variable already set in the environment wins over the .env file:

Variable

Required

Description

REDIS_URL

yes

Redis server host

REDIS_PORT

yes

Redis server port (1-65535)

REDIS_USERNAME

no

ACL username, when the server requires authentication

REDIS_PASSWORD

no

Password, when the server requires authentication

A missing or invalid required variable stops the program with exit code 2 (ERROR). See Environment Variables for the full reference and the .env.example template.

Purpose

The step_adapter consumes the AdapterCloudEventsCamDataV1 and AdapterCloudEventsCpmDataV1 events published by step_client on a Redis input stream and publishes PositionArrayV1 events to the crash prediction Redis stream:

  • for every CAM sender it keeps a short position history, validates each new position against the previous one and fills the gaps with positions interpolated by a cubic spline at the configured output frequency, the received position being always the last point;

  • for every perceived object of a CPM it builds one position array from the measured position and the predicted path, resampled at the configured output frequency (interpolated when the CPM period is longer, decimated when shorter).

Key Features

Real-time Data Processing

  • Stream-based Architecture: Utilizes Redis streams with consumer groups and connection pooling; the input is read without acknowledgement (at most once delivery)

  • Vehicle Position Processing: Transforms raw GNSS measurements into smooth position trajectories using cubic spline interpolation techniques

  • Multi-Message Support: Processes CAM (Cooperative Awareness Messages) and CPM (Collective Perception Messages)

  • Actor Dataset Management: Maintains a position history for each CAM sender, removing the senders without recent positions periodically

Interpolation and Validation

  • Cubic Spline Interpolation: Advanced interpolation engine for generating smooth position trajectories from irregular GNSS data with configurable output frequencies

  • Output Period Resampling: One GapFiller shared by CAM and CPM puts every position array at the configured sample frequency: interpolation of the CAM gaps, interpolation or decimation of the CPM predicted paths

  • Coherence Checks: Positions too close in time, or too far from the local time, are discarded; a too long gap or an implausible speed restarts the actor history

  • Configurable Sampling: Output frequencies of 1, 2, 5 or 10 Hz

  • Bounded Memory Usage: At most 5-30 positions per actor, with automatic cleanup of the expired actors

Configuration and Monitoring

  • Hierarchical Configuration: Multi-level configuration with Redis, Logging, and Adapter settings using Pydantic models for type safety and validation

  • Schema Generation: JSON schema generation for configuration validation and template creation

  • Comprehensive Logging: Multiple output handlers (stream, file, rotating file) with UTC formatting and configurable levels

  • Signal Handling: Graceful shutdown through AppRunner (from step_cloud_schemas)

  • Automatic Reconnection: A failed connection cycle is retried after reconnectInterval seconds; errors a reconnect cannot fix end the program

Core Components

Actor Dataset Manager

The ActorDataset class is the registry of the CAM senders. It handles:

  • Converting each CAM message into a position and routing it to the PointDataset of its sender, created on the first accepted position

  • Wrapping the returned positions in a PositionArrayV1

  • A temporal index (SortedList) of the actors ordered by their last position time

  • The periodic removal of the actors whose last position is older than inputOldestAllowedTime

It is not thread-safe: the program uses it from a single asyncio event loop.

Point Dataset Manager

The PointDataset class manages the position history of one actor; its gaps are filled by cubic spline interpolation through GapFiller. It implements:

  • Coherence Checks: Minimum and maximum period, speed and local time checks of each new position

  • Gap Filling: Delegates the cubic spline interpolation of a gap to GapFiller.fill()

  • Memory Management: A bounded deque of positions and pre-allocated NumPy buffers

  • Output Behavior: Returns interpolated positions followed by the actual received GNSS position as the final point; speed and heading are recomputed from the displacement

  • Performance: O(n + k*log(n)) time per position on the interpolation path, where n is the history size (maxActorHistoryPointNumber, 5-30) and k the number of interpolated positions

Gap Filler

The GapFiller class puts positions at the output period (outputNominalSampleFrequency plus or minus outputPeriodMaxDeviation) with SciPy’s CubicSpline. It keeps no state and is shared by both datasets:

  • fill() (CAM): fills the gap between the last position of an actor and a new one with interpolated positions, followed by the new one

  • resample() (CPM): puts a whole predicted path on the output period grid; a longer period is interpolated, a shorter one decimated, and a grid time equal to a real point keeps that point

  • Speed and Heading: Recomputed from the displacement for every position after the first

Perceived Object Dataset

The ObjectPerceivedDataset class converts every perceived object of a CPM message into one position array (measured position plus predicted path, resampled by GapFiller.resample() to at most 101 points at the configured sample frequency), without keeping any history.

Redis Integration

The Redis integration components come from step_redis (StepRedisPool, StepAdapterRedisStream and StepCrashPredictionRedisStream) and provide:

  • Connection Management: Redis connection pools, with the host, port and credentials read from the environment

  • Stream Operations: Creation of the input stream and its consumer group

  • Message Processing: Receiving and validating CAM and CPM messages from streams

  • Data Distribution: Publishing position array messages to the crash prediction stream

Configuration System

The configuration system (StepAdapterConfig) offers:

  • Hierarchical Configuration: Multi-level configuration with Redis, logging, and adapter settings

  • Type Safety: Strong typing and validation via Pydantic models with comprehensive validation

  • Schema Generation: JSON schema generation for configuration validation and template creation

  • Default Configurations: Pre-configured default instances for quick setup and development

  • Actor Dataset Configuration: Specialized configuration for timing parameters and trajectory management

Logging Infrastructure

The logging system (StepLogger, from step_cloud_schemas) provides:

  • Multiple Handlers: Stream, file, rotating file, and null handlers for flexible output options

  • UTC Formatting: Standardized UTC timestamp formatting for consistent log entries

  • Configurable Levels: Adjustable logging levels for different environments (development, production)

  • Structured Logging: Comprehensive operation logging throughout the service lifecycle with detailed processing metrics

Architecture

Event-Driven Processing

The service follows an event-driven architecture pattern:

  1. Input Processing: Monitors the Redis input stream for CAM and CPM messages

  2. Position Processing: Transforms CAM positions into smooth position trajectories using cubic spline interpolation; resamples the CPM perceived objects at the output period

  3. Actor Management: Maintains an individual dataset for each CAM sender

  4. Output Generation: Publishes the position arrays to the crash prediction stream

  5. Cleanup Operations: Periodically removes the expired actors

Asynchronous Operations

The architecture utilizes:

  • AppRunner (from step_cloud_schemas): Owns the event loop and the signal handling, and runs the StepAdapterApp workload

  • Reconnect Loop: StepAdapterApp derives from ReconnectingApp: each connection cycle is retried after reconnectInterval seconds

  • Task Groups: Three concurrent tasks per cycle: stream reception, actor cleanup and Redis health check

  • Connection Pooling: A Redis connection pool of at most two connections per cycle

Message Flow

  1. Message Reception: CAM and CPM messages received via the Redis input stream from step_client

  2. Trajectory Processing: CAM positions validated and interpolated in the history of their sender; CPM perceived objects converted one by one and resampled at the output period

  3. Position Array Generation: The position arrays published to the crash prediction stream

  4. Cleanup: The actors without recent positions removed every cleanerInterval seconds

Standards Compliance

The step_adapter adheres to key ITS standards and supports:

  • ETSI TS 103 900: Cooperative Awareness Messages (CAM)

  • ETSI TS 103 324: Collective Perception Messages (CPM)

Usage Patterns

The service supports multiple usage patterns:

Service Mode

Run as a continuous service processing real-time data streams:

python -m step_adapter --instance adapter_1 --config production.json

The Redis host, port and credentials must be set in the environment or in a .env file (see Environment Variables).

Configuration Generation

Generate the configuration template and schema into a directory:

python -m step_adapter --conf_template ./config
python -m step_adapter --conf_schema ./config
