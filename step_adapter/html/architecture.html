Architecture

This document describes the architecture of the STEP Adapter, a Python package for processing real-time vehicle position data for crash prediction systems.

Overview

The STEP Adapter is a component of the STEP (Safer Transport for Europe Platform) ecosystem that converts ITS messages into position arrays for the Crash Prediction algorithms. This Redis-based microservice reads CAM (Cooperative Awareness Messages) and CPM (Collective Perception Messages) from a Redis input stream, converts them into PositionArrayV1 messages and publishes them to the crash prediction Redis stream:

  • CAM: every sender keeps a short position history; a new position is validated against the previous one and, when the gap from it is larger than the output period, the gap is filled with positions interpolated by a cubic spline at the configured output frequency.

  • CPM: every perceived object is converted into one position array, from its measured position and its predicted path, without any history between messages.

Library

The STEP Adapter leverages a carefully selected set of libraries and frameworks to implement robust, high-performance position data processing capabilities. The library architecture follows a layered approach with core Python libraries, specialized scientific packages, and custom STEP ecosystem components.

Core Dependencies

Pydantic

Data validation and settings management library that provides the foundation for configuration management throughout the STEP Adapter. Pydantic enables:

  • Type Safety: Strong typing with automatic validation for all configuration parameters

  • Schema Generation: Automated JSON schema creation for configuration documentation

  • Serialization: Robust JSON serialization/deserialization for configuration persistence

  • Model Validation: Runtime validation of configuration data with detailed error reporting

Used in StepAdapterConfig and its nested configuration classes, which are strict, frozen and forbid extra fields.

SciPy

Scientific computing library providing the mathematical foundation for position interpolation:

  • CubicSpline: Cubic spline interpolation for smooth trajectory generation

  • Vector-valued splines: Latitude, longitude and (when every point has one) altitude share one spline, so a single tridiagonal system is solved for all of them

  • No extrapolation: The spline is evaluated with extrapolate=False

Used by GapFiller, shared by PointDataset and ObjectPerceivedDataset, to generate the interpolated positions (see Cubic Spline Interpolation for Trajectories).

NumPy

Numerical computing library that provides efficient array operations:

  • Pre-allocated buffers: Each PointDataset allocates its input arrays (timestamps, latitudes, longitudes, altitudes) once and reuses them on every interpolation

  • Vectorized motion: Distance, speed and heading of a whole position chain (CAM gap or CPM grid) are computed with array operations, from one batched geodesic call

  • Validator replication: The range clamping/wrapping of the pydantic validators is applied once to whole arrays, so the interpolated objects are built without validation

SortedContainers

Pure-Python sorted container implementation used by ActorDataset:

  • SortedList: \(O(log(m))\) insertion and deletion, where m is the number of actors

  • Bisection: A single bisect_right finds every actor older than the allowed time

  • Slice deletion: The expired actors are removed from the index in one batch

step_cloud_schemas

Custom STEP ecosystem library that defines standardized ITS message schemas and data structures. This library provides:

  • ITS Message Schemas: CamDataV1 and CpmDataV1 message structures compliant with ETSI standards

  • Cloud Events: AdapterCloudEventsCamDataV1 and AdapterCloudEventsCpmDataV1 wrappers

  • Position Primitives: PositionInfo, ReferencePosition, ItsTime, Speed, Heading, ActorId and the Geocode geodesic utilities

  • Position Arrays: PositionArrayV1 structures for crash prediction integration

  • Runtime and Logging: AppRunner, ReconnectingApp, StepLogger, LogConfig and LoggingTimer, shared by the STEP programs

step_redis

STEP-specific Redis integration library that provides the messaging and stream processing foundation as a black box interface. Core functionality includes:

  • Connection Pooling: Redis connection pool management

  • Stream Processing: High-level abstractions for Redis streams with consumer group support

  • Message Serialization: Automatic conversion between Python objects and Redis stream data

  • Error Classification: Redis errors that a reconnect cannot fix are raised as StepRedisFatalError

Provides the base classes StepRedisPool and StepRedisStream, plus the specialized streams StepAdapterRedisStream and StepCrashPredictionRedisStream used by the STEP Adapter. The STEP Adapter uses these classes directly without custom extensions.

python-dotenv (through step_redis)

Loads Redis connection credentials from the .env file of the current working directory (or its nearest parent) into the process environment at startup, without overriding a variable already set, so secrets are kept out of the (persisted) JSON configuration document. Used by step_redis RedisCredential.from_env(), called by the StepAdapterApp constructor (see Environment Variables).

Architecture Integration

The library selection supports the STEP Adapter’s architectural requirements:

  • High Performance: SciPy and NumPy enable efficient interpolation of high-frequency position data streams

  • Type Safety: Pydantic provides runtime type validation of the configuration

  • Standards Compliance: step_cloud_schemas ensures ETSI ITS standard compliance for all messages

  • Scalability: step_redis consumer groups let several instances share the input stream; since the actor histories are kept per instance, the CAM messages of one sender must reach the same instance (see Actor Partitioning)

  • Maintainability: Comprehensive development tooling ensures code quality and documentation standards

Components

The architecture follows a modular design pattern that separates concerns between position data processing, interpolation, actor management, Redis integration, and configuration management.

Main Components:

  1. ActorDataset/ActorDatasetConfig: Registry of the per-actor PointDataset instances fed by CAM messages, with time-ordered cleanup of the expired actors

  2. PointDataset/PointDatasetConfig: Per-actor position history with coherence checks; the gaps are filled by GapFiller

  3. GapFiller/GapFillerConfig: Output period resampling shared by CAM and CPM: cubic spline interpolation of longer periods, decimation of shorter ones

  4. ObjectPerceivedDataset/ObjectPerceivedDatasetConfig: Stateless conversion of CPM perceived objects into position arrays resampled at the output period

  5. numeric_bounds: Numeric bounds shared by the JSON configuration, PointDatasetConfig and GapFillerConfig

  6. StepAdapterConfig: Configuration management for the Adapter

  7. Redis Integration (step_redis): Redis connection pooling and stream processing via StepRedisPool, StepAdapterRedisStream and StepCrashPredictionRedisStream

  8. StepLogger (from step_cloud_schemas): Logging utilities used by the STEP Adapter

  9. StepException: Custom exceptions for error handling

  10. Main Application (__main__): Command-line interface; runs StepAdapterApp through AppRunner (from step_cloud_schemas)

  11. StepAdapterApp: Workload of the program: environment-based Redis credentials, asynchronous task orchestration and automatic reconnection

  12. Application Runtime (from step_cloud_schemas): AppRunner, which runs the workload with a cooperative shutdown, and the abstract classes AbstractApp and ReconnectingApp, which StepAdapterApp derives from

ActorDataset

The ActorDataset class (module actor_dataset) is the registry of the CAM senders. It maps every actor (ActorId: station id plus optional object id; a CAM sender has no object id) to its own PointDataset, and keeps a SortedList of (last record time, actor) pairs ordering the actors by the time of their latest accepted point.

Core Responsibilities:

  1. CAM Message Processing: add_cam_message() converts a CamDataV1 into a PositionInfo (POSITION_GNSS, time = CAM creationTime), inserts it into the dataset of its sender and wraps the returned positions in a PositionArrayV1 with sourceType GNSS_SRC, sampleFrequency = outputNominalSampleFrequency and the vehicle length/width of the CAM. A CAM without position is skipped with a warning; a rejected point returns None.

  2. Actor Registration: The PointDataset of a new actor is created on its first point and registered only if that point is accepted.

  3. Temporal Indexing: On every accepted point the (last record time, actor) entry of the actor is replaced in the SortedList, at \(O(log(m))\).

  4. Automatic Cleanup: clear_old_points() computes the limit as the current ITS time minus inputOldestAllowedTime, finds the expired actors with one bisect_right and removes them from the registry and the index in one batch.

Configuration Parameters (ActorDatasetConfig, built by StepAdapterApp from StepAdapterConfig):

  • input_max_point_number: Maximum number of input points retained per actor (maxActorHistoryPointNumber)

  • input_min_altitude_trailing_point_percent: Minimum trailing run of points with altitude needed to interpolate it (minActorHistoryAltitudeTrailingPointPercent)

  • input_max_period_ms: Maximum allowed period between input points (inputMaxPeriod)

  • input_max_local_time_deviation_ms: Maximum allowed local time deviation (inputLocalTimeMaxDeviation converted from seconds)

  • input_oldest_allowed_time_ms: Maximum age of the last point of an actor before cleanup (inputOldestAllowedTime converted from seconds)

  • output_nominal_sample_frequency: Output frequency in Hz; the output period is 1000 // frequency ms

  • output_period_max_deviation_ms: Maximum timing tolerance for interpolation points (outputPeriodMaxDeviation)

Thread Safety:

ActorDataset is not thread-safe: no lock is used. StepAdapterApp calls it from the tasks of a single asyncio event loop, which never interleave inside its synchronous methods, so no lock is needed there; multi-threaded callers need external synchronization.

PointDataset

The PointDataset class (module point_dataset) holds the position history of one actor: a deque of at most n PositionInfoRecord plus four pre-allocated NumPy buffers of n + 1 entries, n = maxActorHistoryPointNumber. Each add_point() call validates the new position, then returns it, possibly preceded by interpolated positions.

Coherence Rules (_COHERENCE_RULES, run by _check_position_coherence()): every check is bound to the action taken when it fails; the checks run in this order and the first failure decides the action of add_point():

A wrong history recovers by itself: rejected positions do not update the last time, so within inputMaxPeriod the maximum period rule restarts the trajectory; the worst case is an output gap of that length for the actor.

A position of another actor is rejected with a warning.

Output Behavior (_create_positions_list()):

  • First position or history reset: The position is returned as-is.

  • Fast path (gap within the nominal output period plus the deviation): the position is returned with speed and heading recomputed from the distance/heading already computed by the coherence check.

  • Interpolation path (larger gap): GapFiller.fill() chooses the output period and the number of intervals (GapFiller.optimal_period(), see Finding the Optimal Interpolation Period), evaluates the cubic spline fitted on the history at the k interpolated timestamps (GapFiller.interpolate()) and returns the k interpolated positions (POSITION_GNSS_ESTIMATED) followed by the received position, the last point being always the measured one.

Speed and Heading: The speed and heading reported by the sender are never preserved: they are always recomputed from the geodesic displacement relative to the previous point (one batched geodesic call over the whole interpolation chain).

Altitude: Interpolated by GapFiller (see GapFiller) from the trailing run of points with altitude ending at the new position.

Vehicle Dimensions: The vehicle length and width are updated on every accepted position when provided (None keeps the stored value) and reset with the history.

Thread Safety:

This component is not thread-safe and requires external synchronization for concurrent access from multiple threads.

GapFiller

The GapFiller class (module gap_filler) puts positions at the output period (outputNominalSampleFrequency ± outputPeriodMaxDeviation). It keeps no state between calls (configuration and logger only) and is shared by both datasets:

  • fill() (streaming, CAM): fills the gap between the last queued position of an actor and a new one with the k interpolated positions of the cubic spline fitted on the actor history, followed by the new position. A gap shorter than the nominal period minus the deviation never reaches it: PointDataset rejects the position (streaming decimation).

  • resample() (batch, CPM): resamples a whole time-ordered list of positions. Positions already at the output period are returned as-is; otherwise the grid is first time + floor(i * span / n), i in [0, n], with n chosen by optimal_period() over the whole span, so a longer input period is interpolated and a shorter one decimated. A grid time equal to an input time keeps the real position (an input period dividing the output one is a pure decimation); the others become POSITION_PERCEIVED_ESTIMATED positions from the spline fitted on every input position. The output is truncated to a maximum number of points.

Speed and Heading: The speed and heading of every output position after the first one are recomputed from the geodesic displacement relative to the previous point (one batched geodesic call over the whole chain); the first position of resample() is unchanged.

Altitude: The altitude is interpolated together with latitude and longitude when every point has one. Otherwise only the trailing run of consecutive points with altitude, ending at the last point, is used by a separate spline, when its length reaches minActorHistoryAltitudeTrailingPointPercent percent of the points (never fewer than 4); the positions before the run, or all of them with a shorter run, have no altitude.

Thread Safety: No mutable state is kept, so concurrent calls are safe as long as the logger is.

ObjectPerceivedDataset

The ObjectPerceivedDataset class (module object_perceived_dataset) converts the perceived objects of a CpmDataV1 message into position arrays at the output period. Unlike ActorDataset, it keeps no history between messages.

add_cpm_message() returns one PositionArrayV1 per perceived object, in message order:

  • Points: The measured position (POSITION_PERCEIVED, with the object speed and heading) followed by one POSITION_PERCEIVED_PREDICTED point per predicted path entry. All points share one Identification: the CPM sender station id, the object type and its confidence. A point not strictly following the previous one is dropped with a warning.

  • Resampling: GapFiller.resample() puts the points at the output period (interpolation of a longer CPM period, decimation of a shorter one), keeping the measured position unchanged and recomputing speed and heading of the following points; at most PositionArrayV1.POINTS_MAX_LENGTH (101) points are kept, the others are dropped with a warning. No limit is applied to the gap between two CPM points.

  • Source Type: CAMERA_SRC.

  • Sample Frequency: outputNominalSampleFrequency.

  • Dimensions: objectDimensionX becomes the vehicle length and objectDimensionY the vehicle width (ETSI CPM convention: X is the longitudinal axis).

  • Skipped Objects: An object without objectId or without predicted positions is skipped with a warning.

StepAdapterConfig

The StepAdapterConfig component (module step_adapter_config) provides the configuration loaded from the JSON file given with -c/--config, leveraging Pydantic for validation, serialization, and schema generation.

Hierarchical Configuration Architecture:

  1. StepAdapterConfig: Top-level configuration class

  2. RedisClientConfig: Redis connectivity and stream management

  3. RedisConnection (from step_redis): Redis connection parameters (database, timeouts, keepalive, SSL, pool); the host, port and credentials are not part of it

  4. RedisStreams: Input stream (RedisStreamInput) and output streams (RedisStreamOutputs, with the crashPrediction RedisStreamOutput)

  5. LogConfig (from step_cloud_schemas): Logging configuration with multiple handler types

Adapter Settings:

  • templateVersion: Configuration schema version; only "1" is accepted

  • instanceName: Unique identifier for the Adapter instance, also used as the Redis stream consumer name (not in the configuration model, -i/--instance runtime parameter)

  • maxActorHistoryPointNumber: Maximum number of points in the history of an actor (5-30)

  • minActorHistoryAltitudeTrailingPointPercent: Minimum trailing run of points with altitude, as a percentage of the history points, needed to interpolate the altitude when some points lack it (0-100, at least 4 points)

  • inputMaxPeriod: Maximum period in milliseconds between two positions of an actor; a longer gap clears its history (1000-4000)

  • inputLocalTimeMaxDeviation: Maximum deviation in seconds between the position time and the local time; a position beyond it is discarded (0-30)

  • inputOldestAllowedTime: Maximum age in seconds of the last position of an actor before the cleaner removes it (0-30)

  • outputNominalSampleFrequency: Output frequency in Hz (1, 2, 5 or 10)

  • outputPeriodMaxDeviation: Maximum deviation in milliseconds from the output period (0-50)

  • cleanerInterval: Period in seconds of the actor cleanup (1-60)

  • reconnectInterval: Time interval in seconds for automatic reconnection attempts (1-60)

Redis Integration Configuration:

  • Connection Management: Database selection, SSL configuration and pool settings; the Redis host, port and credentials are not in the configuration, they are read from the REDIS_* environment variables (see Environment Variables)

  • Socket Configuration: Socket settings for timeout management, keepalive parameters, and connection health monitoring

  • Stream Configuration: The input stream (RedisStreamInput: streamId, consumer group groupId, receive waitTimeout of 10000-300000 ms) and the crash prediction output stream (RedisStreamOutput: streamId, approximate maxLength of 1-1000000)

  • Read Timeout Check: connection.socketTimeout must be at least streams.input.waitTimeout plus READ_TIMEOUT_MARGIN_MS (5000 ms), otherwise validation fails: a blocking XREADGROUP that times out first drops the connection and loses any message delivered in that instant (the input stream is read with noack)

  • Security Settings: SSL/TLS configuration with client certificates, CA verification, and encrypted connections

Validation and Schema Features:

  1. Strict Typing: Strict mode, no type coercion

  2. Range Validation: Numeric fields have inclusive ranges, shared with PointDatasetConfig through numeric_bounds

  3. String Validation: Strings of 1-1024 characters

  4. Immutable Configuration: Frozen model instances, extra fields forbidden

  5. Schema Generation: print_config_schema() writes the JSON schema, with $id set to step_adapter_config_v1_schema

  6. Default Factory Methods: Each configuration class provides get_default(); print_config_example() writes the default configuration as a template

Redis Integration (step_redis)

The STEP Adapter integrates with Redis through the step_redis library, which provides the messaging infrastructure as a black box with well-defined interfaces.

step_redis Interface:

  • StepRedisPool: Redis connection pool, used as an async context manager

  • StepRedisPoolParams: Pool parameters, built by StepRedisPoolParams.from_connection() from RedisConnection and the RedisCredential read from the environment

  • StepRedisStream: Base class for Redis stream operations (stream creation, publishing, receiving); its run_health_check() is used by the health check task

  • StepRedisStreamParams: Stream parameters (stream, consumer group, wait timeout, consumer name, TTL or maximum length)

  • StepAdapterRedisStream: Adapter input stream; receive_adapter_message() yields the AdapterCloudEventsCamDataV1 and AdapterCloudEventsCpmDataV1 messages published by step_client

  • StepCrashPredictionRedisStream: Crash prediction output stream; publish_position_array() publishes a PositionArrayV1 to step_crash_prediction

Integration Benefits:

  • Transparent connection pooling and resource management

  • Automatic message serialization using step_cloud_schemas

  • Consumer group support; the input is read without acknowledgement (noack), so a message is delivered at most once and is lost if its processing fails

  • Asynchronous operations for high throughput

  • Classification of the errors a reconnect cannot fix (StepRedisFatalError)

The StepLogger component provides the logging functionality used by the STEP Adapter:

StepException

The step_exception module defines two plain exception classes:

  1. StepAdapterError: Base class of the STEP Adapter exceptions; raised by ActorDataset and PointDataset when their internal state is inconsistent.

  2. StepCliError: Command line misuse (only one of -c/--config and -i/--instance); main() logs it as a single error line, without a traceback, and returns ExitCode.USAGE.

Main Application (__main__)

The main application module is the command-line entry point. It parses the arguments, loads the configuration and hands the workload, StepAdapterApp, to AppRunner (from step_cloud_schemas), which owns the event loop and the signal handling.

Key features of the main application include:

  1. Command-Line Interface: Provides a CLI (_args_parse()) with options for:

    • no option: Display the help (exit code USAGE)

    • --help/-h and --version/-v: Display help or version information (exit code OK); an invalid or unknown option exits with USAGE

    • --conf_schema/-s: Write the JSON configuration schema into a directory

    • --conf_template/-t: Write the configuration template into a directory

    • --config/-c and --instance/-i: Load configuration and run the service; the two options must be given together, otherwise StepCliError is logged as a plain error line and the exit code is USAGE

  2. Logging Setup: Reconfigures StepLogger from the loaded configuration and logs the program, step_cloud_schemas and step_redis versions.

  3. Application Run: Builds AppRunner[ExitCode] (selector event loop on Windows, as for the other STEP programs) and runs StepAdapterApp, returning its exit code.

  4. Exception Handling: KeyboardInterrupt returns ABORTED; any other unhandled exception (e.g. an invalid configuration file or a missing REDIS_URL/REDIS_PORT variable) is logged with its traceback and returns ERROR.

Application Runtime (step_cloud_schemas)

Note

AppRunner, AbstractApp and ReconnectingApp are not part of the step_adapter package: they are imported from the external step_cloud_schemas dependency, shared by the STEP programs. Only their public interface, the part used by the STEP Adapter, is described here.

The three classes split a long-running program in two parts: the process-wide plumbing (event loop, signal handlers, exception hooks), owned by AppRunner, and the workload, supplied by the program as an AbstractApp subclass. R is the program’s result type: for the STEP Adapter, ExitCode.

Class

Role

AbstractApp[R]

Abstract base class of a workload run by AppRunner. It declares the two methods AppRunner needs and holds no state (empty __slots__, so a subclass declares its own).

ReconnectingApp[R]

Abstract AbstractApp subclass that implements work as a reconnect loop around a connection cycle, implemented by the program.

AppRunner[R]

Singleton that runs an AbstractApp on a new event loop until it ends or a shutdown signal stops it.

The class diagram below shows the public interface of the three classes and how StepAdapterApp plugs into them:

AbstractApp: public interface

  • async work() -> R (abstract): The workload, called once per run as a task of the AppRunner TaskGroup; it returns the result when it ends on its own. On a shutdown signal it is cancelled at the await it is suspended on, so it has to be cancellation-safe.

  • on_shutdown(stop_signal: Signals) -> R (abstract): Called by AppRunner after a shutdown signal stopped work, once every task has unwound (the resources held by work are already released); it runs on the event loop thread and cannot await. Its value is the result of the run.

ReconnectingApp: public interface

  • ReconnectingApp(logger, reconnect_interval): logger is used for the start, error and retry messages, reconnect_interval is the number of seconds to wait before the next cycle.

  • async cycle() -> None (abstract): Opens the connections and runs the tasks until one of them fails; returns only if every task ends normally, and then the next cycle starts at once. Like work, it has to be cancellation-safe.

  • fatal_result() -> R (abstract): The result returned by work after an error that a reconnect cannot fix.

  • async work() -> R: Logs Program started, then runs cycle in a loop. When cycle raises:

    • while a shutdown cancellation is in progress, the error is logged at INFO level and CancelledError is restored, so the shutdown goes on without an ERROR traceback;

    • otherwise the error is logged with its traceback, and if it, or any error nested in an ExceptionGroup (as raised by a TaskGroup), is one of the subclass’s fatal error types, work returns fatal_result();

    • otherwise work waits reconnect_interval seconds and runs cycle again.

    It never returns otherwise: the loop ends only when AppRunner cancels it.

The fatal error types are a class attribute that each subclass sets (StepAdapterApp: StepRedisFatalError); with none set, every error is retried.

AppRunner: public interface

  • AppRunner[R](logger_param, loop_factory=None, exception_handler=None, unraisable_handler=None):

    • logger_param: Logger used by the default exception and unraisable handlers.

    • loop_factory: Factory of the event loop created by every run, forwarded to asyncio.Runner; None uses the asyncio default loop. The STEP Adapter passes asyncio.SelectorEventLoop on Windows, as the other STEP programs do.

    • exception_handler: Event loop exception handler; None logs the exception on the logger.

    • unraisable_handler: Installed as sys.unraisablehook; None logs the exception on the logger.

    The constructor installs the process-wide hooks (signal handlers, sys.unraisablehook): it is called from the main thread as early as possible, which is why main() builds it before parsing the arguments, so that a signal received before run is still handled. Being a singleton, only the first construction takes effect; the arguments of later calls are ignored.

  • logger (property): The logger given to the constructor.

  • run(app: AbstractApp[R]) -> R: Opens an asyncio.Runner, installs the exception handler and the shutdown handlers (SIGINT/SIGTERM on POSIX, CTRL_C/CTRL_BREAK on Windows), then runs app.work() next to a shutdown watcher in a TaskGroup. It returns the value of app.work() when the workload ends on its own, or the value of app.on_shutdown(stop_signal) when a shutdown signal stops it. Any other exception raised by work propagates wrapped in an ExceptionGroup, which main() logs and maps to ExitCode.ERROR.

A shutdown signal never interrupts the workload at an arbitrary point: the signal handler only sets an event, the watcher task turns it into an exception, and the TaskGroup cancels work at the await it is suspended on.

How the STEP Adapter uses them:

StepAdapterApp

StepAdapterApp (module step_adapter_app) is the ReconnectingApp subclass (step_cloud_schemas, see Application Runtime (step_cloud_schemas)) run by AppRunner: the reconnecting adapter service on top of the Redis streams. It implements one connection cycle (cycle()) and the result of a fatal error (fatal_result()), while the reconnect loop is the inherited work(). It also defines the ExitCode enumeration.

Key features of StepAdapterApp include:

  1. Environment-Based Credentials: the constructor calls step_redis RedisCredential.from_env() once: it loads the .env file of the current working directory (or an ancestor of it) and reads REDIS_URL, REDIS_PORT, REDIS_USERNAME, and REDIS_PASSWORD from the environment (see Environment Variables); REDIS_URL and REDIS_PORT are required, the username and password are optional (an empty value counts as unset). Reading them at construction (not in cycle()) makes a missing variable end the program instead of being retried forever.

  2. Asynchronous Task Orchestration: each cycle() creates a new ActorDataset (_actor_dataset_create()) and ObjectPerceivedDataset, opens a StepRedisPool (parameters from StepRedisPoolParams.from_connection(), at most _REDIS_MAX_CONNECTIONS = 2 connections), then uses asyncio.TaskGroup to run three concurrent tasks - _stream_receive_run() (stream reception, conversion and publishing), _cleaner_run() (every cleanerInterval seconds, ActorDataset.clear_old_points()) and _redis_health_check_run() (Redis connection health check).

  3. Message Dispatch: _stream_receive_run() creates the input stream, then routes each received message: an AdapterCloudEventsCamDataV1 to ActorDataset.add_cam_message() (at most one position array), an AdapterCloudEventsCpmDataV1 to ObjectPerceivedDataset.add_cpm_message() (one position array per perceived object); any other type is skipped with a warning. Every resulting position array is published on the crash prediction stream. Each message handling is timed by a LoggingTimer at INFO level.

  4. Stream Parameters: _input_stream_params() builds the input stream parameters (stream, consumer group, wait timeout, the instance name as consumer, TTL from StepRedisStreamParams.ttl_seconds_from_wait_timeout()), also used by the health check; _crash_prediction_stream_params() builds the crash prediction output stream parameters (stream and maxLength).

  5. Automatic Reconnection: A Redis error raised by any task ends the cycle; the inherited work() waits config.reconnectInterval seconds and runs cycle() again. The datasets are created per cycle, so the actor histories collected before the failure are dropped. A message whose conversion fails (StepAdapterError or ValueError, pydantic validation errors included) is only logged and skipped by _message_to_position_arrays(), without ending the cycle.

  6. Permanent Errors: An error that a reconnect cannot fix (_FATAL_ERRORS: StepRedisFatalError from step_redis, i.e. rejected credentials, ACL denial, missing SSL file, untrusted certificate) ends the run with fatal_result() (ExitCode.ERROR) instead of retrying forever.

  7. Graceful Shutdown: Delegated to AppRunner: on SIGINT/SIGTERM (POSIX) or CTRL_C/CTRL_BREAK (Windows) it cancels work(), the async with blocks release the Redis pool and streams, and on_shutdown() logs the signal and returns ExitCode.ABORTED. A failure raised while the cancellation unwinds is turned back into CancelledError instead of triggering a reconnect, and is logged at INFO level without an ERROR traceback.

  8. Exit Code Management: Defines standard exit codes through the ExitCode enum:

    • OK (0): Successful execution

    • USAGE (1): Invalid command-line usage

    • ERROR (2): General execution error

    • ABORTED (3): Process interrupted by signal

Performance Considerations

The complexity figures below use:

  • n = maxActorHistoryPointNumber, the per-actor history size (5-30)

  • k = interpolated positions generated by one CAM insertion, bounded by inputMaxPeriod / (output nominal period - outputPeriodMaxDeviation), at most 80

  • m = number of tracked actors

  • r = number of actors expired by one cleanup

  • o = perceived objects in one CPM message, p = predicted path points per object, g = resampled points per object (at most 101)

Data Structure Performance Characteristics

  • Actor registry (dict): \(O(1)\) lookup of the PointDataset of an actor

  • Temporal index (SortedList): \(O(log(m))\) insertion/deletion

  • Position history (deque with maxlen): \(O(1)\) append, oldest point dropped automatically

  • Interpolation buffers: NumPy arrays of n + 1 entries, allocated once per actor

CAM Message Processing

For one CAM message (ActorDataset.add_cam_message):

  1. Actor Resolution: \(O(1)\) - Hash table lookup

  2. Coherence Checks: \(O(1)\) - One geodesic distance/heading computation

  3. Interpolation (only when the gap exceeds the output period plus the deviation):

    • Spline Construction: \(O(n)\) - Tridiagonal solve over the history

    • Spline Evaluation: \(O(k*log(n))\) - Interval search for each interpolated timestamp

    • Motion and Positions: \(O(k)\) - One batched geodesic call and k positions

  4. Temporal Index Update: \(O(log(m))\)

Overall Complexity: \(O(n + k*log(n) + log(m))\) time and \(O(n + k)\) additional space per CAM message; \(O(log(m))\) on the fast path.

CPM Message Processing

For one CPM message (ObjectPerceivedDataset.add_cpm_message): \(O(o*(p + g*log(p)))\) time and \(O(o*(p + g))\) space: p points parsed, one spline over them evaluated at the estimated grid points, one position array of at most g points per perceived object; no state is kept.

Actor Cleanup

For one cleanup (ActorDataset.clear_old_points):

  1. Expired Actors Search: \(O(log(m))\) - One bisection on the temporal index

  2. Registry Removal: \(O(r)\) - Hash table deletions

  3. Index Removal: \(O(r*log(m))\) - SortedList slice deletion item by item when r < m/8, rebuild of the list otherwise

Overall Complexity: \(O(log(m) + r*log(m))\), \(O(m*log(m))\) in the worst case.

Memory

The total memory is \(O(m*n)\) for the actor histories, plus the transient \(O(n + k)\) buffers of one CAM insertion or the \(O(o*(p + g))\) buffers and output of one CPM message. The actors are removed by the cleaner after inputOldestAllowedTime seconds without a new accepted position.

Bottleneck Analysis

  • Primary Bottleneck: Cubic spline construction and evaluation on the interpolation path (CPU bound)

  • Secondary Bottleneck: Redis stream publication latency (network I/O bound), one publish round trip per message (pipeline over its position arrays, publish_position_arrays)

  • Single Event Loop: Messages are processed one at a time on one asyncio event loop; to scale, run more instances in the same consumer group

  • Actor Partitioning: The actor history is per instance: with several instances, the CAM messages of one sender should reach the same instance to keep its trajectory continuous
