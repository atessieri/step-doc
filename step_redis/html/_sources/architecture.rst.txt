Architecture
============

Overview
--------

The ``step_redis`` package provides robust asynchronous Redis connectivity and stream processing 
capabilities designed for Safer Transport for Europe Platform (STEP) applications. It offers 
enhanced Redis client functionality with a focus on connection management, stream operations, 
and reliable message processing.

The package is built on top of the Redis Python client library and extends it with additional 
features specifically tailored for the needs of distributed systems that require reliable message handling.

Library
-------

The ``step_redis`` package is built on top of the **redis-py** library, the official Python 
client for Redis. This foundational library provides the core Redis functionality that 
``step_redis`` extends and enhances.

**redis-py** is a mature, well-maintained Python library that offers:

   * Comprehensive Redis command support
   * Connection pooling capabilities
   * Async/await support for asynchronous operations
   * SSL/TLS encryption support
   * Pub/Sub messaging functionality
   * Redis Streams support
   * Cluster support for Redis deployments

The ``step_redis`` package leverages redis-py's ``BlockingConnectionPool`` and ``Redis`` 
client classes as its foundation, extending them with additional features specifically 
designed for the Safer Transport for Europe Platform (STEP) requirements. This approach 
ensures compatibility with the broader Redis ecosystem while providing enhanced functionality 
for stream processing, connection management, and reliable message handling.

Key Components
--------------

The package consists of the following main components:

1. **StepRedisPool**: An extended Redis connection pool with ``asyncio`` support
2. **StepRedisStream**: A base comprehensive interface for Redis Streams operations
3. **StepAdapterRedisStream**: Specialized stream handler for STEP Adapter messages (CAM data)
4. **StepClientRedisStream**: Specialized stream handler for STEP Client messages (DENM data)
5. **StepProducerRedisStream**: Specialized stream handler for STEP Producer messages (DENM and collision arrays)
6. **StepCrashPredictionRedisStream**: Specialized stream handler for Crash Prediction messages (position arrays)
7. **StepMonitoringRedisStream**: Specialized stream handler for STEP Monitoring messages (forecasted trajectory data)

Component Details
-----------------

StepRedisPool
~~~~~~~~~~~~~

``StepRedisPool`` extends the ``BlockingConnectionPool`` from redis-py to provide enhanced 
features for asyncio applications. It manages Redis connections with configurable parameters 
and supports both SSL and non-SSL connections.

* SSL/TLS secure connections
* TCP keepalive configuration for connection stability
* Configurable connection limits and timeouts
* Proper resource management through async context managers
* Integrated logging support

StepRedisStreamParams
~~~~~~~~~~~~~~~~~~~~~

``StepRedisStreamParams`` is a frozen dataclass that encapsulates all configuration parameters 
for Redis stream operations. It enforces validation on all fields to ensure correct usage.

**Key Attributes**:

* ``stream_id``: The identifier for the Redis stream (minimum 1 character)
* ``group_id``: The identifier for the Redis consumer group (minimum 1 character)
* ``wait_timeout_ms``: Timeout in milliseconds for waiting to receive a message (non-negative)
* ``max_length``: Maximum length of the stream for automatic trimming (positive integer)
* ``consumer_name``: The name of the consumer (minimum 1 character)
* ``ttl_seconds``: Optional time-to-live in seconds for the stream (positive integer if provided)

StepRedisStream
~~~~~~~~~~~~~~~

``StepRedisStream`` provides a comprehensive base interface for Redis Streams that enables creating, 
managing, and utilizing Redis streams with consumer groups for reliable message processing. This class 
is designed to be extended by specialized stream handlers for different STEP components.

The publisher sends messages to the Redis stream using the a specific stream ID, while consumers read 
messages from the stream using a consumer group. The package ensures that messages are automatically 
acknowledged upon delivery (``noack=True``) for maximum throughput, and it provides mechanisms for 
stream trimming and TTL management to maintain performance and resource efficiency.

**Specialized Stream Classes**:

The package provides five specialized stream implementations that extend ``StepRedisStream``:

* **StepAdapterRedisStream**: Handles STEP Adapter messages, specifically for publishing and consuming 
  Cooperative Awareness Messages (CAM) wrapped in CloudEvents format. Manages CAM data with automatic 
  TTL management.

* **StepClientRedisStream**: Manages STEP Client ITS messages, focusing on Decentralized Environmental 
  Notification Messages (DENM). Publishes CloudEvents-compliant DENM messages to configured streams.

* **StepProducerRedisStream**: Handles STEP Producer services, supporting both DENM messages and 
  station collision array data. Publishes both message types in CloudEvents format.

* **StepCrashPredictionRedisStream**: Specializes in Crash Prediction data processing, publishing 
  position array data as CloudEvents to Crash Prediction streams for real-time analysis.

* **StepMonitoringRedisStream**: Handles STEP Monitoring messages, specifically for publishing 
  forecasted trajectory data and receiving validated monitoring messages from Redis streams for 
  real-time trajectory monitoring and analysis.

Message Flow
------------

Redis Streams Mechanism
~~~~~~~~~~~~~~~~~~~~~~~~

The ``step_redis`` package leverages **Redis Streams**, a log-based data structure that enables 
powerful message streaming capabilities for distributed systems. Redis Streams provide an 
append-only log where messages are immutably stored with unique IDs, allowing multiple 
consumers to process messages independently and reliably.

**Core Concepts**

* **Stream**: An append-only log of messages identified by a stream name (e.g., "cam_stream"). 
  Each message entry has an auto-generated ID (timestamp-sequence) and contains field-value pairs.

* **Consumer Groups**: Enable cooperative message consumption where multiple consumers work together. 
  Each consumer in a group receives different messages, enabling horizontal scaling and load distribution.

* **Consumer**: An individual processor within a consumer group that reads and processes messages. 
  Multiple consumers can be part of the same group to distribute workload.

* **Automatic Acknowledgment**: The package uses ``noack=True`` mode where messages are automatically 
  acknowledged upon delivery, simplifying consumer logic while maintaining high throughput.

* **Stream Trimming**: Streams are automatically trimmed to a configurable maximum length 
  (``max_length`` parameter) using approximate trimming (``~`` operator) for performance efficiency.

* **TTL Management**: Streams can have a Time-To-Live (``ttl_seconds``) that automatically expires 
  streams after the specified duration, useful for temporary data storage.

**Message Publishing Flow**

When a message is published using ``publish_message()`` or specialized methods like 
``publish_cam_message()``, the following operations occur:

   1. Message is serialized to JSON (for CloudEvents-compliant messages)
   2. ``XADD`` command adds the message to the stream with a field named ``payload``
   3. Stream is trimmed to ``max_length`` using approximate trimming (``XTRIM ~ maxlen``)
   4. If configured, stream TTL is refreshed using ``EXPIRE`` command
   5. Message receives a unique ID based on server timestamp and sequence number

**Message Consumption Flow**

When consuming messages using ``receive_message()``, an async generator continuously:

   1. Executes ``XREADGROUP`` to read messages from the consumer group
   2. Uses the special ID ``>`` to receive only new, undelivered messages
   3. Blocks for ``wait_timeout_ms`` milliseconds waiting for new messages
   4. When a message arrives, extracts the ``payload`` field and yields it
   5. Message is automatically acknowledged (``noack=True``) without manual ACK
   6. If configured, refreshes the stream TTL after each read cycle
   7. Continues indefinitely until explicitly stopped

**Stream Initialization**

Before publishing or consuming messages, the stream and consumer group must be initialized:

   1. ``XGROUP CREATE`` creates the consumer group if it doesn't exist
   2. Uses ``mkstream=True`` to automatically create the stream if needed
   3. If the group already exists, the error is caught and logged (idempotent operation)
   4. Initial TTL is set if configured in ``StepRedisStreamParams``

Message Flow Sequence
~~~~~~~~~~~~~~~~~~~~~~

The following sequence diagram illustrates the complete message flow in the STEP Redis 
architecture, showing how publishers, Redis server, and multiple consumers interact:

.. container:: scrollable-diagram

   .. plantuml::
      :align: center

      !theme plain
      
      participant "Publisher\n(StepRedisStream)" as Publisher
      participant "Redis Server\n(Streams)" as Redis
      participant "Consumer Group\nmy_group" as Group
      participant "Consumer 1\n(StepRedisStream)" as Consumer1
      participant "Consumer 2\n(StepRedisStream)" as Consumer2
      
      == Stream Initialization ==
      
      Consumer1 -> Consumer1: create_input_stream()
      Consumer1 -> Redis: XGROUP CREATE my_stream my_group\nmkstream=True
      activate Redis
      Redis --> Consumer1: OK (stream and group created)
      deactivate Redis
      
      Consumer1 -> Consumer1: update_stream_ttl(ttl_seconds)
      Consumer1 -> Redis: EXPIRE my_stream ttl_seconds
      activate Redis
      Redis --> Consumer1: 1 (TTL set)
      deactivate Redis
      
      Consumer2 -> Consumer2: create_input_stream()
      Consumer2 -> Redis: XGROUP CREATE my_stream my_group
      activate Redis
      Redis --> Consumer2: BUSYGROUP (group exists)
      note right: Consumer logs info and continues
      deactivate Redis
      
      == Message Publishing ==
      
      Publisher -> Publisher: publish_message(message)
      Publisher -> Publisher: Serialize message to JSON
      Publisher -> Redis: XADD my_stream MAXLEN ~ max_length\npayload: "{...json...}"
      activate Redis
      Redis -> Redis: Trim stream if length > max_length
      Redis --> Publisher: message_id (e.g., "1234567890123-0")
      deactivate Redis
      
      Publisher -> Publisher: update_stream_ttl(ttl_seconds)
      Publisher -> Redis: EXPIRE my_stream ttl_seconds
      activate Redis
      Redis --> Publisher: 1 (TTL refreshed)
      deactivate Redis
      
      == Message Consumption (Consumer 1) ==
      
      Consumer1 -> Consumer1: receive_message()
      Consumer1 -> Redis: XREADGROUP GROUP my_group consumer1\nSTREAMS my_stream >\nBLOCK wait_timeout_ms COUNT 1 NOACK
      activate Redis
      note over Redis: Consumer1 receives the message\n(automatic acknowledgment)
      Redis --> Consumer1: [[my_stream, [["message_id", {"payload": "..."}]]]]
      deactivate Redis
      
      Consumer1 -> Consumer1: Extract and yield payload
      Consumer1 -> Consumer1: Process message
      
      Consumer1 -> Consumer1: update_stream_ttl(ttl_seconds)
      Consumer1 -> Redis: EXPIRE my_stream ttl_seconds
      activate Redis
      Redis --> Consumer1: 1 (TTL refreshed)
      deactivate Redis
      
      == Message Publishing (Second Message) ==
      
      Publisher -> Publisher: publish_message(message2)
      Publisher -> Redis: XADD my_stream MAXLEN ~ max_length\npayload: "{...json2...}"
      activate Redis
      Redis --> Publisher: message_id_2
      deactivate Redis
      
      == Message Consumption (Consumer 2) ==
      
      Consumer2 -> Consumer2: receive_message()
      Consumer2 -> Redis: XREADGROUP GROUP my_group consumer2\nSTREAMS my_stream >\nBLOCK wait_timeout_ms COUNT 1 NOACK
      activate Redis
      note over Redis: Consumer2 receives message_id_2\n(load distribution within group)
      Redis --> Consumer2: [[my_stream, [["message_id_2", {"payload": "..."}]]]]
      deactivate Redis
      
      Consumer2 -> Consumer2: Extract and yield payload
      Consumer2 -> Consumer2: Process message
      
      == Timeout Scenario ==
      
      Consumer1 -> Consumer1: receive_message()
      Consumer1 -> Redis: XREADGROUP GROUP my_group consumer1\nSTREAMS my_stream >\nBLOCK wait_timeout_ms COUNT 1 NOACK
      activate Redis
      note over Redis: No new messages available,\nwaits for timeout duration
      Redis --> Consumer1: [] (empty response after timeout)
      deactivate Redis
      
      Consumer1 -> Consumer1: Log timeout, continue loop
      
      Consumer1 -> Consumer1: update_stream_ttl(ttl_seconds)
      Consumer1 -> Redis: EXPIRE my_stream ttl_seconds
      activate Redis
      Redis --> Consumer1: 1 (TTL refreshed)
      deactivate Redis

**Key Characteristics**

* **Horizontal Scalability**: Multiple consumers in the same group share the workload, 
  with each message delivered to only one consumer in the group.

* **Automatic Acknowledgment**: Using ``noack=True`` provides maximum throughput by 
  eliminating the overhead of explicit acknowledgments and pending entries list management.

* **Blocking Reads**: Consumers use blocking reads (``BLOCK wait_timeout_ms``) to efficiently 
  wait for new messages without polling, reducing network traffic and CPU usage.

* **Stream Persistence**: Messages remain in the stream until trimmed by length limits, 
  allowing late-joining consumers to catch up on recent history.

* **TTL Refresh Pattern**: Periodic TTL updates ensure active streams remain available while 
  inactive streams automatically expire to conserve memory.

* **Approximate Trimming**: Using approximate trimming (``~`` operator) with ``MAXLEN`` 
  provides better performance by trimming in macro nodes, though actual length may slightly 
  exceed the limit.



Usage Patterns
--------------

The package is designed to be used with async/await syntax in Python and follows context 
manager patterns for proper resource management. Here's a typical usage flow:

   #. Create a ``StepRedisPoolParams`` instance with appropriate connection parameters
   #. Initialize a ``StepRedisPool`` with the parameters
   #. Use the pool to create a ``StepRedisStream`` instance
   #. Perform stream operations (create streams, publish/consume messages)
   #. Properly clean up resources using context managers

Example Usage
~~~~~~~~~~~~~

Base Stream Usage
^^^^^^^^^^^^^^^^^

.. code-block:: python

   import asyncio
   import logging
   from step_redis.step_redis_pool import StepRedisPoolParams, StepRedisPool
   from step_redis.step_redis_stream import StepRedisStream, StepRedisStreamParams

   async def main():
       # Setup logging
       logging.basicConfig(level=logging.DEBUG)
       logger = logging.getLogger()

       # Configure Redis connection parameters
       pool_params = StepRedisPoolParams(
           host="redis.example.com",
           port=6379,
           username="user",
           password="password",
           db=0,
           ssl_enable=True,
           socket_timeout=30,
           socket_connect_timeout=10,
           socket_keep_idle=60,
           socket_keep_alive=10,
           socket_keep_cnt=3,
           ssl_client_key_file=None,
           ssl_client_key_file_password=None,
           ssl_client_cert_file=None,
           ssl_cert_requested=False,
           ssl_ca_certs_file=None,
           health_check_interval=30,
           max_connections=50,
           connection_available_timeout=None,
           protocol=3,
       )

       # Configure Redis stream parameters
       stream_params = StepRedisStreamParams(
           stream_id="my_stream",
           group_id="my_group",
           wait_timeout_ms=5000,
           max_length=1000,
           consumer_name="consumer1",
           ttl_seconds=3600,
       )

       # Create a Redis pool and stream
       async with StepRedisPool(params=pool_params, logger=logger) as pool:
           async with StepRedisStream(pool, stream_params, logger) as stream:
               # Create the input stream and consumer group
               await stream.create_input_stream()

               # Publish a message
               await stream.publish_message("Hello, Redis!")

               # Consume a message
               message = await stream.receive_message(block_timeout=5000)
               print(f"Received: {message}")

   asyncio.run(main())

Error Handling
--------------

The package provides robust error handling for various Redis connection issues:

   * Connection failures (network issues, authentication failures)
   * Operation timeouts
   * Stream-specific errors (non-existent streams/groups)
   * Consumer group management errors

All operations log appropriate error messages and raise relevant exceptions 
that can be caught and handled by the client application.

Design Considerations
---------------------

The ``step_redis`` package was designed with the following considerations:

   * **Reliability**: Ensuring reliable message delivery and processing with automatic acknowledgments (noack=True)
   * **Performance**: Minimizing overhead and maximizing throughput for high-performance applications
   * **Resource Management**: Proper handling of connections and resources through async context managers
   * **Security**: Support for SSL/TLS connections with TLSv1.2+ and client certificate authentication
   * **Configurability**: Extensive configuration options via immutable dataclasses (frozen=True) with validation
   * **Extensibility**: Base stream class designed for specialization by STEP components
   * **CloudEvents Integration**: Native support for CloudEvents-compliant message formats
   * **Type Safety**: Leveraging dataclasses with slots for memory efficiency and type validation

CloudEvents Integration
-----------------------

All specialized stream classes (``StepAdapterRedisStream``, ``StepClientRedisStream``, 
``StepProducerRedisStream``, and ``StepCrashPredictionRedisStream``) integrate with the 
``step_cloud_schemas`` package to provide CloudEvents-compliant message formatting. This ensures:

   * **Standardized Message Format**: All messages follow the CloudEvents specification
   * **Schema Validation**: Messages are validated against defined schemas
   * **Metadata Enrichment**: Automatic inclusion of message IDs, timestamps, source information
   * **Interoperability**: Messages can be consumed by any CloudEvents-compliant system

Each specialized stream class wraps domain-specific data (CAM, CPM, DENM, collision arrays, position arrays) 
in CloudEvents envelopes before publishing to Redis streams, ensuring consistent message structure 
across all STEP components.

This architectural design ensures that the package can handle the demands of distributed 
systems while providing a clean and intuitive API for developers.
