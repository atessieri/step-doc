1.5.0 - 2026-08-25

1.5.0 - Added

  • StepRedisPoolParams gained a new required retry_count field that configures StepRedisPool to automatically retry a failed Redis command (PING, XADD, XREADGROUP) with jittered exponential backoff (redis-py’s default_backoff()) on ConnectionError only, transparently reconnecting instead of raising immediately. Root cause: the Redis server closes connections that have been idle longer than its configured timeout (60s in the current deployment), and step_redis previously had no retry logic anywhere, so the next command on a dropped connection raised uncaught, crashing consumers (e.g. cancelling an entire asyncio.TaskGroup in step_client). retry_count is required, not defaulted, so every caller must choose a value explicitly; pass retry_count=0 to opt out and preserve the previous fail-fast behavior. Deliberately scoped to ConnectionError and NOT TimeoutError: an earlier version of this fix also retried TimeoutError, which caused a regression on receive_message()’s XREADGROUP ... BLOCK <ms> — a read-timeout retry silently re-issued the full block duration on every attempt, starving the stream’s TTL refresh cadence and producing spurious NOGROUP errors once the stream key expired mid-retry. TimeoutError is intentionally left for callers to keep handling as before (receive_message() already does, via except RedisTimeoutError).

1.5.0 - Fixed

  • receive_message() now awaits the stream’s TTL refresh before yielding a received message, instead of only in a finally block that runs the next time the generator is resumed. Root cause: finally in an async generator only runs when the generator is later resumed or closed, which never happens synchronously if the caller breaks out of the async for loop right after receiving a message — exactly the pattern shown in this package’s own usage example. This left the TTL refresh for the last delivered message deferred to an unspecified later point (garbage-collection-triggered finalization), which could also race with __aexit__’s connection teardown.

  • ping() now catches RedisConnectionError/RedisTimeoutError, logs the failure, and re-raises, matching what its docstring already claimed (“logs debug information about the ping attempt and any errors that might occur”). Previously a failing ping() call propagated with no logging from this method at all; only run_health_check(), which wraps its own call to ping(), logged failures.

1.5.0 - Documentation

  • architecture.rst’s StepRedisPoolParams class diagram listed socket_keep_alive as bool; the real field is int (a TCP keepalive probe interval), and the diagram’s wrong type reintroduced exactly the misconception the field’s own docstring warns against.

  • architecture.rst’s CloudEvents Integration section omitted StepMonitoringRedisStream from the list of classes that integrate with step_cloud_schemas, despite it doing so identically to the other four service classes.

  • update_stream_ttl()’s docstring gained a Raises: section documenting the ValueError it raises for a non-positive ttl_seconds.

1.4.2 - 2026-08-21

1.4.2 - Fixed

  • receive_client_message(), receive_adapter_message(), receive_crash_prediction_message(), receive_monitoring_message(), and receive_producer_message() no longer stop consuming when a single message fails Pydantic validation: the ValidationError is now caught, logged, and the message is discarded so iteration continues with the next message.

  • receive_message() now only recovers automatically from RedisResponseError when the error is actually NOGROUP (detected via the server’s error-message prefix, since redis-py exposes no structured error code); any other RedisResponseError is re-raised instead of being silently swallowed and misreported as a NOGROUP/consumer-group-recreation event.

1.4.0 - 2026-08-16

1.4.1 - Fixed

  • Critical: StepRedisStream.receive_message() never yielded messages when the connection pool was configured with protocol=2 (RESP2), because the response from XREADGROUP is a list under RESP2 but only a dict under RESP3, and only the dict shape was handled. Both shapes (plus the None timeout shape) are now normalized and handled correctly.

  • receive_message() could permanently stop consuming messages if the stream’s TTL expired while a blocking read was in progress: the resulting NOGROUP ResponseError was previously unhandled and propagated out of the generator. It is now caught, logged, and the consumer group is automatically recreated.

  • StepRedisStreamParams.__post_init__ now validates that ttl_seconds is strictly greater than wait_timeout_ms (converted to seconds) when both are provided, preventing the misconfiguration that caused the issue above.

  • StepProducerRedisStream.publish_denm_message now uses the current publish time (ItsTime()) for the CloudEvents time field, consistent with every other publish method in the package (it previously used the DENM payload’s own managementContainer.referenceTime).

1.4.1 - Changed

  • Corrected several stale/inaccurate docstrings: a nonexistent RedisStreamConfiguration class name referenced across most modules (the real class is StepRedisStreamParams), broken doctest-style usage examples with outdated method signatures, and a false “TTL is automatically calculated as twice the wait timeout” note present in every subclass’s __init__ docstring.

  • Clarified the socket_keep_alive and ssl_cert_requested fields on StepRedisPoolParams: their docstrings now describe actual behavior (a keepalive probe interval, not an enable/disable flag; and a flag that disables all server-certificate/hostname verification when False, not just client-certificate behavior). No field names or runtime behavior changed.

  • The TCP keepalive option selection in StepRedisPool now branches explicitly on sys.platform == "darwin" instead of sys.platform in ("win32", "linux"), so other non-macOS platforms no longer incorrectly fall into the macOS-only TCP_KEEPALIVE branch.
